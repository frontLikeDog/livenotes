# 录音云存储与飞书分享：方案选项

> 状态：方案调研，未实现
> 日期：2026-11-18
> 关联：[docs/16-recording-sharing-options.md](16-recording-sharing-options.md)、[app/audio.py](../app/audio.py)、[app/feishu.py](../app/feishu.py)、[tools/feishu_bot.py](../tools/feishu_bot.py)、[app/config.py](../app/config.py)

## 0. 结论先行

1. **云存储先回答「为谁存」。** 备份防丢、多设备可用、对外分享是三件事，一套方案很难同时最优。建议主链路是 **对象存储 + 预签名直传（方案 A）**，先覆盖备份与多设备；对外分享继续复用 [docs/16](16-recording-sharing-options.md) 的分享页。**如果首要目标是「不承担存储成本、不接触用户数据」，走 BYOS（第 11 节）**，用用户的网盘/飞书云空间，我们只做接入层。
2. **不要用云盘同步承载产品能力（方案 D）。** 音频文件能同步，SQLite 不能；权限、审计、冲突处理都是黑盒，只适合个人备份。
3. **飞书「只能发到自己会话」不是接口缺失，是寻址和授权模型没做。** 代码里 `send_audio` / `send_file` 已经能发任意 `open_id` / `chat_id`（[app/feishu.py:250](../app/feishu.py:250)、[:267](../app/feishu.py:267)），但入口只有 owner 私聊与白名单群（[app/feishu.py:154](../app/feishu.py:154)、[:527](../app/feishu.py:527)）。
4. **补齐顺序**：复制分享文案（0 开发）→ 机器人接收人选择器（1~2 天）→ 云空间指定协作者（2~3 天）→ 以用户身份发送（需要公网 OAuth，暂缓）。

## 2. 云存储要解决的三个目标

| 目标 | 典型诉求 | 对方案的要求 | 现状 |
|---|---|---|---|
| A 备份防丢 | 硬盘坏了、误删、系统重装 | 自动上传、版本/回收站、低成本 | 无 |
| B 多设备 | 手机听上一场、换电脑继续 | 元数据同步、增量、冲突处理 | 无 |
| C 对外分享 | 发同事/客户/群 | 鉴权链接、过期、撤销、CDN | 半套（局域网 reader + 飞书片段） |

三件事的成本差一个量级：A 只要「存」，B 要「同步协议 + 账号」，C 要「公网 + 权限 + 合规」。**先做 A 再做 B，C 复用分享页**，不要一次性上齐。

## 3. 五种云存储方案

### 方案 A：对象存储 + 预签名直传（推荐主线）

**形态**

- 客户端向后端要一个短期 `PUT` 预签名 URL，音频**直传** OSS/COS/七牛/TOS，不过业务服务器。
- 后端只存元数据：`object_key`、`sha256`、字节数、时长、`session_id`、状态。
- 播放用短期 `GET` 签名 URL + CDN；私有桶，不开公共读。
- 生命周期规则做冷归档与到期删除，和本地保留策略同一套口径。

**优点**

- 便宜、成熟、不限语言；带宽走 CDN，不占本机上行。
- 权限模型现成：私有桶 + 签名 URL + Referer 防盗链 + 限流。
- 与 [docs/16](16-recording-sharing-options.md) 的「分享页」天然一体：页面用 token，音频用签名 URL。
- 可做多云（OSS/COS/R2 同一套 S3 兼容接口），不被一家锁死。

**缺点**

- 同步协议要自己做：去重（`sha256`）、增量、冲突副本、断点续传。
- 国内自定义域名要备案；不备案只能用厂商默认域名。
- 需要账号体系，否则「谁的录音」无法回答。

**工作量**：后端签名 + 元数据 + 生命周期约 1 周；客户端上传队列 3~5 天；多设备同步 1~2 周。

**适用**：要把云存储做成产品能力，长期主链路。

---

### 方案 B：全托管 BaaS（Supabase Storage / 腾讯云开发 CloudBase / LeanCloud）

**形态**：文件桶 + 托管数据库 + 登录 + 行级权限，一套 SDK 全包。

**优点**

- 最快：2~3 天能跑通「登录 → 上传 → 列表 → 播放」。
- 行级权限（RLS）能直接表达「这条录音只有这几个人能看」，不用自己写授权。
- CloudBase 国内合规、微信/企微生态顺；Supabase 海外成熟、SQL 通用。

**缺点**

- 数据模型要从 SQLite 迁或双写，长期有厂商锁定。
- Supabase 国内访问质量需实测；CloudBase 的存储/数据库计费按量，量大后不一定便宜。
- 复杂查询（跨场次话题、说话人聚合）在 BaaS 上不如本地 SQLite 顺手。

**工作量**：MVP 3~5 天；迁移与双写 1~2 周。

**适用**：想快速验证「云端多设备」，但不想先建后端与账号体系。

---

### 方案 C：自建 MinIO / NAS（群晖、TrueNAS）+ 组网

**形态**：一台内网机器当 S3 兼容存储，Tailscale / WireGuard 组网；公网分享走反代或临时隧道。

**优点**

- 数据完全自主，录音不出内网；边际成本≈电费。
- 内网读写极快，适合「采集机 + 存储机」分离。
- 无厂商锁定，S3 SDK 直接可用。

**缺点**

- 单点故障、要运维（磁盘、备份、证书、升级）。
- 公网分享要么穿透（不稳、无 SLA），要么反代（安全面扩大）。
- 团队协作与移动端体验弱。

**工作量**：1~2 天搭起来；要做成产品能力，仍需方案 A 的签名/同步层。

**适用**：隐私硬约束、已有 NAS、个人或小团队自用。

---

### 方案 D：云盘同步（OneDrive / iCloud Drive / 坚果云 / 百度网盘）

**形态**：把 `data/audio` 放进同步目录，靠客户端同步。

**优点**：零开发；自带版本历史与回收站；跨设备无感。

**缺点**

- **SQLite 不能这样同步**，索引与音频会脱节；冲突处理黑盒。
- 无 API 级权限、无访问审计、无过期/撤销；链接二次扩散不可控。
- 移动端播放体验差，大文件限速。
- 公司内容进个人云盘有合规风险。

**工作量**：0.5 天（只改路径）。

**定位**：个人备份可以，**不做产品能力**。

---

### 方案 E：音视频 PaaS（腾讯云点播 VOD / 阿里云智能媒体 / 火山引擎 / 七牛）

**形态**：上传后自动转码多码率、CDN 分发、播放器 SDK、防盗链/DRM、音频审核、ASR。

**优点**

- 播放体验最好：秒开、倍速、HLS、弱网自适应。
- 转码、审核、水印、截图开箱即用，省掉 ffmpeg 运维。
- 大文件分发省心，流量包比对象存储外网价低。

**缺点**

- 贵：转码 + 存储 + 流量三项叠加；绑定厂商。
- 我们的核心资产（时间轴、逐字稿、说话人、校对）仍要自己做，PaaS 带不走。
- 接入复杂度高于纯对象存储。

**工作量**：2~3 周（含播放器替换与转码模板）。

**适用**：对外交付常态化、需要品牌播放页、或要做音频审核。

---

### 0 号基线：不上云

继续本地存储，只补「导出分享包 + 手动备份到移动硬盘」。成本为零，但多设备与防丢问题不解。

## 5. 成本量级（不是报价）

按当前 32 kbps AAC 归档：

| 项 | 量级 |
|---|---|
| 1 小时录音 | 约 14 MB |
| 每天 4 小时、每月 22 天 | 约 1.2 GB/人/月 |
| 100 个重度用户、一年 | 约 1.5 TB |
| 对象存储标准层 | 约 0.1 元/GB/月 → **约 150 元/月/年累积** |
| 外网下行 | 约 0.5 元/GB；100 次完整播放/场 ≈ 1.4 GB ≈ 0.7 元/场 |

**结论**：存储是白菜价，**流量和转码才是成本项**。所以：默认私有桶 + 签名 URL + CDN；整场播放走 CDN 流量包；片段分享优先（体积小一个量级）。

## 7. 飞书集成全景

现在接的是**企业自建应用机器人**（`app_id` / `app_secret` + 长连接），不是自定义机器人 webhook。可接的能力与现状：

| # | 能力 | 形态 | 现在我们能做什么 | 状态 |
|---|---|---|---|---|
| 1 | **机器人消息** | 单聊/群聊发文本、卡片、语音、文件 | `/分享` 发片段、`/分享包` 发 zip | 已实现，寻址受限 |
| 2 | **云文档 docx** | 周报/复盘/纪要写入文档，按人授权 | `/周报`、`/复盘` 建文档并授权发起人 | 已实现 |
| 3 | **云空间 drive** | 上传文件拿 `file_token`，加协作者/设链接范围 | 未接 | 可补 |
| 4 | **多维表格 Bitable** | 录音索引表，附件字段存音频，按记录授权 | 未接 | 可补 |
| 5 | **妙记 Minutes** | 整场音频 + 自动转写 + 时间轴链接 | 人工上传后回填链接 | 半自动 |
| 6 | **日历/会议** | 录音挂日程、会议纪要 | 未接 | 可选 |
| 7 | **小程序/H5 工作台** | 把 reader 嵌进飞书 | 未接 | 可选 |
| 8 | **审批/任务** | 复盘行动项进审批/任务 | 未接 | 可选 |

**优先级**：#1 补齐寻址 → #3 做正式交付 → #4 做团队素材库 → #5 等租户验证 → 其余按需。

### 关键接口（已核实）

- 上传音频：`POST /open-apis/im/v1/files`，`file_type=opus`，单文件 ≤ 30 MB，返回 `file_key`；其他格式需先转 OPUS（单声道 16 kHz）。
- 发送消息：`POST /open-apis/im/v1/messages`，`receive_id_type` 支持 `open_id` / `union_id` / `user_id` / `email` / `chat_id`；`msg_type` 支持 `file` / `audio`。
- 权限：`im:message` 或 `im:message:send_as_bot`；上传资源需 `im:resource`。
- **自定义机器人 webhook 不可用于此场景**：只能在它被添加的那个群发消息，不支持单聊，不支持 `file` / `audio`，请求体 ≤ 20 KB。如果哪条链路还在用 webhook，那就是「发不出去」的直接原因。

## 8. 「发给一个人/一个群」为什么现在不完善

代码层面的三个事实：

0. **仓库内没有任何 webhook 配置**，线上不存在「自定义机器人」链路；能力本身是齐的，缺的是寻址。
1. **寻址只有一个默认值**：`_send()` 里 `rid = open_id or self.open_id`（[app/feishu.py:181](../app/feishu.py:181)），没有「选人」参数；上层分享永远发回当前会话。
2. **群是白名单，不是通讯录**：群聊消息先判断 `chat_id not in bot.chat_ids` 就丢弃（[app/feishu.py:527](../app/feishu.py:527)）。白名单是「允不允许这个群用机器人」，不是「可以发到哪些群」。
3. **私聊只认 owner**：`admit()` 只放行 `owner_open_id`（[app/feishu.py:154](../app/feishu.py:154)），其他人发消息直接忽略。

再叠加平台规则：

- 机器人只能向**它已在的群**发消息；不在群里就发不了，这是平台约束，不是 bug。
- 机器人给用户发单聊，要求对方在**应用可用范围**内；范围外发不出去。
- 以 `tenant_access_token` 发出的消息，接收方看到的是**机器人**，不是「我」。

## 9. 四条修复路线

### 路线 A：机器人 + 接收人选择器（推荐，1~2 天）

- 单聊：搜索组织内用户 → `open_id` → `im/v1/messages`。
- 群聊：`GET /open-apis/im/v1/chats` 列出机器人所在群 → `chat_id`。
- 群不在列表：提示「先把机器人拉进群」，或降级为复制链接。
- 需要补的权限：`im:message:send_as_bot`、`im:resource`；搜索用户还需通讯录只读权限。
- 产品约束要写清楚：**机器人只能发到它所在的群**，这是选择器要显式告诉用户的。

### 路线 B：复制分享文案/链接（0.5 天，先上）

- 生成一段可直接粘贴的文案：`【录音片段】CH01 18:21–18:25｜一句话摘要｜<链接>`。
- 用户自己粘贴到任何单聊/群，**100% 可达、零权限申请**。
- 链接指向分享页（带 token、过期、撤销），比直接发文件更可控。
- 已有基建可复用：`/api/share/info`（[app/server.py:1398](../app/server.py:1398)）、分享卡复制链接与下载 PNG（[app/web/js/sharecard.js:365](../app/web/js/sharecard.js:365)），只需把「片段」纳入同一张卡。
- 这是最快补齐「能发给任何人」的方式，也是路线 A 的降级兜底。

### 路线 C：以用户身份发送（进阶，2~3 天 + 公网条件）

- OAuth 拿 `user_access_token`，权限 `im:message.send_as_user`，以「我」的身份发到我有权限的会话。
- 最符合「分享」的心智：接收方看到的是本人，不是机器人。
- 障碍：OAuth 需要 `redirect_uri`，当前服务无公网域名；token 2 小时、refresh 30 天，要处理续期。
- 建议等云存储/分享页有公网入口后再做。

### 路线 D：云空间 + 指定协作者（2~3 天）

- `drive/v1/files/upload_all` 上传拿 `file_token`。
- `drive/v1/permissions/{token}/members` 把指定人加为 `viewer`，或设置链接分享范围与过期。
- 适合「给对方一个文件」而不是「发一条消息」；权限与审计由飞书管。
- 短板：对方要在飞书里打开，且没有时间轴联动。

### 组合建议

| 时间 | 做什么 | 解决什么 |
|---|---|---|
| 本周 | 路线 B | 「能发给任何人」，零风险 |
| 下周 | 路线 A | 「在应用里直接选人/选群」 |
| 之后 | 路线 D | 「正式交付、权限可审计」 |
| 待公网 | 路线 C | 「以我身份发送」，体验最好 |

## 10. 合规清单

1. **定性**：录音含第三方声音，属于个人信息；声纹可识别身份，属于敏感个人信息，需要单独同意与更严格的最小化。
2. **位置**：云端存哪个地域、是否出境，决定合规路径；国内优先选境内区域。
3. **加密**：传输 TLS；存储服务端加密；分享链接用短期签名，不暴露长期密钥。
4. **保留期**：云端与本地同一口径；场次删除时对象存储同步删除，分享链接随之失效。
5. **授权**：录音来自直播/会议，再分发要有主播/参会人授权；默认只做内部，外发逐次确认。
6. **审计**：谁在何时听了哪一段、是否下载；至少进现有事件流。
7. **最小化**：默认分享片段 + 摘要，不默认给整场原声。

## 11. 让用户自带存储（BYOS）

### 11.1 先拆责任：省的是哪一块

| 责任 | 自建（方案 A） | BYOS |
|---|---|---|
| 存储容量 | 我们付 | 用户付 |
| 下行流量 | 我们付（CDN） | 用户付 / 对方网盘承担 |
| 元数据与索引 | 我们存 | **仍要解决**（见 11.4） |
| 分享与权限 | 我们做 token/过期/撤销 | 用对方平台原生权限，**我们无法撤销** |
| 合规责任 | 我们是处理者，要等保/加密/审计 | 数据不经过我们，责任大幅下降 |
| 研发与客服 | 一套后端 | N 个渠道的接入、token、兼容、排障 |

**一句话**：BYOS 把「可变成本」换成了「固定研发成本 + 客服成本」。用户少的时候不划算，用户多的时候很划算。

### 11.2 五种形态

#### A. 系统同步文件夹（零集成，最快）

把 `data/audio` 指到 iCloud Drive / OneDrive / 坚果云同步目录，靠系统客户端同步。

- 优点：**零 API、零 OAuth、零审核**，1~2 天可上线；用户心智简单。
- 缺点：只解决"文件在"，不解决索引；SQLite 不能这样同步；iOS/Android 端无法直接读。
- 适用：桌面端首发、个人用户。

#### B. 网盘 App 文件夹（Google Drive / OneDrive / Dropbox）

用各家的"应用专属文件夹"授权：`drive.file`、`Files.ReadWrite.AppFolder`、`app_folder`。

- 优点：只碰自己创建的文件，权限最小；跨平台；用户能在外网盘里看到并转发。
- 缺点：国内可达性差（Google/Dropbox）；每家一套 OAuth 与限流；应用商店对云盘权限有额外审核。
- 适用：海外用户、Mac/iOS 生态。

#### C. 通用协议（WebDAV / S3 兼容）

用户填服务器地址与凭证：坚果云、群晖、Nextcloud、MinIO、R2、OSS。

- 优点：**一套协议覆盖大量私有云**；国内可用；企业客户接受度高；无需逐家审核。
- 缺点：配置门槛高（地址、端口、路径、应用密码）；各家 WebDAV 实现有差异；质量参差。
- 适用：NAS 用户、技术型用户、企业内网。

#### D. 飞书 / 企微云空间（用户 OAuth）

用户授权后，音频上传到**他自己租户的云空间**，分享用飞书原生权限。

- 优点：零存储成本；权限、审计、水印、外部分享策略全是飞书现成的；组织内转发最顺。
- 缺点：需要 `user_access_token` 与 OAuth 回调（桌面端能否登记 `127.0.0.1` 需在租户后台验证）；跨租户分享仍受管理员策略限制；每条录音都产生一次云空间写入。
- 适用：已经把飞书当工作台的团队——**这也是我们最顺的一条**。

#### E. 企业自带应用 / 私有化

客户在自己的飞书租户里建自建应用，填 `app_id` / `app_secret`，数据全留在客户租户。

- 优点：B2B 最容易被安全/IT 部门接受；我们零存储、零数据接触。
- 缺点：每家客户一次部署与权限沟通；版本升级要跟着客户走。
- 适用：中大型企业客户、对数据出境/等保有硬要求的场景。

### 11.3 对比矩阵

| 维度 | A 系统文件夹 | B 网盘 App | C WebDAV/S3 | D 飞书云空间 | E 企业自带应用 |
|---|---|---|---|---|---|
| 我们出的存储成本 | 0 | 0 | 0 | 0 | 0 |
| 接入工作量 | 1~2 天 | 每家 3~5 天 | 3~5 天 | 3~5 天 | 5~10 天/客户 |
| 中国可用 | ★★★★★ | ★★ | ★★★★★ | ★★★★★ | ★★★★★ |
| 跨平台 | ★★ | ★★★★ | ★★★★ | ★★★★ | ★★★★ |
| 分享能力 | ★（靠系统） | ★★★★ | ★★★ | ★★★★★ | ★★★★★ |
| 用户配置难度 | ★★★★★（最简单） | ★★★★ | ★★ | ★★★★ | ★★★ |
| 我们能撤销分享 | 否 | 否 | 否 | 否（飞书管） | 否（客户管） |
| 审核/合规门槛 | 无 | 中（应用商店） | 低 | 低 | 中 |

### 11.4 三个必须解决的坑

1. **元数据也得跟着走。** 只把音频放远端，换台机器就没有标题、逐字稿、说话人。解法：每场录音在远端放一个 sidecar `<sid>.json`（标题、时长、说话人、逐字稿指针），本地索引可由远端目录**重建**。这样 SQLite 不需要同步，只需要缓存。
2. **分享链接的权限归用户，我们撤销不了。** 自建方案能"过期/撤销/审计"，BYOS 不能——链接在对方网盘手里。产品文案不能承诺"可撤销"。
3. **token 会过期、接口会限流、网络会断。** 必须本地优先：先落本地，队列重试，失败不影响录音；远端只是副本，不是真相源。

### 11.5 成本对比（量级）

| | 自建对象存储 | BYOS |
|---|---|---|
| 1 万重度用户、一年 | 存量约 70~140 TB，存储约 0.7~1.4 万元/月，下行流量通常更高 | 存储 0 |
| 研发 | 1 套后端 + 同步协议 | 每个渠道 3~5 人天 |
| 长期 | 成本随用户线性增长 | 研发一次、边际近乎为零 |
| 风险 | 容量承诺、数据泄露责任 | 第三方 API 变更、用户配置失败 |

**结论**：自建存储本身并不贵，贵的是流量与责任。BYOS 真正的价值是**不承诺容量、不接触数据**，而不是省下那点存储费。

### 11.6 推荐的产品形态：混合

| 版本 | 存储 | 说明 |
|---|---|---|
| 免费 / 个人 | BYOS（本地文件夹 + WebDAV） | 我们零成本，用户自己接管 |
| 团队 / 付费 | 我们的托管存储（方案 A） | 卖点是"不用配、换机就能用" |
| 企业 | 自带应用 / 私有化（方案 E） | 数据不出客户租户 |

**首发只做三种**：A 系统文件夹、C WebDAV、D 飞书云空间。B 网盘 App 放在海外版再做。

### 11.7 对「发给一个人/一个群」的直接影响

如果音频在**用户自己的飞书云空间**，分享就退化成飞书原生操作：用户在飞书里选人、选群、设权限，我们不用做接收人选择器。这条路径能绕开第 8、9 节的全部问题。

代价是：每条录音都要 OAuth + 云空间写入；跨租户仍受管理员策略限制；我们拿不到完整的访问审计。**适合"团队已经在飞书里"的场景，不适合"发给外部客户"的场景。** 具体落地拆解见第 12 节。

## 12. 落地设计：飞书云空间作为主存储

> 前提：产品完全跑在飞书上，不自建对象存储。目标是把「存」和「分享」都交回飞书。

### 12.1 两种子形态，差别在文件归谁

| | D1 用户个人云空间 | D2 应用云空间 + 授权 |
|---|---|---|
| 调用身份 | `user_access_token`（OAuth） | `tenant_access_token` |
| 文件落点 | 用户「我的空间」 | 应用自己的文件夹 |
| 是否需要 OAuth 回调 | **是**（桌面端要解决 `redirect_uri`） | 否 |
| 文件归属 | 用户本人 | 应用 |
| 配额算谁的 | 用户个人云空间 | 租户/应用云空间 |
| 用户能否原生转发 | 能 | 能（授予 `full_access` 后） |
| 实现难度 | 高 | 低 |

**建议 MVP 走 D2**：不需要 OAuth，复用已有的 `FEISHU_DOC_FOLDER_TOKEN` 与 `create_docx` 的授权套路（[app/feishu.py:296](../app/feishu.py:296)），一周内能跑通。D1 等有公网回调或飞书网页应用形态后再做。

> 注意：D2 的「用户自己的云空间」严格说是**公司租户的云空间**，文件所有者是应用。离职、应用被停用都会影响文件。要「跟人走」必须 D1。

### 12.2 数据流（D2）

```text
录音结束
  → 本地转 m4a（已有，app/audio.py）
  → 判定是否「归档」：手动标记 / 超长场次 / 周报引用
  → drive/v1/files/upload_all（≤20 MB）或分片上传（>20 MB）
  → 拿到 file_token
  → drive/v1/permissions/{token}/members 授予操作者 full_access
  → 发一张卡：已存入云空间 [打开] [复制链接]
  → 用户在飞书里打开 → 分享 → 选人/选群/设权限（飞书原生）
```

第 6 步是关键：**我们不选接收人，用户自己在飞书里选**。上一轮的寻址问题（第 8 节）在这条路径上不存在。

### 12.3 接口与限制（已核实）

| 项 | 事实 |
|---|---|
| 上传 | `POST /open-apis/drive/v1/files/upload_all`，`parent_type=explorer`，`parent_node=<文件夹 token>` |
| 单文件上限 | **20 MB**；超过必须走分片上传 |
| 调用身份 | `tenant_access_token` 或 `user_access_token` 均可 |
| 权限点 | `drive:drive` / `drive:file` / `drive:file:upload` 任一 |
| 频率 | 5 QPS、10000 次/天 |
| 加协作者 | `POST /open-apis/drive/v1/permissions/:token/members?type=file` |
| 协作者类型 | `openid` / `email` / `openchat`（群）/ `opendepartmentid` 等 |
| 权限角色 | `view` / `edit` / `full_access` |

**待实测**（不要写进承诺）：
- 租户云空间配额与单文件上限的实际值；
- 桌面端能否把 `http://127.0.0.1:<port>/callback` 登记为 OAuth 重定向地址；
- 分片上传的单文件最大尺寸与分片规则。

**已实测（2026-11-27，手机端真机）**：

**在线播放能力（最关键的一条，结论已定）**：

| 格式 | 手机飞书点开 | 结论 |
|---|---|---|
| `m4a`（含 5 分 22 秒整场） | 出现播放器、进度条可拖、显示 `00:02 / 05:22` | **A 可在线播放** |
| `mp3` | 同上 | **A 可在线播放** |
| `wav` | 同上 | **A 可在线播放** |
| `opus` | 「该文件类型无法查看：.opus」+「用其他应用打开」 | **C 不可预览** |

所以：
- **手机能听整场这件事成立**，前提是归档的是 m4a（现在生产的正是 m4a，AAC 32 kbps），
  不需要额外转 mp3，也不需要 opus。
- `opus` 只适合当飞书语音消息（`im/v1/files` 的 `file_type=opus`），**不要**放进云空间当归档格式。
- 这条写法要钉死：接口侧的 `type`/`doc_type` **完全无法区分**（全部报 `file`），
  以后别指望用 API 判断，改格式前都要真机点一次。

**其余接口结论**：
- `upload_all` 返回体自带 `url`，是**租户域名**（`https://<tenant>.feishu.cn/file/<token>`）；
- 通用域名 `https://feishu.cn/file/<token>` 会 301 到 `www.feishu.cn` 再跳登录页，
  **不能**当兜底链接用——这是 `app/feishu_drive.py::file_url()` 现在的默认值，见 [docs/51](51-archive-on-publish-brief.md)；
- `drive/v1/permission_member` 用 `type="folder"` 授权文件夹**可用**（`code=0`），
  docs/50 阶段 3 的前提成立；
- 分片上传（`upload_finish`）的返回体同样带 `url`；5 分 22 秒的 1.28 MB 整场 m4a
  走的是 `upload_all` 单次上传，播放正常。

### 12.4 产品规则（比接口更重要）

1. **不要默认全量上传。** 4 小时/天 ≈ 58 MB/天 ≈ 1.7 GB/月/人，10 个人一年就是 200 GB。只上传「标记归档」「周报引用」「要分享」的场次。
   > **2026-11-27 调整**：发布即归档已经落地（[docs/50](50-cloud-folders-and-archive.md) 阶段 0），因为这里的「全量」实际只指已发布的场次，且只传 m4a。`FEISHU_ARCHIVE_ON_PUBLISH=0` 可回到只手动上传。
2. **超过 20 MB 必须分片。** 1 小时场约 14 MB 可以直接传；2 小时以上一定会超，分片上传是必做项，不是优化项。
3. **本地仍是真相源。** 云空间是副本；上传失败进重试队列，不影响录音与回听。
4. **删除要显式。** 本地删除不自动删云端（用户可能已经转发出去）；云端删除也不影响本地。两边各自留痕。
5. **配额要可见。** 上传前查剩余容量，不足时提示「清理旧场次」而不是静默失败。
6. **跨租户分享仍受管理员策略限制。** 发给外部客户前要验证；不通就回退到分享包或自建分享页。

### 12.5 会得到什么、失去什么

**得到**：零新增存储账单；飞书原生权限、审计、水印、外部分享策略；组织内转发路径最短；不用做接收人选择器。

**失去**：reader 的时间轴联动（飞书里只有文件和播放器）；跨租户外部分享的可控性；分享链接的撤销权（在文件所有者/管理员手里）。

**成本性质变化**：不是「零成本」，是**从我们的云账单转移到公司的飞书云空间配额**。对内部工具是划算的，对多租户 SaaS 要重新算。

### 12.6 工作量

| 项 | 工作量 |
|---|---|
| 上传 + 分片 + 授权 + 卡片 | 3~5 天 |
| 归档标记、配额检查、重试队列 | 2 天 |
| 真实租户验证（预览、配额、外部分享） | 1~2 天 |
| 合计 | **约 1 周** |

## 13. 待拍板

1. **云存储首要目标是哪个**：备份防丢 / 多设备 / 对外分享？三者预算与工期差一个量级。
2. **录音是否允许出内网/出公司**？决定选 A/B 还是 C。
3. **分享默认单位**：整场还是片段？建议片段。
4. **谁能发起分享**：只有 owner，还是白名单群成员也可以？
5. **是否必须「以我身份发送」**？如果是，就要规划公网域名与 OAuth。
6. **云端与本地谁是真相源**：云端删除后本地是否保留？建议本地优先、云端可重建。
7. **商业模式选哪种**：全 BYOS（零成本、配置门槛高）/ 全托管（体验最好、成本我们担）/ 混合（免费 BYOS、付费托管）？这决定要不要建账号体系与计费。
8. **云空间用 D1 还是 D2**：D1 文件跟人走但要做 OAuth；D2 一周可上线但文件归应用、算租户配额。
9. **是否默认全量上传**：建议默认只传「标记归档/要分享」的场次，避免配额被日常录音吃光。
