# 41 · 语音厅知识化：从「一场直播的笔记」到「一个越听越懂你的大脑」

> 面向：产品、设计、实现
> 依据：[30 · 场面高光与叙事周报](30-scene-highlights-and-narrative-weekly.md)、[36 · P1 第二次打开](36-p1-second-visit-iteration-plan.md)、[38 · P2 增长与商业化](38-p2-growth-and-monetization-options.md)、[07 · AI 分析流水线](07-ai-analysis-pipeline-decision.md)、[05 · 声纹与说话人](05-voiceprint.md)
> 结论时间：2026-11-18
> 一句话：**用户嫌「笔记混乱」，根因不是总结写得差，是我们一直用「一场直播 = 一个主播 + 几个嘉宾」的直播电商模型在建模，而用户录的是「10 人语音厅、十几二十人轮流上麦、主持人只暖场」的多人讨论。先换模型（场 = 一档节目、人 = 跨场实名的主讲人、内容 = 可积累的观点），再谈 AI 管家；否则 AI 只会把混乱整理得更整齐一点。**

阅读路径：只看结论读 §0、§7、§9；看数据怎么改读 §3；看 AI 管家落地读 §4；看排期读 §8。

## 0. 结论先行

### 0.1 你的判断里，哪几条我完全同意

1. **G1「主播返场卡」在你们的产品形态里是错位的。** 语音厅没有「被记录的主播」。主持人（麦序、暖场、叫人上麦）发言占比可能不到 15%，真正的内容在轮流上麦的十几个人身上。让「主播」署名发粉丝群，等于让一个话最少的人去代表一场内容最多的直播。**传播主体应该是「这场讨论本身」和「讲得最好的那几位」**，不是房间的主人。
2. **G2「免费工具矩阵」和产品定位同病**：三个工具（回放转文字 / 开播提醒 / 话术提取）全都预设了「直播电商 + 主播话术」的场景。在语音厅里，「话术提取」没有意义，「回放转文字」有意义但太通用、打不过大厂。**这条可以不砍，但必须换题。**
3. **「系统分不清知识型主讲 vs 多人观点碰撞」——这是准确的自我诊断。** 见 §1 的代码证据：我们的整条 AI 链路里，`主播` 是一个**按发言时长排序**自动贴上的标签，`嘉宾N` 是顺序编号，跨场身份按「标签名」对齐而不是声纹。这三件事加在一起，系统眼里的语音厅就是「一个话最多的人 + 一堆龙套」。
4. **「笔记没有看下去的欲望」不是文案问题。** 现在的笔记页是按「要点 1/2/3 + 高光 + 书签」列的，每一条都是「主播说了什么」。在语音厅里，读者真正想知道的是「**这场的几个观点分别是谁提的、彼此怎么冲突、谁最值得跟**」。我们的页面结构里没有任何一层能回答这个。

### 0.2 你想要的「AI 大脑」，现在有几分之几

| 能力 | 现状 | 代码位置 | 差距 |
|---|---|---|---|
| 存录音 + 逐字稿 | ✅ 有 | `sessions` / `utterances` | — |
| 说话人区分 | ⚠️ 有，但上限 8~10 人、跨场按标签而非身份 | `app/live.py:1226`、`app/recluster.py:27` | 语音厅「十几二十人上麦」直接撑爆 |
| 跨场认人 | ✅ 有（声纹底库） | `app/voiceprint.py`、`person_emb` | 只有「谁在不在」，没有「他说过什么」 |
| 单场总结 | ✅ 有（理解段 1 次调用） | `app/analysis.py`、`summaries` | 只理解单场，不跨场 |
| 跨场周报 | ✅ 有（主线 + 证据门） | `app/report.py`、`weekly.py` | 按「话题」聚合，不按「人和观点」聚合 |
| 全文检索 + 问笔记 | ✅ 有（FTS5 + 引用） | `app/notes.py`、`app/qa.py` | 检索单元是「一场的要点」，不是「一个人的观点」 |
| 知识库 / 长期记忆 | ❌ **没有** | — | 每一场的结论都散在各场 `summaries` 里，没有合并、没有演化、没有「上次说过什么」 |
| 主动追问 / 对话 | ⚠️ 有问笔记，但是**一次性问答** | `app/qa.py` | 没有会话历史、没有追问上下文、不会主动找你 |
| 人物档案 | ⚠️ 只有「出没记录」 | `app/web/people.html` | 没有「这个人主张过什么、擅长什么、观点变过没有」 |

**所以「现在有没有一个 AI 知识库」的准确回答是：没有知识库，只有一堆积木。** 转写、说话人、总结、检索、周报这五块都在，但它们各自独立、以「场」为最小单位，没有任何一层把「一个人在多场里反复讲的同一件事」连起来。你感觉「笔记混乱」，本质上是我们把**素材**（每场逐字稿和要点）当成**成品**交给了你。

### 0.3 我的主张：不是「加一个 AI 总结」，是换三层模型

| 层 | 现在 | 应该变成 | 为什么这是根 |
|---|---|---|---|
| **场** | 一场 = 一次直播 = 一篇笔记 | 一场 = **一档节目的一期**（主持人 × 本场主题 × 上麦名单） | 语音厅是按「档期」运营的，同一档节目每周固定开，人和主题都在延续 |
| **人** | `主播/嘉宾N` 位置标签 | **主持人 / 主讲 / 上麦嘉宾** 三种角色，跨场用声纹实名 | 「是不是一个知识储备多的人在输出」就是靠角色 + 跨场发言史判断的 |
| **内容** | 每场要点，互不相连 | **观点（claim）** 是原子，跨场合并、标明谁提的、有没有被反驳/修正 | 「笔记混乱」= 观点没有被结构化成可比较的单元 |

做到这三层，你要的「AI 管家」才有地基：
- 它知道**这个人上次在别的场讲过同一件事，而且这次说法变了**；
- 它知道**这场是一场圆桌，有三个立场**，而不是「主播说了 5 个要点」；
- 它能答「关于 OPC，阿哲和小鹿的观点有什么分歧」——因为它的检索单元是「人 × 观点」，不是「场 × 要点」。

### 0.4 对 G1 / G2 的具体改法（不砍方向，换载体）

| 原方案 | 问题 | 改成 | 为什么这次对 |
|---|---|---|---|
| G1 主播返场卡 | 语音厅没有「主播即内容」 | **G1'「本场观点卡」**：一场生成 3 个「谁 × 什么观点 + 一句原话」，落款是「本场 12 人上麦，来自 XX 语音厅」；由**观点提出者本人**转发，不是主持人 | 传播动机从「我替你宣传」变成「**我讲的东西被认真记录了**」——对知识型上麦者这是强动机；对主持人仍然有动力（他转发的是「我主持的场」） |
| G2 免费工具矩阵 | 三个工具都是电商直播语境 | **G2'「语音厅内容助手」**：① 回放/录音转文字（保留）② **多人圆桌摘要**（上传一段多人录音，输出「谁说了什么观点、分歧在哪」）③ **上麦者名片**（把一个人在你这儿录过的所有发言，生成一页「他讲过什么」） | ②③ 都是「只有做过语音厅记录的人才会想到的工具」，大厂不会做；而且②③正好是内部能力的公开切片，不额外造轮子 |

### 0.5 一句话取舍

- **做**：场次形态识别（单人输出 / 圆桌 / 问答厅）→ 说话人容量与角色 → 观点原子 + 跨场人-观点档案 → 对话式追问 → 主动推送。
- **不做**（本轮）：向量库（数据量还不需要）、通用聊天助手（不做「什么都聊」的豆包式入口）、自动替用户下结论、把语音厅内容公开分发的任何形态。
- **先做哪一步**：**§3 的「观点原子」+ §2 的「场次形态与角色」**。这两步不做，后面所有 AI 功能都是在错的模型上加层。

## 1. 为什么现在会觉得「乱」：四条代码证据

不是感觉问题，是建模问题。下面每条都能点进代码看。

### 1.1 「谁是主播」是按发言时长算出来的

`app/live.py:1226 _labels_locked()`：

```python
auto[self.host_id] = "主播"
...
auto[sid] = "嘉宾" if n == 1 else "嘉宾%d" % n
```

`host_id` 取的是**累计发言秒数最多**的簇，并且带滞回（`app/live.py:1236`，超过 1.6 倍且多 20 秒才换）。

在直播电商里这基本对；在语音厅里它会把「本场话最多的那个上麦嘉宾」标成主播。于是一个 90 分钟、12 人上麦的厅，整理出来的笔记读起来就是「主播说了 A、B、C」——**而真正的内容是那 12 个人说的**。这是「笔记没有看下去欲望」的第一来源：主语错了。

### 1.2 说话人上限 8~10，语音厅直接溢出

- 实时聚类 `LIVE_MAX_SPEAKERS` 默认 **8**（`app/config.py:108`）；
- 结束后重聚类 `KMAX_HARD = 10`（`app/recluster.py:27`）；
- 超限时 `Clusters.assign()` 的行为是「并到最像的那一个」（`app/live.py:270` 附近的 fallback），不是报错。

你说「一场直播可能十几二十个人上麦」。那么第 9 个人开始，系统就在**默默把不同的人合并**，而用户完全不知道。这比「分不准」更糟：**分错了但看起来分好了**。

### 1.3 跨场身份按「标签名」对齐，不按声纹

`app/coach.py:160 cross()` 的注释写得非常诚实：

> 身份是按**标签名**对齐的（每场里都叫「主播」的那个），不是按声纹。

也就是说，「阿哲上周讲了什么」在现有实现里是靠「上周那场里标签也叫阿哲的那个簇」来拼的；如果那场他被标成「嘉宾2」，就断了。`persons` / `person_emb` 那套声纹底库是做**认人**的（他在不在场），但**没有接到内容层**：`person_appearances()`（`app/store.py:1444`）只返回「哪场、哪段、几句」，不返回「他说了什么观点」。

### 1.4 检索与问答的单位是「场」，不是「人 × 观点」

`app/notes.py:197 index_session()` 把一场索引成 summary / point / highlight / bookmark 四类单元，全部挂在 `session_id` 下；`app/qa.py:61 retrieve()` 检索的就是这些单元。所以问「阿哲怎么看 OPC」，召回的是**包含「阿哲」字样的句子**或**那场的要点**，而不是「阿哲这个人关于 OPC 的主张」。`app/store.py:2389 search_note_units()` 的 SQL 里甚至没有 speaker 维度的过滤条件（只有 text / title LIKE 或 FTS MATCH）。

**结论：不是 AI 不够聪明，是喂给 AI 的单元里根本没有「谁的主张」这个字段。**

## 2. 第一层：场次形态与角色（先让系统知道这是哪种直播）

### 2.1 三种形态，先分类再整理

| 形态 | 特征 | 整理方式 | 现有能力够不够 |
|---|---|---|---|
| **单人输出**（讲课/口播） | 主持人占比 > 55%，其余是零星提问 | 现在的「要点 + 高光」就对 | ✅ 够 |
| **圆桌讨论**（语音厅主形态） | 3~15 人轮流，主持人占比 < 30%，同话题多立场 | 要变成「**观点 × 人**」，见 §3 | ❌ 不够 |
| **问答厅**（连麦答疑） | 一问一答成对出现，提问者多、回答者集中 | 要变成「**问题清单 + 谁答的**」 | ⚠️ 半够（`question_consult` 类别已在，但没成对） |

### 2.2 形态判定：0 token 的本地规则，够用

在 `analysis.finalize()`（`app/analysis.py:891`，已经是 0 次模型调用的汇总段）里加一段判定，用已有数据就能算：

```
主持占比   = host_seconds / total_speech_seconds
发言人效   = 发言 >= 30 秒的簇数
问答密度   = question_consult 句数 / 总句数
换手频率   = speaker switch 次数 / 分钟
```

- `主持占比 >= 0.55` → 单人输出
- `问答密度 >= 0.25 且 发言人效 <= 3` → 问答厅
- 其余 → 圆桌

判定结果落一个 `sessions.shape` 字段（`single | roundtable | qa`），**只用于选择整理模板和默认展示，不阻断任何现有页面**。

> 为什么不调模型：形态是结构性特征，规则在 20 场真实录音上调阈值就够了。调模型反而会因为「模型觉得这像讲课」把结构判歪，而结构判歪会让后面所有整理都歪。

### 2.3 角色：三种，不是「主播 + 嘉宾N」

| 角色 | 判定依据（按可信度排序） | 落点 |
|---|---|---|
| **主持人**（host） | 人工确认 > 麦序/欢迎/点名话术密度（`coach.SCRIPT_GROUPS` 的 `welcome`/`guest` 已有正则）> 换手时「接话者」比例 | `speakers.role` |
| **主讲 / 上麦嘉宾**（speaker） | 单次连续发言 >= 60 秒，或本场发言时长 top-3 且实质发言占比 >= 60% | `speakers.role` |
| **听众 / 短问**（asker） | 平均单次发言 < 15 秒且以提问结尾 | `speakers.role` |

关键改动有三条：

1. **主持人和「主播」解耦**。语音厅里主持人是流程角色，可能话最少。UI 上把「主播」这个词换掉——在圆桌形态里显示「主持」和「主讲」，在单人形态里才显示「主播」。
2. **角色是场内的，身份是跨场的**。`speakers.role` 跟着场次走；`persons` 跟着声纹走。一个人可以是「A 场的主持人、B 场的主讲」。
3. **主持人的发言默认降权**。`coach.SCRIPT_GROUPS` 里那套「欢迎/感谢/关注/转化/留人」正则在语音厅里命中的大多是主持流程话术，现在它们已经被 `host_control` 分类降权了；角色判定之后可以再降一档，并把「主持人发言占比」从质量指标里去掉——**在语音厅里主持人话多不是优点**。

### 2.4 说话人容量：8 → 可配置，并且「溢出必须可见」

- `LIVENOTES_MAX_SPEAKERS` 默认从 8 提到 **12**，并在设置页给出说明「实时聚类上限；超出后会被并入最接近的声音」；
- `recluster.KMAX_HARD` 从 10 提到 **16**；
- **最重要的是让溢出可见**：`Clusters.assign()` 在「超过 max_n 且相似度不够」时走的是并入分支，这里要给会话记一个 `speaker_overflow` 计数，场次详情和笔记页显示「本场有 N 段语音因超出人数上限被合并到其他说话人」。
- 语音厅「十几二十人」的真实上限：在线聚类 12 人需要更多 CPU，但**离线重聚类可以到 16**（`recluster` 是整场跑，几千句 O(n·k·iters) 仍是线性的）。建议：**实时 12 + 离线 16**，并允许用户事后「重新分人」把漏掉的人拆出来（`recluster` 已有这条路径）。

> 诚实边界：**观众端只有一路混音**（README「已知边界」）。十几人**同时**说话仍然不可解，我们做的是「轮流上麦、不同时说话」这个真实场景——这恰好是语音厅的常态。文档里要把这条写清楚，不承诺会议记录级质量。

## 3. 第二层：观点原子（把「场 × 要点」换成「人 × 观点」）

### 3.1 什么是「观点原子」

一条观点（claim）最少包含四个字段：

```json
{
  "claim_id": "clm_...",
  "who": "阿哲",            // persons.person_id，认不出时退回 speaker_label
  "topic": "OPC 政策",       // 复用该场的 AI 主题词表，不新造
  "stance": "我认为明年 OPC 会被平台收紧",   // 一句话主张，<= 40 字
  "evidence": [{"session_id": "...", "t": 1234.5, "quote": "原话..."}],
  "kind": "claim | question | answer | prediction | disagreement"
}
```

和现有「要点（point）」的区别：

| | 现在的 point | 观点原子 |
|---|---|---|
| 归属 | 一场 | 一个人（跨场可合并） |
| 粒度 | 一个话题下的 2~4 句证据 | **一句可独立成立的主张** |
| 生命周期 | 跟场过期 | **跨场累积、可被修改、可被反驳** |
| 用途 | 笔记页展示 | 检索、周报、人物档案、AI 追问 |

### 3.2 怎么产出：复用现有两次调用，不新增调用

关键判断：**观点原子不是新的一次 AI 调用，而是把现有「理解段」的输出换一种落库方式。**

- `analysis._llm_points()`（`app/analysis.py:571`）每次理解段已经让模型读全场的采样句，输出 `points[{title, gist, evidence_ids}]`。**在这里给每个 point 加两个字段：`claim_speaker`（这条主张主要属于谁，spk 表的索引）和 `stance`（一句话主张）。** 输入零增量，输出每条约 +12 token。
- 证据闸门照旧：`evidence_ids` 必须落在给定句子里，`claim_speaker` 必须是该证据里出现过的说话人（否则丢弃该字段，退回「本场」归属）。
- ~~没有模型时走 `_extractive_points()` 兜底~~：2026-11-19 起本地抽取式已从总结链路移除。没有模型就不生成总结，也不会产出观点层；界面明确说明原因，不再用本地拼接稿冒充。

### 3.3 跨场合并：先规则，后模型，最后才是向量

三条路径，按成本从低到高，**默认只跑前两条**：

1. **规则合并（0 token）**：`(person_id, topic)` 相同，且 `stance` 的字符级相似度（去标点后 Jaccard / difflib，`scenes.py` 里已经用了 difflib）>= 0.55 → 视为同一观点的新表述，合并成一条 `claim`，证据追加。**观点变了但话题没变**（相似度 < 0.35）→ 记一条 `claim_revision`（「他上周说 A，这周说 B」），这本身就是很有价值的内容。
2. **模型合并（1 次调用，按需）**：同一 `(person, topic)` 下累积超过 5 条时，让模型判断哪些是重复、哪些是演化。只在「人物档案」页被打开时触发，不在记录结束后自动跑——**避免每场都烧钱**。
3. **向量召回**：P2 再说。理由同 docs/36 §8.2：单机几千到几万条观点，FTS5 + 主题闭集 + 人维度过滤已经够；加 embedding 等于多一条索引链路和一次模型调用，收益要等数据量到 5 万条以上才显现。

### 3.4 新的检索维度：人 + 主题 + 时间

`search_note_units()` 现在只按 text / title 检索。观点层落地后，`qa.retrieve()` 的召回要多两个入口：

- `speaker_person = 'per_xxx' AND topic = 'OPC 政策'` → 「阿哲关于 OPC 说过什么」；
- `topic = 'OPC 政策'` 且按人分组 → 「关于 OPC 有哪几种观点」。

这两个入口**不需要新增 FTS 表**：`claims` 表加 `(person_id, topic)` 索引即可，`note_units` 继续做全文兜底。

### 3.5 笔记页要跟着改：从「要点列表」到「观点地图」

这是「看不下去」最直接的解药。圆桌形态的笔记页顶部应该是一张**观点地图**，而不是五条要点：

```
本场 14 人上麦 · 主持：老王 · 3 个主题

▌OPC 政策        ┌ 阿哲：明年会被收紧（三处论证）  🔗 3 场
                  ├ 小鹿：我不同意，真正的变量是备案  🔗 2 场  ⚡与阿哲冲突
                  └ 大周：补充了一个案例              🔗 1 场

▌选品逻辑        ┌ Mia：...

▌还没答案的问题  · 平台抽成到底按什么口径算？（本场 3 人提到，无人回答）
```

每条观点点开 → 原话 + 时间码 + 回放；点人名 → 人物档案（§4）。**一张图回答「这场谁说了什么、分歧在哪」，比十条要点有用得多。**

### 3.6 不要做的事

- **不要**让模型在观点层做「谁对谁错」的判断。我们只记「谁主张什么、谁不同意」，对错留给用户（这是 docs/30 证据门原则的延续）。
- **不要**把观点原子做成新的用户可见概念。界面上仍然是「观点」，不出现 `claim`、`stance`、`person_id` 这些词。
- **不要**在记录进行中就抽观点。观点需要全场上下文；实时阶段只做「近聊话题」（`livebrief.topics()` 已有），不抢它的活。

## 4. 第三层：像管家一样的 AI（追问、记忆、主动）

### 4.1 现状：问笔记是「一次性问答」，不是「对话」

`app/qa.py` 的 `ask()` 每次是一个独立问题 + 24 小时缓存，没有多轮上下文、没有「基于上一个问题接着问」、不会主动提醒。它更像「搜索框加强版」，不是你要的 ChatGPT 式体验。

### 4.2 三步走，不要一步到位

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **A. 追问** | 问答结果下面给 2~3 个「基于这条答案的追问」；追问带上一轮答案作为上下文（只带答案摘要 + 引用 id，不带全文） | 成本最低（一次问答多 ~200 token），体验差距最大（从「搜一下」变成「聊下去」） |
| **B. 记忆** | 每个人物一页「他讲过什么」：按主题分组的观点、出现场次、观点变化时间线；每次新场结束自动更新（规则合并，0 token） | 「AI 学习、持续进化」的**可感知**形态。用户看到的不该是「模型变聪明了」，而是「阿哲这页多了一条」 |
| **C. 主动** | 记录中/记录后，当新观点与历史观点冲突、或同一个问题第 3 次出现没人回答时，给一条不打断的提示 | 这是「管家感」的来源。但必须克制：每场最多 1 条，且必须能一键关（沿用 `notify` 的偏好体系） |

### 4.3 追问怎么设计（A 步细节）

现有 `qa.answer()` 返回 `{answer, citations}`。追问建议的生成有两种做法：

- **规则拼接（默认，0 token）**：从 citations 的 `kind` 和人物/主题派生。「这条是阿哲说的 → 他在别的场怎么说过？」「这条是预测 → 后来验证了吗？」「这条有 3 个人不同意 → 另外两个怎么说？」。`notes.suggest_questions()` 已有这套模式的雏形。
- **模型生成（可选）**：在回答的同一次调用里多返回一个 `followups: [str]`，成本约 +30 token。建议**先做规则版**，因为追问的价值在于「指向下一步动作」，不在于措辞漂亮。

多轮上下文：新增 `qa_threads` 概念（可以是 `qa_answers` 加一个 `thread_id` + `parent_id`），追问时把上一轮 answer 摘要（<= 200 字）+ 引用 id 一起送模型。**不要**把整个对话历史塞进去——本地单机，预算敏感。

### 4.4 「人物档案」从「出没记录」变成「观点档案」

`app/web/people.html` 现在的详情页是「哪场出现、几句、置信度」——这是**声纹调试页**，不是人物页。改法：

```
阿哲                                    跨 7 场 · 累计 4 小时 12 分 · 主讲 5 次 / 主持 2 次
────────────────────────────────────────────────────
他的主张（按主题）
  OPC 政策    明年会被收紧 · 首次 10-12 · 最新 11-16 · 3 场
               └ 11-16 改了说法：「不是收紧，是备案门槛抬高」  [听原话]
  选品逻辑    ...
他常被问到的问题（3 个，其中 1 个至今没答）
他和其他人的分歧（2 处，均在小鹿）
────────────────────────────────────────────────────
最近出没：11-16《…》 00:12:30 起
```

数据来源：`persons` + `claims` + `person_appearances()`，全部本地，全部可点回原话。**这一页就是「AI 学习、持续进化」的用户可见形态**——比任何「模型已升级」的提示都有说服力。

### 4.5 主动提醒的边界（C 步）

只做三种，且都要能被设置页关掉：

1. **观点反转**：「阿哲这场说的和 11-02 那场相反，要回看对比吗？」
2. **老问题有新答案**：「『平台抽成怎么算』上次没人答，这场大周答了。」
3. **高频主讲出现**：「小鹿上麦了，她在你这儿有 6 条观点。」

**不做**：情绪化提醒、催更式提醒、任何需要联网核实的「外部事实核查」。

## 5. 你提的「AI 学习 / 进化」到底该怎么落

这是最容易变成空话的一条，所以说清楚它**不做什么**：

- **不是**微调模型。本地单机、用户量小、数据量小，微调不划算也不可能在用户机器上跑。
- **不是**给模型加「长期记忆」的新架构。我们已经有 SQLite，**记忆就是库里的表**。
- **是**三件具体的事：
  1. **结构化**：观点原子（§3）让「学到的东西」有形状；
  2. **累积**：跨场合并让「同一件事」只有一条记录，并且带时间线；
  3. **可用**：检索按「人 × 主题」召回，追问带上一轮上下文，人物页能一眼看到变化。

「进化」在用户侧的表现应该是：**同一场直播，你听得越多，问你问题的成本越低**——第一次你得翻逐字稿，第十次你只问一句「上次那个谁怎么说的」。这就是管家感，不需要模型真的「学会」什么。

## 6. 对 G1 / G2 的完整改写（可以直接替换 docs/38 的两节）

### 6.1 G1' 「本场观点卡」：让上麦的人替你转发

**形态**：一场圆桌结束，生成 3 张竖版卡，每张 =「**一个人名 + 一句他的观点 + 一句原话 + 本场信息**」，落款「本场 14 人上麦 · 某某语音厅 · 由 LiveNotes 记录」。观点提出者可以认领并转发到自己的群/朋友圈；扫码打开的是**这一条观点的只读页**（不是整场笔记），页尾是「记录你自己的上麦」。

**为什么比原方案对**：

| | 原 G1（主播返场卡） | G1'（观点卡） |
|---|---|---|
| 传播者 | 主持人（话最少的人） | 观点提出者本人（最有动机的人） |
| 传播动机 | 「替工具宣传」 | 「**我讲的话被认真记下来了**」 |
| 内容单元 | 一场的高光 | **一个人的观点**（可跨场累积，越用越厚） |
| 对主持人 | 唯一主角 | 仍有价值：他转发的是「我主持的场」，而且卡上会写主持人 |

**落点**：`app/web/js/sharecard.js` 加第 4 套模板（观点卡）；数据来自 §3 的 `claims`；只读页复用 `docs/37` 的公网只读页方案。工作量 3–4 人日（不含公网地基）。

**风险**：未经授权传播他人观点——默认只显示昵称 + 文字，不显示头像、不提供原声下载，认领后才展示更多，提供下架通道（沿用原 G1 的口径）。

### 6.2 G2' 「语音厅内容助手」：三个工具换掉两个

| 工具 | 输入 | 输出 | 为什么只有我们能做 |
|---|---|---|---|
| 回放/录音转文字（保留） | ≤15 分钟音频 | 带时间码的样例笔记 | 保留原方案，作为流量入口 |
| **多人圆桌摘要（替换「开播提醒」）** | 一段 ≥3 人的录音 | 「有几个人、每个人说了什么观点、分歧在哪」 | 大厂的转写不区分「观点归属」；**这是我们刚做出来的能力** |
| **上麦者名片（替换「话术提取」）** | 一个人名（在用户自己的库里） | 他讲过的观点摘要页 | 只有「持续记录同一个厅」的用户才有这份数据——**天然的产品黏性** |

**为什么换**：「开播提醒」是纯工具，谁都能做，而且需要公网常驻服务（成本高、compliance 重）；「话术提取」是电商直播专用，语音厅里没意义。换掉的两个都更好做、更有辨识度、并且**都是内部能力的切片**，不是新造轮子。

## 7. 和现有路线的关系：不推翻 P2，但要把顺序换掉

docs/38 的 P2 路线是「先收钱地基，再增长」。本文的结论是：**在「场 = 主播 + 嘉宾」这个模型修正之前，增长和变现都在给一个错的产品做放大器。**

| docs/38 阶段 | 本文的建议 |
|---|---|
| P2.0 收钱地基（许可/授权/支付/公网） | **保留，但降为并行**。它不依赖产品模型，可以先做 |
| P2.1 首购与传播（G1 返场卡） | **换成 G1' 观点卡**，并且依赖 §2/§3 |
| P2.2 服务化（工具矩阵 / 模板市场） | **G2 换成 G2'**；模板市场**不做**，只留 4 套官方导出预设（圆桌纪要 / 问答清单 / 上麦者名片 / 复盘交付包）——形态判定已自动选模板，UGC 提示词会破坏证据门。详见 [docs/38 §3 E1'](38-p2-growth-and-monetization-options.md) |
| P2.3 高客单（竞品监测 / 白标） | 不变，但**竞品监测在语音厅场景的买家变了**：不是品牌投流团队，而是**语音厅运营方 / MCN 的直播内容团队**（他们要的是「这个厅每天讲了什么、谁讲得好」） |

**新增优先级（本文建议）**：

```
P2.0' 产品模型修正（§2 场次形态与角色 + §3 观点原子）   ← 最高（已落地）
P2.1' 人物档案 + 观点地图（§4.4 + §3.5）                ← 让修正可见（已落地）
P2.2' 追问 + 主动提醒（§4.2 A/C）                        ← 管家感（已落地）
P2.3  收钱地基 + G1' 观点卡 / G2' 内容助手               ← 原 P2.0/P2.1
P2.4  E1' 官方导出预设 + G3' 渠道代理                    ← 见 docs/38 §3 / §1
```

理由：**产品模型错了，收钱地基做得再好也只是把错的东西卖出去。**

## 8. 排期与验收（按 1 人熟手估）

| 阶段 | 内容 | 人日 | 硬验收 |
|---|---|---|---|
| **S1** | 场次形态判定（0 token）+ 角色三种 + 说话人上限 12/16 + 溢出可见 | 6–8 | 20 场真实录音里，形态判定人工抽检 ≥ 85% 正确；超出上限的场次能看到「N 段被合并」 |
| **S2** | 观点原子：理解段加 `claim_speaker`/`stance`、`claims` 表、跨场规则合并（无模型时明确不生成，不做抽取兜底） | 10–14 | 一场 12 人圆桌，观点归属正确率 ≥ 80%（人工抽检 30 条）；同一 `(人, 主题)` 跨场能合并成 1 条并保留时间线 |
| **S3** | 笔记页观点地图 + 人物档案改版 + 检索加「人 × 主题」维度 | 8–10 | 笔记页首屏能回答「这场有几种观点、谁和谁冲突」；人物页能答「他讲过什么」且每条可点回原话 |
| **S4** | 追问（规则版）+ 主动提醒三种 + 设置开关 | 6–8 | 追问点击率 ≥ 25%；主动提醒每场 ≤ 1 条且可关 |
| **S5** | G1' 观点卡 + G2' 两个工具（依赖公网地基） | 10–14 | 观点卡扫码率 / 安装转化 ≥ 3%；工具页 UV → 下载 ≥ 3% |
| **合计** | | **40–54 人日** | |

**砍单顺序**：S5 → S4 的主动提醒 → S3 的人物档案改版（先只做观点地图）→ S2 的模型合并（只留规则合并）。**不能砍**：S1、S2 的观点原子与归属、S3 的观点地图。

**最小可验证切片（约 8 人日）**：只做 S1 的形态判定 + S2 的观点归属字段（不做 `claims` 表，先存在 `summaries.payload_json` 里）+ 笔记页把要点按「人」分组显示。用来验证「按人组织是否真的让笔记可读」这个核心假设——**这是整份方案里唯一需要先验证的假设**，其余都是工程实现。

## 9. 风险与边界

| 风险 | 对策 |
|---|---|
| **十几人同时说话不可解**（只有一路混音） | 明确定位为「轮流上麦」场景；重叠段维持现有「标记 + 不转写」；文档和界面都要写「同时说话的部分记不下来」 |
| 观点归属错误（模型把 A 的观点归给 B） | 归属必须能在证据里找到该说话人（证据闸门）；人工可一键改归属，改过的不会被重算覆盖（沿用 `edited_at` 的哲学） |
| 说话人上限提到 16 后实时聚类变慢 | 实时仍 12，16 只在离线重聚类用；低配模式下回到 8 并在界面说明 |
| 观点合并过度（把两个不同观点合成一条） | 阈值保守（0.55 起步），合并后保留所有原始证据；允许「拆分」操作 |
| 主动提醒变成骚扰 | 每场 ≤ 1 条、默认关、可分类开关（沿用 `notify` 的偏好体系） |
| 「AI 管家」承诺过高 | 界面文案不出现「AI 管家 / 大脑 / 学习」这类词；只出现「观点」「他的主张」「和上次不同」 |
| 传播他人观点涉版权/人格权 | 沿用 docs/38 §8：只做公开直播、默认文字 + 昵称、认领 + 下架通道、不提供原声批量导出 |

## 11. 一句话总结

**你不需要「再让 AI 总结一遍」，你需要让 AI 换个方式记：不是「一场直播的五个要点」，而是「十四个人轮流上麦，阿哲主张 X、小鹿反对、大周补了个案例，关于 Y 至今没人回答」。** 这套模型的原子是「人 × 观点」，不是「场 × 要点」；它一旦落地，笔记会自己变得可读，人物档案会自己变厚，追问会自己变准，而你要的「AI 管家」就只是这套结构的一个界面——**顺序不能反：先有结构，再有对话；先能回答「谁说过什么」，再谈「像 ChatGPT 一样」。**
