# 47 · 飞书原生阅读面：不建公网网页，把「读、找、转」放回飞书

> 面向：产品 / 架构决策
> 结论时间：2026-11-25
> 关联：[docs/16](16-recording-sharing-options.md)、[docs/37](37-cloud-storage-and-feishu-share.md)、[docs/41](41-voice-room-knowledge-product-iteration.md)、[docs/46](46-three-surfaces-governance-review.md)
> 一句话：公网网页解决的是「飞书外的人也能看」；如果读者就在飞书里，云文档 + 多维表格 + 卡片已经够用，而且更顺手。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 还要不要做 Cloudflare 公网网页？ | **不作为默认方案。** 它把「阅读」误当成「再做一个桌面端网页」；如果读者在飞书里，云文档、多维表格、卡片已经覆盖阅读、查找、转发、评论、权限。只有「非飞书外部客户」才需要单独立项。 |
| 飞书端到底是什么？ | **阅读面 + 检索面 + 转发面**，不是桌面端的缩小版。桌面负责整理和校对，飞书负责「我在外面看一眼、找一句话、转给一个人」。 |
| 最小闭环是什么？ | **一场 = 一篇云文档 + 一行多维表格；一人 = 一篇档案 + 一行人物；一周 = 一篇周报；一个动作 = 一条任务。** |
| 最大的前提是什么？ | 云端场次必须先有转写和总结。`capture_only` 不产生总结，离线补转写也不触发 finalize（[docs/46](46-three-surfaces-governance-review.md) P1）；**不接通这条链，文档就是空壳。**（2026-11-26 已接通） |
| 先做什么？ | 先修 `offline_asr → finalize`，再做发布器（场次文档 + 场次表 + 收尾卡）。不要先做搜索页、问答页、公网网页。（P0 已落地，见 §7） |

## 1. 先回答「为什么没必要」

### 1.1 公网网页真正解决的是什么

| 需求 | 公网网页 | 飞书原生 | 建议 |
|---|---|---|---|
| 自己在外面用手机看 | 完整页面，但要域名、证书、登录 | 文档/表格原生阅读，消息推送 | **飞书够** |
| 同事在飞书内看 | 要再发链接，权限另做一套 | 飞书权限、评论、@、搜索现成 | **飞书更好** |
| 外部客户/非飞书用户看 | 唯一顺路径 | 受租户外部分享策略限制 | 只有这类才考虑公网 |
| 精确回听 + 逐字稿联动 | 现有 reader 直接搬 | 文档不能跳音频秒；妙记可但二次转写 | 桌面 / 妙记 |
| 完整桌面 UI、设置、校对 | 可以 | 不适合 | 桌面 |

结论：如果 80% 的阅读发生在飞书内，公网网页是为 20% 的场景造 100% 的系统。**先把飞书内做顺，外部交付再单独立项。**

### 1.2 飞书端的独特优势

- **内容长在协作流里**：一条消息、一篇文档、一张表、一个任务，都能被转发、评论、@、搜索、提醒。公网网页做不到这些，除非再造一套协作系统。
- **身份和权限现成**：组织架构、群、外部联系人、离职回收，都是飞书已经处理好的。
- **手机原生**：推送、离线阅读、搜一搜、收藏、稍后读，不需要我们做 App。
- **零新增基础设施**：不需要域名、备案、证书、登录、分享审计。云文档和多维表格由飞书托管，**我们不需要为阅读面备案**；数据仍在飞书租户内，受租户策略约束。
- **代价**：不能自定义播放器和布局；文档 API 有块级上限；妙记不能程序化创建；卡片表单依赖客户端版本。这些代价决定了「哪些不搬」。

### 1.3 所以飞书端不抄桌面端

| 维度 | 桌面端 | 飞书端 |
|---|---|---|
| 场景 | 坐下整理、校对、采集控制 | 在外面读、找、转 |
| 内容 | 逐字稿、时间轴、全员命名 | 结论、观点、原话、人物 |
| 交互 | 播放器、拖拽、批量改名 | 文档、表格、卡片、搜索 |
| 不做什么 | — | 逐字稿校对、重聚类、术语表编辑、设置、采集方式切换 |

**一句话：桌面端是「编辑室」，飞书端是「刊物 + 索引 + 剪报」。**

## 3. 产品形态：四个「一」

### 3.1 一场 = 一篇场次文档

**为什么不是逐字稿**：手机上看不完，也没必要。文档只放「结论 + 观点 + 原话 + 人物」，逐字稿留在桌面端/导出文件/附件。目标篇幅 **1500~2500 字**，5 分钟读完。

模板（以语音厅圆桌为例）：

```markdown
# 2026-11-25 22:30 ·「今晚聊 AI 出海」· 圆桌

> 房间：XXX ｜ 时长：1 小时 42 分 ｜ 上麦：8 人 ｜ 主持：阿岚
> 采集：云端节点 ｜ 状态：已总结 ｜ 观点 6 条 ｜ 高光 3 条

## 一句话
这场真正吵起来的是「先做东南亚还是先做中东」，不是标题里的「AI 出海」。

## 观点地图
### 阿哲 · 3 条
- **先做东南亚**：支付和内容生态更成熟，冷启动快。（22:14）
  > 原话：「你在中东买量，先亏三个月，还不一定回本。」
- **改口**：上周说「中东客单价高值得试」，这场说「先东南亚」。（22:41）

### 小北 · 2 条
- **先做中东**：客单价高，愿意为工具付费。（23:02）
  > 原话：「东南亚付费率摆在那儿，你补贴到什么时候？」

### 没人回答的问题
- 小北问「中东的本地化客服谁来做」，到结束没人接。

## 值得回听
| 时间 | 谁 | 为什么值得听 | 原话 |
|---|---|---|---|
| 22:14 | 阿哲 | 这场分歧的起点 | 「你在中东买量……」 |
| 23:02 | 小北 | 反方最完整的一段 | 「东南亚付费率……」 |
| 23:41 | 阿岚 | 主持收束，给了判断标准 | 「那就看谁先跑通复购。」 |

## 人物
| 上麦者 | 发言 | 时长 | 档案 |
|---|---|---|---|
| 阿哲 | 18 条 | 26 分 | 阿哲 · 观点档案 |
| 小北 | 14 条 | 21 分 | 小北 · 观点档案 |

## 相关场次
- 11-18 ·「中东工具市场」· 阿哲也提过客单价
- 11-11 ·「东南亚支付」· 小北当时在场

---
由 LiveNotes 生成。逐字稿与完整时间轴在桌面端；本页只保留结论与可引用的原话。
```

**写作纪律**：

- 原话每条 ≤ 80 字，只留能独立成立的句子；口头禅清掉，但不改意思。
- 时间码是纯文本，**不假装能点**；能点的只有：妙记链接（人工回填）、云盘录音、机器人发的片段。
- 没有总结就明确写「待补转写 / 总结失败」，**不生成规则版兜底稿**（与「不做本地抽取兜底」一致）。
- 人名没补全时，用「一位上麦者」而不是猜一个名字；文末放补名入口。
- 有明确行动项时，加一段 `## 待办`（谁 / 做什么 / 何时前）；P2 再同步成飞书任务，不要在 P0 就做任务系统。

### 3.2 一行 = 场次索引（多维表格）

**为什么用 Base 而不是文档里的列表**：手机上要按房间、日期、状态筛选，要按观点数排序，要一眼看到「哪场还没转写」；这些是表格的原生能力，文档列表做不到。

P0 只建 **场次表**：

| 字段 | 类型 | 说明 |
|---|---|---|
| 标题 | 文本（主字段） | `11-25 22:30 · 房间 · 圆桌` |
| 日期 | 日期 | 用于排序/本周视图 |
| 房间 | 文本 | 语音厅名称 |
| 形态 | 单选 | 单人 / 圆桌 / 问答 |
| 主持 | 文本 | 没有就空着 |
| 上麦人数 | 数字 | 来自 `shape.speaker_count` |
| 时长分钟 | 数字 | 来自 `session.duration_s` |
| 一句话 | 文本 | 来自 `summary.overview` |
| 观点数 | 数字 | 来自 `counts.points` |
| 高光数 | 数字 | 来自 `counts.highlights` |
| 状态 | 单选 | 待转写 / 待总结 / 已发布 / 发布失败 |
| 文档链接 | URL | 场次文档 |
| 录音链接 | URL | 云盘 m4a，可空 |
| session_id | 文本（隐藏） | 幂等键，不给人看 |
| 标签 | 文本（顿号分隔） | 主题词，来自 `summary.topics`；P0 先不用多选，避免选项不存在导致写不进去 |
| 逐字稿附件 | 附件 | 可选；不放正文 |

视图：

- **最近场次**：日期倒序，手机默认打开这个。
- **本周**：日期在最近 7 天。
- **按房间分组**：看哪个厅产出多。
- **待补转写**：状态 = 待转写，运营每天清一次。
- **观点最多**：观点数倒序，找值得回看的场。

P1 再加 **人物表** 和 **观点表**：

| 表 | 关键字段 |
|---|---|
| 人物 | 昵称、首次出现、最近出现、场次、上麦时长、观点数、主要主题、档案链接、person_id |
| 观点 | 观点、谁、主题、场次、时间码、原话、状态（新提出/重申/修正/被反驳）、首次、最近、claim_id、场次文档链接 |

**MVP 纪律**：不用「关联」字段，用文本 `session_id` / `person_id` + URL 字段。关联字段要跨表 token、record_id，upsert 复杂，第一版不值得。

### 3.3 一人 = 一篇人物档案

人物档案回答的是「他讲过什么」，不是「他在哪几场出现过」。模板：

```markdown
# 阿哲 · 观点档案

> 首次：2026-10-14 ｜ 最近：2026-11-25 ｜ 场次：7 ｜ 上麦：3 小时 12 分 ｜ 观点：19 条

## 最近在讲什么
### AI 出海
- **先做东南亚**（11-25）：支付和内容生态更成熟。
  > 「你在中东买量，先亏三个月……」
- **改口**：11-18 说「中东客单价高值得试」→ 11-25 说「先东南亚」。
- 更早：10-28「先做工具，不做内容」；11-04「内容才是壁垒」。

### 工具选型
- ……

## 出现场次
| 日期 | 场次 | 时长 | 文档 |
|---|---|---|---|
| 11-25 | 今晚聊 AI 出海 | 26 分 | 打开 |
| 11-18 | 中东工具市场 | 31 分 | 打开 |

---
身份来自声纹聚类与人工补名，可能认错；以本人/主持确认为准。
```

**必须写的免责声明**：声纹是概率匹配，不是身份证。错认一个人，比不认更伤信任。

### 3.4 一周 = 一篇周报

周报是手机端的「首页」，不是场次文档的堆叠。现有 `report.build()` 已经能生成（[app/report.py:963](../app/report.py)），只需要：

- 每场后面加「场次文档」链接；
- 加一段「下周可追的问题」（从 `opinion_map` 的未回答问题里取）；
- 加「本周人物」（观点数/改口最多的 3 个人，链到人物档案）；
- 末尾加「全部场次」Base 视图链接。

周报已经在机器人 `/周报` 里建 docx（[tools/feishu_bot.py:996](../tools/feishu_bot.py)），P0 只需补链接，不重写生成逻辑。

### 3.5 一个动作 = 一条任务（P2）

只把**明确说出来的行动项**建成飞书任务：谁、做什么、什么时候前。任务来源必须是总结里的显式条目，不做「猜测式行动项」。任务带 `origin.href` 指回场次文档（Task API 的 `origin` 支持 URL + 标题），用户在任务中心点开就能回到原话。

语音厅的行动项通常不多；这条是锦上添花，不进 P0。

| 逐字稿校对 | 有 | **不做** | 桌面 | 不搬 |
| 重聚类/术语表 | 有 | **不做** | 桌面 | 不搬 |
| 设置/采集方式 | 有 | **不做** | 桌面 | 不搬 |

**两个特别说明**：

1. **分享卡不要照搬**。桌面分享卡的二维码指向「公网只读页」；不做公网页，二维码就是死链。飞书端的等价物是**可转发的消息卡片**（一个人 + 一句观点 + 一句原话 + 场次文档链接），不是 PNG。
2. **回听不要假装能跳秒**。云文档里的时间码是文本；要听就发 30~90 秒片段（机器人已有 `send_audio`，见 [app/feishu.py](../app/feishu.py)），或者人工上传妙记后回填链接。妙记是「整场兜底」，不是主入口。

## 5. 三个关键流程

### 5.1 收尾发布：finalize → 文档 + 表 + 卡片

```
captured ──→ transcribed ──→ summarized ──→ published
   │              │                │
   └─ 待补转写 ───┴─ 待总结 ───────┴─ 发布失败（可重试）
```

**状态规则**：

| 状态 | 什么时候 | 文档里写什么 |
|---|---|---|
| 待补转写 | 仅采集，或离线 ASR 未完成 | 标题、时间、时长、房间、录音链接、「转写完成后自动更新」；**不写摘要** |
| 待总结 | 有逐字稿，总结未完成/失败 | 逐字稿统计、上麦者列表、「总结失败，原因……」；**不写规则兜底稿** |
| 已发布 | 总结成功 | 完整模板 |
| 发布失败 | 文档/表格接口失败 | 库里有内容，卡片/命令可重试；不阻塞采集 |

**流程**：

1. `tasks._run_summary` 成功 → `notes.index_session`（[app/tasks.py:92](../app/tasks.py)）→ 触发 `feishu_publish.publish(sid)`。
2. 发布器读取 `notes.build_note()` + `claims.profile()` + `person_appearances()`，生成发布用 Markdown（新增 `export.to_publish_md()`，不要直接复用 `to_note_md`，后者缺时间码、观点地图、人物链接）。
3. `ensure_doc(sid)`：查 `feishu_publish`，有 `document_id` 就复用；没有就 `create_docx`。
4. 覆盖正文：列出根块 → `batch_delete` 清空 → `block_descendant.create` 写入新块。
5. `permission_member` 授权给 owner（群场景授权给群，member_type 用 `openchat`，需验证）。
6. upsert 场次表：按 `session_id` 找 `record_id`，有就 update，没有就 create。
7. 发收尾卡片：`看文档` / `补名` / `听 3 段` / `问这场`。
8. 写 `feishu_publish`：`state=ok`、`version=hash`、`doc_token`、`record_id`、`latency_ms`。

**实现落点（2026-11-26）**：

- `tasks._run_summary` 只在「整场口径」的总结后自动发布；带筛选条件的总结不发布，避免筛选稿冒充整场文档。
- 仅采集下播由 `live._auto_finalize` 先发「待补转写」骨架；离线补完字后调 `POST /api/sessions/finalize`（`recluster=False`，重聚类已由补转写做过），走同一套收尾和发布。
- 正文更新是「列根块 → `batch_delete` → 从 0 写回」。这会丢评论锚点，所以只有版本变化、补名或显式 `/发布` 才重写；普通重试版本没变就跳过。

**幂等**：

- `feishu_publish` 唯一键 `(session_id, kind)`；`version` 是 Markdown + 标题 + 人名的 hash。版本没变，重试直接跳过。
- 文档建成功但正文失败：保留 `document_id` 和 `url`，下次只补正文，不新建第二篇。
- 表格写成功但文档失败：表格行标 `发布失败`，文档重试成功后改回 `已发布`。

**重发布**：

- 只在「补名后」「用户显式 `/发布`」时重发布；不要每次重试都重写，避免评论锚点丢失。
- 清空根块会丢评论锚点；文档里加一句「重新发布后旧评论可能失效」，或在重发布前把评论数记进日志。

**失败降级**：

- 文档失败 → 发 `.md` 文件 + 表格行仍然可查；不阻塞总结/采集。
- 表格失败 → 文档仍然可读；表格行下次重试补。
- 飞书未配置 → 整个发布器静默跳过（日志 `feishu.publish_skipped`），不影响本地。

### 5.2 补名：飞书端唯一反向写回

**为什么重要**：语音厅 10 个人轮流上麦，没有名字，观点地图就是「一位上麦者 A/B/C」。补名是「知识产品是否成立」的分水岭（[docs/46](46-three-surfaces-governance-review.md) R6）。

**流程**：

1. 收尾卡检测 `top3.named < slots`（`/api/sessions/top_speakers` 已经返回 `preview` 3 秒窗口和声纹建议，见 [app/naming.py:92](../app/naming.py)）。
2. 机器人依次发 3 条音频消息：A/B/C，每条 3 秒，来自 `preview.t_start/t_end`（`/api/audio?session_id=&t_start=&t_end=`）。
3. 发一张卡片 2.0 表单：3 个输入框，标签 A/B/C；有可信建议时预填「像阿哲」，用户可改。
4. 用户提交 → 卡片回调带 `form_value` → 校验操作者（owner 或发起人）→ 调 `/api/speakers/name`（[app/server.py:2937](../app/server.py)）→ 声纹注册、观点归属重建。
5. 成功后重发布场次文档（人名变了），更新人物表/观点表。
6. 兜底：用户直接回「1 阿哲 2 小北」，机器人解析；卡片回调不可用时也能用。

**隐私**：

- 声纹只留本地，**不进飞书、不进 Base**。
- 3 秒音频只在用户点「补名」后发，且只发私聊/授权群；不自动发群。
- 人名是个人信息；文档权限默认只给 owner/房间群，不做公开链接。

### 5.3 读、搜、问

| 入口 | 用户动作 | 后端 | 返回 |
|---|---|---|---|
| 机器人菜单 | 点「今日」 | 最近 24h 场次 + 周报 | 卡片：场次标题 + 一句话 + 文档链接 |
| `/文档 CH01` | 看某场 | `feishu_publish` 查 doc_url | 文档链接 + 一句话 |
| `/找人 阿哲` | 看某人 | `persons` + `claims.profile` | 人物档案链接 + 最近 3 条观点 |
| `/搜 关键词` | 找原话 | `/api/search`（FTS + 术语扩展） | Top 5：场次 + 时间码 + 原话 + 文档链接 |
| `/问 问题` | 问笔记 | `/api/qa/answer` | 答案 + 引用 + 文档链接 |
| 飞书搜索 | 搜标题/文档 | 飞书原生索引 | 文档/表格；**不搜逐字稿** |

**分工**：飞书搜索负责「找文档」，机器人 `/搜` `/问` 负责「找原话、问结论」。不要做第三个搜索页。

## 6. 架构：单向发布，不做双向同步

```
SQLite（唯一真相源）
  │
  ├─ finalize / offline_asr ──→ publish_jobs ──→ app/feishu_publish.py
  │                                                   │
  │                                                   ├─→ docx（场次/人物/周报）
  │                                                   ├─→ Base（场次/人物/观点）
  │                                                   └─→ Drive（整场音频，可选）
  │
  └─ 补名卡片 ──→ bot callback ──→ /api/speakers/name ──→ SQLite ──→ 重发布
```

**原则**：

1. **引擎是真相源**；飞书是「发布产物」。文档里的人工编辑不回流，评论只当反馈，不当数据。
2. **唯一反向通道是补名**：因为它要写声纹和观点归属，必须回到引擎。
3. **发布器不加载模型**：只做 Markdown 组装 + HTTP，不增加云端节点内存；发布失败不影响采集/转写/总结。
4. **不双向同步**：双向同步要处理冲突、删除、权限、块级 diff，成本远高于收益；第一版坚决不做。
5. **不自动建群**：把机器人拉进用户已有的房间群即可；自动建群是打扰。
6. **应用建的 Base 也要授权**：和文档一样，应用创建的 Base 默认只有应用能看；用 `permission_member`、`type=bitable` 授权给 owner/群，否则用户点开就是无权限。

**配置新增**（已实现；环境变量优先，其次 `data/feishu.json` 同名键）：

| 配置 | 用途 |
|---|---|
| `FEISHU_PUBLISH_ENABLED=1` | 总开关；默认关，桌面用户可不开 |
| `FEISHU_PUBLISH_FOLDER_TOKEN` | 场次/人物文档的云空间文件夹；不填复用 `doc_folder_token` |
| `FEISHU_PUBLISH_OWNER` | 默认授权给 owner；不填用机器人配置里的 `owner_open_id` |
| `FEISHU_BASE_FOLDER_TOKEN` | 多维表格存放文件夹；不填复用文档文件夹 |
| `FEISHU_BASE_APP_TOKEN` | 可选：预建 Base，避免每次新建 |
| `FEISHU_BASE_TABLE_ID` | 可选：预建数据表；不填自动建 |
| `FEISHU_PUBLISH_BASE=0` | 只发文档、不写场次表 |
| `FEISHU_BASE_URL_BASE` | 可选：Base 链接前缀；不填用飞书返回的 `app.url` |

授权对象优先用 `FEISHU_PUBLISH_OWNER`，没配就沿用现有 `open_id` /
`owner_open_id`：建文档/建 Base 后都用 `permission_member` 授权给这位用户
（Base 用 `type=bitable`）。Base token 首次建好后写进 `index_meta`，进程
重启不会重建。

**可观测**：

- `feishu.publish_ok` / `feishu.publish_failed`：session_id、kind、latency_ms、error。
- `feishu.base_upsert`：table、record_id、created/updated。
- `feishu.publish_skipped`：未配置/版本未变。
- `/状态` 卡片增加一行「发布：最近成功时间 / 待重试数」。

- 场次表先只建一个默认视图「最近场次」；文档里的 5 个筛选视图没做——

2. 表格失败 → `state=partial`，文档已可读；下次发布/重试只补表格，不重写正文。
3. 版本未变且上次成功 → 直接跳过，不产生第二条记录、不重写正文（避免丢评论锚点）；

4. 飞书没配置/开关关着 → `publish_skipped`，不写 `feishu_publish` 行，采集/总结不受影响。
5. 没有总结 → 文章只写状态和已有事实，不生成规则版兜底稿。

## 12. P1 读侧实施记录（2026-11-26）

**范围**：这一片只做「读」，不碰发布器的场次文档和场次表。落地：

| 项 | 落地 |
|---|---|
| 人物档案 Markdown | `app/reading.py::person_markdown()`：按主题列最新主张、原话、改口、更早说法与出现场次；头部给首次/最近/场次/上麦/观点数；文末固定免责声明 |
| 人物档案文档 | `app/reading.py::publish_person_doc()`：按需建 docx；`person_docs` 表做版本缓存，版本没变复用、变了原地重写；重写失败保留旧链接 |
| 场次文档链接 | `app/reading.py::session_doc_url()`：只读 `feishu_publish` 台账；没有行就写「未发布」，不伪造链接 |
| `/找人 阿哲` | 解析底库或观点昵称 → 生成/复用档案 → 回「最近 3 条观点 + 文档链接」；没有观点的人不生成空档案 |
| `/搜 关键词` | 先调 `/api/search`（术语扩展），服务没起来回退本地 `note_units` + 逐字稿；Top 5 带时间码、原话、文档链接或「未发布」 |
| `/问 问题` | 调 `/api/qa/ask` 并在后台轮询 `/api/qa/answer`；答案带引用、场次文档链接与追问建议 |
| 补名卡 | `/补名 [CH]` 发 3 段 3 秒试听 + 表单卡（A/B/C，可信声纹建议预填）；卡片回调走 `/api/speakers/name`；文字兜底「1 阿哲 2 小北」/「A 阿哲」 |
| 卡片回调 | `app/feishu.py::card_event_value()` 把 `action.form_value` 合并进 `value["_form"]`，否则表单提交永远是空动作 |

**与方案的差异（有意）**：

- **人物档案按需生成，不在每场 finalize 后自动跑**：一晚 8 个人就是 8 篇文档，
  且多数人当次不会被点开。用户 `/找人` 时才生成/刷新，版本没变不重写。
- **这一片没有做人物表/观点表 Base**：Base 的建表、字段和 upsert 属于发布器
  P0 的表格能力；这一片先把 Markdown 与命令跑通，表格等发布器合并后再接。
- **`/搜` 的文档链接只读台账**：场次没发布时明确写「未发布」，不拿本地
  reader 链接冒充手机能打开的文档；发布器合并后同一套台账直接带出文档链接。
- **补名卡不自动发群**：只在用户显式 `/补名` 或收尾卡入口发；3 秒音频也只
  发到当前会话，不广播。

**失败语义**：

1. 档案文档建失败 → `/找人` 仍然回最新 3 条观点 + 失败原因；不会因为飞书
   不可用让人物档案整个不可读。
2. 档案版本变了但重写失败 → 保留旧文档链接并标注「这次没刷新」，不新建第二篇。
3. 没有观点 / 只有出没记录 → 不生成空档案，明确说「还没有观点记录」。
4. `/问` 没配置模型、超预算、证据不足 → 原样报错，不退回本地摘录。
5. 补名某个名字失败 → 其它名字照常写入；全失败保留卡片，允许再试。

**测试**：`tests/test_reading.py` 32 例（人物 Markdown/改口/空档案、文档幂等
创建与重写、旧链接保留、场次文档链接、`/找人` `/搜` `/问` 输出、补名名单/
试听/表单/文字兜底/回调）。与 P0 合并后全量 `874 passed`（原 823 + 19 + 32）。
