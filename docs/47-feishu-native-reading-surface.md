# 47 · 飞书原生阅读面：不建公网网页，把「读、找、转」放回飞书

> 面向：产品 / 架构决策
> 结论时间：2026-11-25
> 关联：[docs/16](16-recording-sharing-options.md)、[docs/37](37-cloud-storage-and-feishu-share.md)、[docs/41](41-voice-room-knowledge-product-iteration.md)、[docs/46](46-three-surfaces-governance-review.md)
> 一句话：公网网页解决的是「飞书外的人也能看」；如果读者就在飞书里，云文档 + 多维表格 + 卡片已经够用，而且更顺手。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 还要不要做 Cloudflare 公网网页？ | **不作为默认方案。** 它把「阅读」误当成「再做一个桌面端网页」；如果读者在飞书里，云文档、多维表格、卡片已经覆盖阅读、查找、转发、评论、权限。只有「非飞书外部客户」才需要单独立项。 |
| 飞书端到底是什么？ | **阅读面 + 检索面 + 转发面**，不是桌面端的缩小版。桌面负责整理和校对，飞书负责「我在外面看一眼、找一句话、转给一个人」。 |
| 最小闭环是什么？ | **一场 = 一篇云文档 + 一行多维表格；一人 = 一篇档案 + 一行人物；一周 = 一篇周报；一个动作 = 一条任务。** |
| 最大的前提是什么？ | 云端场次必须先有转写和总结。`capture_only` 不产生总结，离线补转写也不触发 finalize（[docs/46](46-three-surfaces-governance-review.md) P1）；**不接通这条链，文档就是空壳。**（2026-11-26 已接通） |
| 先做什么？ | 先修 `offline_asr → finalize`，再做发布器（场次文档 + 场次表 + 收尾卡）。不要先做搜索页、问答页、公网网页。（P0 已落地，见 §7） |

## 1. 先回答「为什么没必要」

### 1.1 公网网页真正解决的是什么

| 需求 | 公网网页 | 飞书原生 | 建议 |
|---|---|---|---|
| 自己在外面用手机看 | 完整页面，但要域名、证书、登录 | 文档/表格原生阅读，消息推送 | **飞书够** |
| 同事在飞书内看 | 要再发链接，权限另做一套 | 飞书权限、评论、@、搜索现成 | **飞书更好** |
| 外部客户/非飞书用户看 | 唯一顺路径 | 受租户外部分享策略限制 | 只有这类才考虑公网 |
| 精确回听 + 逐字稿联动 | 现有 reader 直接搬 | 文档不能跳音频秒；妙记可但二次转写 | 桌面 / 妙记 |
| 完整桌面 UI、设置、校对 | 可以 | 不适合 | 桌面 |

结论：如果 80% 的阅读发生在飞书内，公网网页是为 20% 的场景造 100% 的系统。**先把飞书内做顺，外部交付再单独立项。**

### 1.2 飞书端的独特优势

- **内容长在协作流里**：一条消息、一篇文档、一张表、一个任务，都能被转发、评论、@、搜索、提醒。公网网页做不到这些，除非再造一套协作系统。
- **身份和权限现成**：组织架构、群、外部联系人、离职回收，都是飞书已经处理好的。
- **手机原生**：推送、离线阅读、搜一搜、收藏、稍后读，不需要我们做 App。
- **零新增基础设施**：不需要域名、备案、证书、登录、分享审计。云文档和多维表格由飞书托管，**我们不需要为阅读面备案**；数据仍在飞书租户内，受租户策略约束。
- **代价**：不能自定义播放器和布局；文档 API 有块级上限；妙记不能程序化创建；卡片表单依赖客户端版本。这些代价决定了「哪些不搬」。

### 1.3 所以飞书端不抄桌面端

| 维度 | 桌面端 | 飞书端 |
|---|---|---|
| 场景 | 坐下整理、校对、采集控制 | 在外面读、找、转 |
| 内容 | 逐字稿、时间轴、全员命名 | 结论、观点、原话、人物 |
| 交互 | 播放器、拖拽、批量改名 | 文档、表格、卡片、搜索 |
| 不做什么 | — | 逐字稿校对、重聚类、术语表编辑、设置、采集方式切换 |

**一句话：桌面端是「编辑室」，飞书端是「刊物 + 索引 + 剪报」。**

### 2.1 三个已经验证的事实

2. **云盘归档已经跑通**：`upload_file` 支持 20MB 以内直传、超过分片；`grant_member` 授权；`archive_session` 把 token/链接写回库（[app/feishu_drive.py:155](../app/feishu_drive.py)、[app/feishu_drive.py:181](../app/feishu_drive.py)、[app/feishu_drive.py:212](../app/feishu_drive.py)）。
3. **内容已经是结构化的**：`notes.build_note()` 已经有一句话、要点、按人分组、观点地图、高光、书签、说话人（[app/notes.py:88](../app/notes.py)）；`claims.profile()` 已经有「人 × 主题 × 主张 × 改口」（[app/claims.py:301](../app/claims.py)）；`report.build()` 已经能出周报 Markdown（[app/report.py:963](../app/report.py)）。**发布是组装，不是重新造 AI。**

### 2.3 这不是飞书的全部能力（2026-11-25 核对）

**不是。** 上面这张表只列了「与阅读面相关、且我们真的会用」的子集。飞书开放平台 SDK `lark-oapi` 1.9.0（2026-11-25 发布）包含 **60 个产品线**，从 IM、云文档、多维表格、妙记，到审批、OKR、绩效、人事、薪酬、服务台、邮箱、日历、会议 VC、低代码、企业百科都有；我们只用了其中 9 个（im、docx、drive、bitable、wiki、task、minutes、cardkit、search）。

> 核对方式：2026-11-25 直接抓取飞书官网 AI/Base/Minutes/Docs 产品页、PyPI `lark-oapi` 1.9.0 与开放接口文档。没有找到可核实的 2026 发布会官方页面（AI 页的预约链接仍指向 2025 landing），所以这里按「今天线上可用的能力」列，不按「发布会新闻」列。

今天能直接核到的几件事：

- **SDK 1.9.0 与 1.7.5 的 API 模块清单相同**（都是 60 个）。这一轮更新主要是 `client_assertion` 免密、应用一键注册、WebSocket 连接参数和 Channel 模块弃用，**不是新增了一批产品 API**。
- **飞书 AI 官网当前主推 6 块**：豆包工作、智能会议纪要（9900 元/年，不限人数）、豆包工作伙伴（企业 Agent 平台）、多维表格 AI、飞书妙搭（AI 原生系统搭建）、飞书项目 AI。**企业知识问答 API** 出现在「企业版 Plus / 旗舰版」的权益里，属于高阶套餐。
- **多维表格 AI** 已有：AI 字段捷径、AI 生成公式、AI 侧边栏、仪表盘 AI 分析、工作流 AI Agent 节点、AI 生成工作流，以及 200+ AI 模型/插件；同时支持 BI、行列级 RBAC。官网营销说「单表千万热行」，但开放接口文档仍写「单表 2 万条」——**以租户版本和接口文档为准，P0 按 2 万设计**。
- **妙记 AI** 已有：AI 会议纪要、智能待办、评论/@、导出视频/文档、创建片段、分享权限；但开放接口仍只有读取/搜索/订阅，**没有创建/上传**。
- **云文档** 已有：思维导图/流程图、任务、投票、群卡片/日程/任务、密级标签、同步块、可嵌入业务系统的文档网页组件；这些大多是 UI 原生能力，不需要我们开发。

**对我们意味着什么**：

1. **P0 不变**：阅读面仍然只需要 3 个容器——云文档、场次表、收尾卡。AI 平台/低代码/项目 AI 都不进 P0。
2. **`/问` 仍以引擎为准**：我们的问答能引到逐字稿时间码和术语表；企业知识问答 API/Aily 只能看到已发布文档，适合作为「在飞书里顺手问」的补充，不能替代引擎的证据链。
3. **Base AI 不重复造**：场次表/人物表建好后，用户可以自己加 AI 字段做打标/分析；我们不要把引擎已有的观点抽取再做成 Base AI 字段。
4. **文档协作免费用**：评论、@、投票、任务、同步块都是飞书原生；P0 的场次文档一发布，这些能力就自动可用。
5. **不接的**：智能会议纪要（只服务飞书会议，不服务外部语音厅）、项目 AI（独立产品，现阶段和我们的引擎重复）、审批/OKR/人事/薪酬/服务台（与场景无关）。**妙搭**单独说：它确实能搭自定义界面，是「比公网网页更飞书原生」的一条路；但它是另一套应用运行时，接引擎/数据要另做，现阶段 docs/Base 足够，等真有自定义界面需求再评估。

> 结论：docs/47 是「阅读面选型」，不是「飞书功能大全」。飞书的能力边界比这张表大得多；但对我们的产品，**能减少自研的只有云文档、Base、卡片、妙记读取和文档协作**，其余最多是 P2 的体验补充。

## 3. 产品形态：四个「一」

### 3.1 一场 = 一篇场次文档

**为什么不是逐字稿**：手机上看不完，也没必要。文档只放「结论 + 观点 + 原话 + 人物」，逐字稿留在桌面端/导出文件/附件。目标篇幅 **1500~2500 字**，5 分钟读完。

模板（以语音厅圆桌为例）：

```markdown
# 2026-11-25 22:30 ·「今晚聊 AI 出海」· 圆桌

> 房间：XXX ｜ 时长：1 小时 42 分 ｜ 上麦：8 人 ｜ 主持：阿岚
> 采集：云端节点 ｜ 状态：已总结 ｜ 观点 6 条 ｜ 高光 3 条

## 一句话
这场真正吵起来的是「先做东南亚还是先做中东」，不是标题里的「AI 出海」。

## 观点地图
### 阿哲 · 3 条
- **先做东南亚**：支付和内容生态更成熟，冷启动快。（22:14）
  > 原话：「你在中东买量，先亏三个月，还不一定回本。」
- **改口**：上周说「中东客单价高值得试」，这场说「先东南亚」。（22:41）

### 小北 · 2 条
- **先做中东**：客单价高，愿意为工具付费。（23:02）
  > 原话：「东南亚付费率摆在那儿，你补贴到什么时候？」

### 没人回答的问题
- 小北问「中东的本地化客服谁来做」，到结束没人接。

## 值得回听
| 时间 | 谁 | 为什么值得听 | 原话 |
|---|---|---|---|
| 22:14 | 阿哲 | 这场分歧的起点 | 「你在中东买量……」 |
| 23:02 | 小北 | 反方最完整的一段 | 「东南亚付费率……」 |
| 23:41 | 阿岚 | 主持收束，给了判断标准 | 「那就看谁先跑通复购。」 |

## 人物
| 上麦者 | 发言 | 时长 | 档案 |
|---|---|---|---|
| 阿哲 | 18 条 | 26 分 | 阿哲 · 观点档案 |
| 小北 | 14 条 | 21 分 | 小北 · 观点档案 |

## 相关场次
- 11-18 ·「中东工具市场」· 阿哲也提过客单价
- 11-11 ·「东南亚支付」· 小北当时在场

---
由 LiveNotes 生成。逐字稿与完整时间轴在桌面端；本页只保留结论与可引用的原话。
```

**写作纪律**：

- 原话每条 ≤ 80 字，只留能独立成立的句子；口头禅清掉，但不改意思。
- 时间码是纯文本，**不假装能点**；能点的只有：妙记链接（人工回填）、云盘录音、机器人发的片段。
- 没有总结就明确写「待补转写 / 总结失败」，**不生成规则版兜底稿**（与「不做本地抽取兜底」一致）。
- 人名没补全时，用「一位上麦者」而不是猜一个名字；文末放补名入口。
- 有明确行动项时，加一段 `## 待办`（谁 / 做什么 / 何时前）；P2 再同步成飞书任务，不要在 P0 就做任务系统。

### 3.2 一行 = 场次索引（多维表格）

**为什么用 Base 而不是文档里的列表**：手机上要按房间、日期、状态筛选，要按观点数排序，要一眼看到「哪场还没转写」；这些是表格的原生能力，文档列表做不到。

P0 只建 **场次表**：

| 字段 | 类型 | 说明 |
|---|---|---|
| 标题 | 文本（主字段） | `11-25 22:30 · 房间 · 圆桌` |
| 日期 | 日期 | 用于排序/本周视图 |
| 房间 | 文本 | 语音厅名称 |
| 形态 | 单选 | 单人 / 圆桌 / 问答 |
| 主持 | 文本 | 没有就空着 |
| 上麦人数 | 数字 | 来自 `shape.speaker_count` |
| 时长分钟 | 数字 | 来自 `session.duration_s` |
| 一句话 | 文本 | 来自 `summary.overview` |
| 观点数 | 数字 | 来自 `counts.points` |
| 高光数 | 数字 | 来自 `counts.highlights` |
| 状态 | 单选 | 待转写 / 待总结 / 已发布 / 发布失败 |
| 文档链接 | URL | 场次文档 |
| 录音链接 | URL | 云盘 m4a，可空 |
| session_id | 文本（隐藏） | 幂等键，不给人看 |
| 标签 | 文本（顿号分隔） | 主题词，来自 `summary.topics`；P0 先不用多选，避免选项不存在导致写不进去 |
| 逐字稿附件 | 附件 | 可选；不放正文 |

视图：

- **最近场次**：日期倒序，手机默认打开这个。
- **本周**：日期在最近 7 天。
- **按房间分组**：看哪个厅产出多。
- **待补转写**：状态 = 待转写，运营每天清一次。
- **观点最多**：观点数倒序，找值得回看的场。

P1 再加 **人物表** 和 **观点表**（人物表的完整设计见 §3.6）：

| 表 | 关键字段 |
|---|---|
| 人物 | 名称、状态、首次出现、最近出现、场次、上麦时长、观点数、主要主题、档案链接、person_id（隐藏）。**只收已命名的人**，见 §3.6 |
| 观点 | 观点、谁、主题、场次、时间码、原话、状态（新提出/重申/修正/被反驳）、首次、最近、claim_id、场次文档链接。**按场次整体替换**，不逐条 upsert |

**MVP 纪律**：不用「关联」字段，用文本 `session_id` / `person_id` + URL 字段。关联字段要跨表 token、record_id，upsert 复杂，第一版不值得。

### 3.3 一人 = 一篇人物档案

人物档案回答的是「他讲过什么」，不是「他在哪几场出现过」。模板：

```markdown
# 阿哲 · 观点档案

> 首次：2026-10-14 ｜ 最近：2026-11-25 ｜ 场次：7 ｜ 上麦：3 小时 12 分 ｜ 观点：19 条

## 最近在讲什么
### AI 出海
- **先做东南亚**（11-25）：支付和内容生态更成熟。
  > 「你在中东买量，先亏三个月……」
- **改口**：11-18 说「中东客单价高值得试」→ 11-25 说「先东南亚」。
- 更早：10-28「先做工具，不做内容」；11-04「内容才是壁垒」。

### 工具选型
- ……

## 出现场次
| 日期 | 场次 | 时长 | 文档 |
|---|---|---|---|
| 11-25 | 今晚聊 AI 出海 | 26 分 | 打开 |
| 11-18 | 中东工具市场 | 31 分 | 打开 |

---
身份来自声纹聚类与人工补名，可能认错；以本人/主持确认为准。
```

**必须写的免责声明**：声纹是概率匹配，不是身份证。错认一个人，比不认更伤信任。

### 3.4 一周 = 一篇周报

周报是手机端的「首页」，不是场次文档的堆叠。现有 `report.build()` 已经能生成（[app/report.py:963](../app/report.py)），只需要：

- 每场后面加「场次文档」链接；
- 加一段「下周可追的问题」（从 `opinion_map` 的未回答问题里取）；
- 加「本周人物」（观点数/改口最多的 3 个人，链到人物档案）；
- 末尾加「全部场次」Base 视图链接。

周报已经在机器人 `/周报` 里建 docx（[tools/feishu_bot.py:996](../tools/feishu_bot.py)），P0 只需补链接，不重写生成逻辑。

### 3.5 一个动作 = 一条任务（P2）

只把**明确说出来的行动项**建成飞书任务：谁、做什么、什么时候前。任务来源必须是总结里的显式条目，不做「猜测式行动项」。任务带 `origin.href` 指回场次文档（Task API 的 `origin` 支持 URL + 标题），用户在任务中心点开就能回到原话。

语音厅的行动项通常不多；这条是锦上添花，不进 P0。

### 3.6 人物表设计：索引，不是通讯录

**定位一句话**：人物表是「已确认人物」的索引，是命名行为的投影，不是标注工作台。正文在人物档案文档，表只负责找得到人。

#### 3.6.1 身份分三层，现在的绑定在哪

| 层 | 是什么 | 谁产生 | 稳定性 |
|---|---|---|---|
| 槽位 | 本场第 N 位 / `SPK_00` | diarization，必然存在 | 只在本场有效 |
| 声音 | 同一个声音跨场 | 声纹比对；**现在要有名字才创建** | 跨场，可能错 |
| 人物 | 这个声音叫阿哲 | 人工补名/确认 | 跨场，权威 |

核对代码后的事实：

- `persons` 只在 `enroll_speaker()` 里创建（[app/voiceprint.py:137](../app/voiceprint.py)），唯一调用入口是补名（[app/naming.py:186](../app/naming.py)）；
- `match_session()` 只在**已有的人**里匹配（[app/voiceprint.py:343](../app/voiceprint.py)），底库为空直接返回「先在任意一场里把说话人改成真实昵称」；
- 没命名的声音簇跨场不聚合，永远停在「本场第 N 位上麦者」。

所以：**跨场人物能力 = 命名率的函数**。不是人物表绑得死，是「人物」这个实体由命名事件创建。v1 接受这个前提；要不要解耦，看 3.6.5 的数据门槛。

#### 3.6.2 命名率为 0 时，哪些链路会断

| 链路 | 命名率为 0 时 | 结论 |
|---|---|---|
| 采集 / 转写 / 总结 | 正常 | 不断 |
| 场次文档 | 显示「本场第 N 位上麦者」（[app/identity.py:90](../app/identity.py) 的逐级兜底） | 不断，只是不具名 |
| 观点地图 / 分享卡 | 用本场 `who` 兜底（[app/claims.py:99](../app/claims.py)） | 不断 |
| 观点表 | 照常出列，`person_id` 为空 | 不断；跨场按人筛会漏 |
| 人物表 / 人物档案 | 空 | 是「缺」，不是「断」 |
| 周报人物段 | 归入「其他上麦者」 | 不断 |
| 补名后的历史场次 | 只重建当场（[app/naming.py:205](../app/naming.py)） | **隐性断点，v1 必须补**（3.6.4） |
| Base 三张表 | 发布器是单向投影 | 不会反噬引擎 |

**产品不可用的唯一触发条件**：把「先命名」设成发布前置，或把 Base 当真相源、允许人在表里改身份。守住 §6 的单向发布与「补名是唯一反向通道」，这两条都不会发生。

#### 3.6.3 表结构（v1）

| 字段 | 类型 | 来源 / 规则 |
|---|---|---|
| 名称 | 文本（主字段） | `persons.name` |
| person_id | 文本（隐藏） | 幂等键，不给人看 |
| 状态 | 单选 | 已确认 / 自动识别 / 待确认 |
| 首次出现 / 最近出现 | 日期 | `speakers` 聚合 |
| 出现场次 / 上麦分钟 / 观点数 | 数字 | `person_appearances` + `claims`（只统计已归属的 claims） |
| 主要主题 | 多选 | `claims.topic` top 3 |
| 档案链接 | URL | 人物档案 docx |
| 合并到 | 文本（隐藏） | 错认合并后指向新 person_id |

**状态口径**：

- 已确认：至少有一次人工注册/确认（出现过 `person_state='confirmed'`）；
- 自动识别：只有 `auto` 匹配；
- 待确认：只有 `cand` 低分匹配；
- 「仅本场」的人不进表。

**收行规则**：只发布**已命名、且（观点数 > 0 或 场次 ≥ 2）**的人。路人、只出现一次且没观点的人不进表——与「没有观点不生成空档案」同一条纪律。命名率低时表是空的，这是预期行为，不是故障。

**主要主题的局限**：`claims.topic` 是本场标注词，跨场尚未归一化；归一化完成前，这一列只用于人内浏览，不用于跨人统计（与观点表的主题筛同一前提）。

**写入规则**：

- 本地维护 `person_id → record_id` 映射，按 record_id update；**不要在 Base 里按名字查重**，名字会变、也会重名；
- 改名、合并只更新属性，不新增行；合并后旧行标「已合并」并指向新档案，不删除（保住历史链接）；
- 观点表相反：`claim_id` 是 `hash(session_id, 要点序号)`（[app/store.py:372](../app/store.py)），每场重建是原意，所以**按场次整体替换**（先删该场旧行再写），换模型重生成也不留孤儿行。

视图：**活跃人物**（最近 30 天）、**本周新面孔**、**观点最多**、**待确认**（自动识别/低分）。

**建表时机**：top 3 命名率连续两周 ≥ 50% 再建；低于阈值先把补名卡做好，表建了也是空的。

#### 3.6.4 手动标注的角色

名字只能人工给，声纹只回答「是不是同一个声音」。目标不是消灭标注，是让不标注也不崩、标注有回报：

- **量**：只补 top 3~5，不补全员（[app/naming.py:2](../app/naming.py) 的既有设计）；
- **频次**：每天一条收尾卡，30 秒；跳过不影响任何视图；
- **回报**：命名一次 → 声纹入库 → 下次自动认 → 人物档案与跨场观点才成立；
- **身份源优先级**：平台昵称（若采集端能拿到麦序/昵称）> 人工补名 > 声纹。采集节点能否抓到昵称值得先核实，这比做匿名聚类便宜得多。

**v1 必须补的一环：补名后回填历史。** 现在 `name_speaker()` 只 `claims.rebuild_session(conn, sid)` 当前场；该人此前出现过的场次不会自动改归属。做法：补名成功后，后台对该 person 的候选场次重跑 `voiceprint.match_session()` 并 `claims.rebuild_session()`（走队列，不在请求线程里做，遵守 [docs/45](45-offline-asr.md) 的内存约束）。历史场次文档**不重写**（避免丢评论锚点），只更新人物档案与人物表；历史文档等用户显式 `/发布` 再重发。

#### 3.6.5 匿名声音档案（P1.5，先看数据再决定）

如果同一个人反复上麦但从不命名，人物表会一直缺他。解法是让「声音」先于「名字」存在：同一声音**第二次高置信出现**时才建 provisional person（显示「声音 · 11-25 首现」），命名时把名字绑上去，而不是新建一个人。

先量三个数（现有库就能算），不达标不做：

1. top 3 命名率；
2. 说话人回访率（出现 ≥ 2 场的声音占比）；
3. 未命名回访声音占发言时长的比例。

判据：回访率 < 30% 说明是路人局，人物表本就不该是重点，观点表按主题走；回访率高、命名率低，匿名声音档案才成立。风险控制：一次性的声音永不建行；只有一个 3 秒样本不建；否决/合并/拆分是一等操作；用「人工否决率」度量错并率。

#### 3.6.6 明确不做

1. Base 人物表不做编辑与合并——身份操作只在引擎侧，表只读；
2. 不用昵称/姓名做关联键，永远 `person_id`；
3. 不为路人建行，不给没观点的人建空档案；
4. 不追求 100% 命名率，追 top 3 命名率；
5. 不叫「通讯录」——文案统一「声音档案」，「这个声音出现过 7 场」比「这个人是阿哲」错得起。

## 5. 三个关键流程

### 5.1 收尾发布：finalize → 文档 + 表 + 卡片

```
captured ──→ transcribed ──→ summarized ──→ published
   │              │                │
   └─ 待补转写 ───┴─ 待总结 ───────┴─ 发布失败（可重试）
```

**状态规则**：

| 状态 | 什么时候 | 文档里写什么 |
|---|---|---|
| 待补转写 | 仅采集，或离线 ASR 未完成 | 标题、时间、时长、房间、录音链接、「转写完成后自动更新」；**不写摘要** |
| 待总结 | 有逐字稿，总结未完成/失败 | 逐字稿统计、上麦者列表、「总结失败，原因……」；**不写规则兜底稿** |
| 已发布 | 总结成功 | 完整模板 |
| 发布失败 | 文档/表格接口失败 | 库里有内容，卡片/命令可重试；不阻塞采集 |

**流程**：

1. `tasks._run_summary` 成功 → `notes.index_session`（[app/tasks.py:92](../app/tasks.py)）→ 触发 `feishu_publish.publish(sid)`。
2. 发布器读取 `notes.build_note()` + `claims.profile()` + `person_appearances()`，生成发布用 Markdown（新增 `export.to_publish_md()`，不要直接复用 `to_note_md`，后者缺时间码、观点地图、人物链接）。
3. `ensure_doc(sid)`：查 `feishu_publish`，有 `document_id` 就复用；没有就 `create_docx`。
4. 覆盖正文：列出根块 → `batch_delete` 清空 → `block_descendant.create` 写入新块。
5. `permission_member` 授权给 owner（群场景授权给群，member_type 用 `openchat`，需验证）。
6. upsert 场次表：按 `session_id` 找 `record_id`，有就 update，没有就 create。
7. 发收尾卡片：`看文档` / `补名` / `听 3 段` / `问这场`。
8. 写 `feishu_publish`：`state=ok`、`version=hash`、`doc_token`、`record_id`、`latency_ms`。

**实现落点（2026-11-26）**：

- `tasks._run_summary` 只在「整场口径」的总结后自动发布；带筛选条件的总结不发布，避免筛选稿冒充整场文档。
- 仅采集下播由 `live._auto_finalize` 先发「待补转写」骨架；离线补完字后调 `POST /api/sessions/finalize`（`recluster=False`，重聚类已由补转写做过），走同一套收尾和发布。
- 正文更新是「列根块 → `batch_delete` → 从 0 写回」。这会丢评论锚点，所以只有版本变化、补名或显式 `/发布` 才重写；普通重试版本没变就跳过。

**幂等**：

- `feishu_publish` 唯一键 `(session_id, kind)`；`version` 是 Markdown + 标题 + 人名的 hash。版本没变，重试直接跳过。
- 文档建成功但正文失败：保留 `document_id` 和 `url`，下次只补正文，不新建第二篇。
- 表格写成功但文档失败：表格行标 `发布失败`，文档重试成功后改回 `已发布`。

**重发布**：

- 只在「补名后」「用户显式 `/发布`」时重发布；不要每次重试都重写，避免评论锚点丢失。
- 清空根块会丢评论锚点；文档里加一句「重新发布后旧评论可能失效」，或在重发布前把评论数记进日志。

**失败降级**：

- 文档失败 → 发 `.md` 文件 + 表格行仍然可查；不阻塞总结/采集。
- 表格失败 → 文档仍然可读；表格行下次重试补。
- 飞书未配置 → 整个发布器静默跳过（日志 `feishu.publish_skipped`），不影响本地。

### 5.2 补名：飞书端唯一反向写回

**为什么重要**：语音厅 10 个人轮流上麦，没有名字，观点地图就是「一位上麦者 A/B/C」。补名是「知识产品是否成立」的分水岭（[docs/46](46-three-surfaces-governance-review.md) R6）。

**流程**：

1. 收尾卡检测 `top3.named < slots`（`/api/sessions/top_speakers` 已经返回 `preview` 3 秒窗口和声纹建议，见 [app/naming.py:92](../app/naming.py)）。
2. 机器人依次发 3 条音频消息：A/B/C，每条 3 秒，来自 `preview.t_start/t_end`（`/api/audio?session_id=&t_start=&t_end=`）。
3. 发一张卡片 2.0 表单：3 个输入框，标签 A/B/C；有可信建议时预填「像阿哲」，用户可改。
4. 用户提交 → 卡片回调带 `form_value` → 校验操作者（owner 或发起人）→ 调 `/api/speakers/name`（[app/server.py:2937](../app/server.py)）→ 声纹注册、观点归属重建。
5. 成功后重发布**当场**文档（人名变了），更新人物档案/人物表；该人的历史场次由后台重跑匹配并重建 claims（§3.6.4），历史文档不重写。
6. 兜底：用户直接回「1 阿哲 2 小北」，机器人解析；卡片回调不可用时也能用。

**隐私**：

- 声纹只留本地，**不进飞书、不进 Base**。
- 3 秒音频只在用户点「补名」后发，且只发私聊/授权群；不自动发群。
- 人名是个人信息；文档权限默认只给 owner/房间群，不做公开链接。

## 6. 架构：单向发布，不做双向同步

```
SQLite（唯一真相源）
  │
  ├─ finalize / offline_asr ──→ publish_jobs ──→ app/feishu_publish.py
  │                                                   │
  │                                                   ├─→ docx（场次/人物/周报）
  │                                                   ├─→ Base（场次/人物/观点）
  │                                                   └─→ Drive（整场音频，可选）
  │
  └─ 补名卡片 ──→ bot callback ──→ /api/speakers/name ──→ SQLite ──→ 重发布
```

**原则**：

1. **引擎是真相源**；飞书是「发布产物」。文档里的人工编辑不回流，评论只当反馈，不当数据。
2. **唯一反向通道是补名**：因为它要写声纹和观点归属，必须回到引擎。
3. **发布器不加载模型**：只做 Markdown 组装 + HTTP，不增加云端节点内存；发布失败不影响采集/转写/总结。
4. **不双向同步**：双向同步要处理冲突、删除、权限、块级 diff，成本远高于收益；第一版坚决不做。
5. **不自动建群**：把机器人拉进用户已有的房间群即可；自动建群是打扰。
6. **应用建的 Base 也要授权**：和文档一样，应用创建的 Base 默认只有应用能看；用 `permission_member`、`type=bitable` 授权给 owner/群，否则用户点开就是无权限。

**配置新增**（已实现；环境变量优先，其次 `data/feishu.json` 同名键）：

| 配置 | 用途 |
|---|---|
| `FEISHU_PUBLISH_ENABLED=1` | 总开关；默认关，桌面用户可不开 |
| `FEISHU_PUBLISH_FOLDER_TOKEN` | 场次/人物文档的云空间文件夹；不填复用 `doc_folder_token` |
| `FEISHU_PUBLISH_OWNER` | 默认授权给 owner；不填用机器人配置里的 `owner_open_id` |
| `FEISHU_BASE_FOLDER_TOKEN` | 多维表格存放文件夹；不填复用文档文件夹 |
| `FEISHU_BASE_APP_TOKEN` | 可选：预建 Base，避免每次新建 |
| `FEISHU_BASE_TABLE_ID` | 可选：预建数据表；不填自动建 |
| `FEISHU_PUBLISH_BASE=0` | 只发文档、不写场次表 |
| `FEISHU_BASE_URL_BASE` | 可选：Base 链接前缀；不填用飞书返回的 `app.url` |

授权对象优先用 `FEISHU_PUBLISH_OWNER`，没配就沿用现有 `open_id` /
`owner_open_id`：建文档/建 Base 后都用 `permission_member` 授权给这位用户
（Base 用 `type=bitable`）。Base token 首次建好后写进 `index_meta`，进程
重启不会重建。

**可观测**：

- `feishu.publish_ok` / `feishu.publish_failed`：session_id、kind、latency_ms、error。
- `feishu.base_upsert`：table、record_id、created/updated。
- `feishu.publish_skipped`：未配置/版本未变。
- `/状态` 卡片增加一行「发布：最近成功时间 / 待重试数」。

| 重发布丢评论 | 协作反馈丢失 | 只在补名/显式发布时重写；日志记录评论数 |
| 发布延迟/成本 | 云端节点带宽/内存 | 发布器不加载模型；文档/表格写入异步；大音频不自动上传 |

## 14. 观点表实施记录（2026-11-27）

**范围**：在已有 Base 里新增第二张表「观点」（与「场次」表同 `app_token`），作为 `claims` 表的单向只读投影，补上「跨场追一个观点」的索引。不调模型、不重抽、不做双向同步、不放逐字稿全文。

**字段（13 列，主字段「观点」在首位，默认视图「最近观点」）**：

| 字段 | 类型 | 规则 |
|---|---|---|
| 观点 | 文本（1，主字段） | `claims.stance`；空退 `gist`，再空退 `quote[:80]` |
| 谁 | 文本（1） | `person_id` 非空 → `persons.name`；否则 `claims.who`；未命名退回 `identity.claim_ref` 的「本场第 N 位上麦者」 |
| 主题 | 文本（1） | `claims.topic` 自由词表，空着也照写（不用多选，避免选项缺失导致整行失败） |
| 类别 | 单选（3） | `主张` / `问题`（`claims.kind` 的 `claim` / `question`） |
| 状态 | 单选（3） | `新提出` / `重申` / `修正` |
| 场次 | 文本（1） | `sessions.title` |
| 日期 | 日期（5） | `started_at` → 毫秒时间戳 |
| 时间码 | 文本（1） | `timefmt.offset(t)` 纯文本，不假装可点击 |
| 原话 | 文本（1） | `claims.quote`（截 300 字） |
| 场次文档链接 | URL（15） | 仅取 `feishu_publish`（`kind="session"`）台账 `doc_url`；没有就不写该键 |
| claim_id / session_id / person_id | 文本（1） | 隐藏索引/排查/批量删除键，不用关联字段 |

**建表、配置与替换策略**：

- 复用 `ensure_base()`（并确保复用已有 Base 时也会走一次 `permission_member` 授权，覆盖表内所有表）；`_find_table` / `_create_table` / `_ensure_fields` 参数化共用，老表缺字段自动补。
- `table_id` 持久化到 `index_meta` 的 `feishu_base_claims_table_id`；环境变量 `FEISHU_BASE_CLAIMS_TABLE_ID` 优先；开关沿用 `FEISHU_PUBLISH_BASE=0`（两张表一起停）。
- **按场次整体替换**（`_upsert_claims`）：用每条 `claim_id|person_id|who|topic|stance|kind|quote|t|状态` 加 `doc_url` 算 sha1 前 16 位签名，落台账 `feishu_publish(session_id, kind="claims")`。签名未变且 `state=ok`（非 `force`）直接跳过；无观点且从未写过也跳过不建空表。需要写入时先按 `session_id` 翻页（`page_size=100`）查全量旧行 → `batch_delete`（每块 ≤500）→ `batch_create`（每块 ≤500），避免要点数量变动留下孤儿行；删成功建失败记 `failed`，重试走「搜空→再建」不会重复。
- **失败隔离**：`_publish()` 正常路径里观点表失败只标整场 `partial` 并在 `error` 记「观点表没写成功：…」，不让文档失败；下次重试只补观点表不重写正文。文档失败时观点表仍照写（无链接），文档恢复后因 `doc_url` 进签名自动重写补链。版本未变早退路径下若仅 `doc_url` 或观点变化，只重写观点表、不碰文档正文（保住评论锚点），返回 `claims_updated: True`。

**状态规则**：

- 按 `claims.person_key(person_id, who)` + `topic` 找**更早场次**（`sessions.started_at < 当前场` 且未删除）里最近一条（`started_at DESC, t DESC`）；同场内多条不互相比较。
- 无更早记录 → `新提出`；`claims.similarity(当前, 上条)` `>= SAME_RATIO` → `重申`，`< REVISION_RATIO` → `修正`，其余 → `新提出`。

**已知局限**：

- 不做「被反驳」：引擎仅有 `claims.disagrees()` 词面判断，缺少「谁反驳谁」归属，硬做会误报。
- 状态相对更早场次计算：补发更早历史场次后，已发布场次的状态不会自动重算，除非对该场再执行 `/发布`。
- 默认只建「最近观点」视图，不加筛选视图（`app_table.view` 筛选请求体未验证）。
- `claims.topic` 为本场标注自由词，跨场尚未归一化，筛选以文本包含为主。
