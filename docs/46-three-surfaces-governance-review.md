# 46 · 多端职责与云端采集制度审查

> 面向：产品 / 架构决策
> 审查对象：桌面端、网页端、飞书机器人、云端仅采集节点
> 结论时间：2026-11-25
> 方法：代码走读 + 全量 `pytest`（本机 823 通过）+ 部署文档核对

## 0. 先回答四个问题

| 问题 | 结论 |
|---|---|
| 桌面、飞书、云端分别负责什么？ | 现在不是「三个端」，而是**一个引擎 + 两个界面 + 三种部署**。云端不是一个新客户端，而是同一引擎的「仅采集」部署档位。 |
| 人在外面、只用飞书，能否完整体验产品？ | **不能。** 飞书是「控制面 + 投递面」，不是阅读面；云端仅采集又砍掉了实时字幕、说话人命名与知识化能力。 |
| 桌面端是否已经可以选择云端服务器采集？ | **不能。** 桌面只会拉起并接管本机引擎，采集方式只有 browser / direct / external 三种本地实现。 |
| 引入云端后是否满足回归？本地采集是否保留？ | 本地采集默认保留，823 个测试通过；但编排层与桌面壳没有自动回归，并发现一个采集方式切换竞态、一个云端死链和一条离线补转写后的下游断链。 |

## 1. 产品模型：一个引擎 + 两个界面 + 三种部署

```
                    ┌──────────────────────────────┐
                    │           引擎 app/ run.py     │
                    │  采集入库 / ASR / 存储 / API   │
                    │  网页 / 简报 / 调度 / 通知      │
                    └──────────────┬───────────────┘
                                   │ HTTP（同源）
              ┌────────────────────┼────────────────────┐
              │                    │                    │
     ┌────────▼────────┐  ┌────────▼────────┐  ┌────────▼─────────┐
     │ 桌面壳 desktop/ │  │ 网页 app/web    │  │ 飞书机器人 tools/ │
     │ 窗口/托盘/本地引擎│  │ 完整阅读与整理面 │  │ 命令 + 卡片 + 文件 │
     │ WebView2 采集    │  │                │  │ 不持有业务数据     │
     └────────┬────────┘  └────────────────┘  └────────┬─────────┘
              │                                          │
     ┌────────▼──────────────────────────────────────────▼─────────┐
     │ 三种部署：桌面全量 / 局域网全量 / 云端仅采集 + 离线补转写     │
     └──────────────────────────────────────────────────────────────┘
```

| 部署 | 进程 | 可用界面 | 采集 | 转写 | 数据位置 |
|---|---|---|---|---|---|
| 桌面全量 | Tauri 壳 + 本机引擎 + helpers（飞书机器人、采集代理） | 桌面壳 + 全部网页 | 应用内 WebView2 / 抖音直取 / 外部 Chrome | 实时 | `%LOCALAPPDATA%\LiveNotes\data` |
| 局域网全量 | `run.py --lan` + 手动起采集代理/机器人 | 手机/电脑网页（同一 Wi-Fi） | per_room / shared / direct | 实时 | 仓库 `data/` |
| 云端仅采集 | 引擎（`LIVENOTES_CAPTURE_ONLY=1`）+ 直取代理 + 飞书机器人 + 可选离线补转写 | **只有飞书** | 仅 direct（Linux 无浏览器采集） | 无实时，事后补 | VPS `/opt/livenotes/data` |

**关键判断：** 云端采集是「部署参数」，不是「端」。它之所以看起来像第三端，是因为它没有可用的网页界面（只绑回环、无备案域名），只剩飞书这一个操作面。把部署叫成端，会直接导致后面所有职责、能力、回归问题都说不清。

## 2. 职责边界（现状与越界点）

| 组件 | 应负责 | 不应负责 | 现在的越界 / 耦合 |
|---|---|---|---|
| 引擎 `app/` | 唯一业务真相源：采集入库、ASR、SQLite、检索、总结、API、网页 | 窗口、托盘、飞书长连接 | 断流预警自己拼 `lan.base_url()` 链接（[app/live.py:1914](../app/live.py)），不知道外面是手机还是桌面 |
| 桌面壳 `desktop/` | Windows 生命周期、托盘、拉起/接管本机引擎、WebView2 采集、原生子视图 | 业务数据、云端节点管理 | 自己决定「谁接房间」：读 prefs 判断 capture_mode（[desktop/src-tauri/src/rooms.rs:712](../desktop/src-tauri/src/rooms.rs)） |
| 网页 `app/web` | 完整阅读、整理、校对、分享卡、周报、设置 | 采集进程生命周期 | 网页版与桌面壳各有一套采集方式文案（[app/web/index.html:298](../app/web/index.html) vs [desktop/dist/shell.html:475](../desktop/dist/shell.html)） |
| 飞书机器人 `tools/feishu_bot.py` | 远程命令、状态、卡片、音频片段、文件投递 | 转写、总结、采集本身 | 用**自己进程的** `CAPTURE_ONLY` 决定文案（[tools/feishu_bot.py:38](../tools/feishu_bot.py)），不是读引擎状态 |
| 采集代理 `tools/capture_agent.py` | 房间 → 浏览器 / ffmpeg 的进程生命周期、断流重建、下播判定 | 会话归属决策 | 会接管任何 pending/starting/live 房间（[tools/capture_agent.py:1381](../tools/capture_agent.py)），不区分房间由谁启动 |
| 离线补转写 `app/offline_asr.py` | 增量出字、声纹、收尾重聚类 | 总结/观点/通知流水线 | 补完只写 utterances + recluster，不触发 finalize（[app/offline_asr.py:443](../app/offline_asr.py)） |

**制度含义：** 目前有四个地方在决定「谁来采、怎么采」——`run.py` 的 helper 编排、桌面壳 watcher、采集代理、设置页 prefs。它们没有共享同一个房间归属契约，这是后面竞态与文案不一致的根因。

## 3. 只用飞书：能力审计

### 3.1 结论

**不能完整体验。** 飞书端覆盖了「开录、看状态、停/重试、听片段、要总结、导包、周报」这条运行闭环；但产品的第二半——**读、校对、命名、整理、分享、沉淀**——几乎全部缺席。云端仅采集模式还要再砍掉实时字幕与实时说话人，直到离线补转写追上。

> **2026-11-25 补充**：本节说的是「现状」，不是「飞书能力上限」。不建公网网页也能补阅读面：用云文档承载场次/人物/周报、多维表格承载索引、卡片承载补名与分发。方案与路线见 [docs/47](47-feishu-native-reading-surface.md)。下面的「✗」是当前产品缺口，不是平台限制。

| 产品能力 | 桌面/网页 | 飞书（本机完整引擎） | 飞书（云端仅采集） |
|---|---|---|---|

### 3.3 具体缺陷（按严重度）

**P0 · 云端与桌面是两套孤立数据。** 云端场次、逐字稿、录音都只存在 VPS 的 `data/`；桌面端没有「远端节点」概念，也没有导入接口。唯一的取出路径是 `/分享包` 或 `/分享` 手动转发。后果：用户白天在手机录、晚上开桌面，看到的是两个互不相干的历史；周报、观点档案、人物页各算各的。

**P0 · 手机无法补名，知识产品的主语缺失。** 机器人没有任何命名/改判命令（`feishu_bot.py` 无 `naming` 调用）。云端补转写后说话人仍是「说话人1/2」，总结与观点只能写「说话人2认为」。对一个语音厅产品，「谁说的」是核心价值，这一项在手机上不可修复。

**P1 · 云端没有实时字幕，`/近聊` `/总结` 有前置条件。** 仅采集模式不加载 ASR（[app/config.py:24](../app/config.py)），补转写追平前，`/近聊` 只会回「这段时间还没有字幕」，`/总结` 没有内容。机器人隐藏按钮的逻辑是对的（[tools/feishu_bot.py:1406](../tools/feishu_bot.py)），但用户看不到「还要等多久」——没有进度/ETA，只有「仅录制」或「补转写 N 句」。

**P1 · 手机无法完成首次配置与排障。** 机器人没有设置命令；LLM 配置、采集方式、周报时间、通知开关都只能上网页或 SSH。按 [docs/44](44-cloud-feishu-bot.md) 部署完，如果没在服务器 `settings.json` 里配模型，`/总结` 会一直失败，而手机上没有修复入口。

**P1 · 关注/自动记录在手机上不可用，且下播后必须手动 `/重试`。** `follows` 是网页/桌面功能；机器人里的「关注」其实是关键词加权（`profile.add`），不是关注直播间。云端 7×24 的核心卖点「出门也一直录」，实际上每场结束都要人发一次 `/重试`；`LIVENOTES_RESUME_ROOMS=1` 只是环境变量，没有产品入口（[app/config.py:20](../app/config.py)、[docs/44 §5](44-cloud-feishu-bot.md)）。

**P1 · 磁盘/健康告警到不了手机。** `notify.*` 只写本地通知表（[app/notify.py:99](../app/notify.py)），桌面壳轮询它；云端没有人读这张表。磁盘不足、静音预警、笔记完成都不会出现在飞书。断流预警虽然走 `push_capture_lost`，但文本里带的是 `lan.base_url()`（[app/live.py:1914](../app/live.py)），云端默认是 `127.0.0.1`，手机上点不开。

**P2 · 帮助文本漏命令，且「关注」一词两义。** `/回听`、`/分享包`、`/妙记` 都存在，但 `_help_text()` 没列（[tools/feishu_bot.py:2212](../tools/feishu_bot.py)）；「关注 FDE」是关键词，网页里的「关注」是关注直播间，同一个词指两件事，手机用户很容易误解。

**P2 · 分享载体受限。** 机器人只能发文本/卡片/音频/文件，没有图片（[app/feishu.py:208](../app/feishu.py) 起），所以四套分享卡在手机上不可用；`/分享` 单条 ≤5 分钟，`/分享包` 长场次可能撞飞书文件大小上限（[docs/44 §7](44-cloud-feishu-bot.md)）。云端没有公网 reader，`/回听` 只能给「发 /分享」的提示。

## 4. 桌面端能否选择云端服务器采集？

**不能。** 证据链：

- 桌面壳每次都**自己拉起本机引擎**：选空闲端口、`LIVENOTES_HOST=127.0.0.1`、Job Object 随壳回收（[desktop/src-tauri/src/engine.rs:105](../desktop/src-tauri/src/engine.rs)、`:235`）。
- 主窗口注入的 `window.__LN_ENGINE__` 就是这个本机端口（[desktop/src-tauri/src/lib.rs:350](../desktop/src-tauri/src/lib.rs)），没有远端地址字段。
- 采集方式枚举只有 `browser / direct / external`（[app/settings.py:118](../app/settings.py)、`:145`），三个都是本机实现；桌面设置页也只列这三项（[desktop/dist/shell.html:475](../desktop/dist/shell.html)）。
- 全仓库没有「远端引擎地址 / token / 节点注册」配置；`LIVENOTES_ENGINE_EXE` 指的是本机可执行文件（[desktop/src-tauri/src/engine.rs:410](../desktop/src-tauri/src/engine.rs)）。
- 唯一能指向别处的组件是飞书机器人（`LIVENOTES_API`，[tools/feishu_bot.py:49](../tools/feishu_bot.py)），但桌面壳启动的是**本机**机器人，并把 `LIVENOTES_API` 固定为本机端口（[run.py:300](../run.py)）。

**为什么这不是加一个下拉框的事：** 桌面壳对引擎有生命周期所有权（启动、健康检查、退出回收、Job Object）。指向云端需要先拆掉这层所有权，再加鉴权、隧道/公网、音频回传与卡片链接策略。当前云端引擎只绑回环、无鉴权（[docs/43 §5](43-capture-only-mode.md)），直接暴露是安全问题。

**建议：** 短期明确「桌面不接云端」，在设置页写清楚「云端采集只能通过飞书操作」；如果确实需要桌面看云端，优先做**离线包导入**而不是远程引擎。

## 5. 回归审计：云端有没有破坏本地？

### 5.1 已经守住的

- `LIVENOTES_CAPTURE_ONLY` 默认 `0`（[app/config.py:24](../app/config.py)），桌面/网页默认走完整链路。
- 桌面 `capture_mode` 默认空 → `browser`（[run.py:203](../run.py)）；`browser` 时不拉外部采集代理（[run.py:216](../run.py)）。
- helpers 只在 `LIVENOTES_HELPERS=1` 时启动（[run.py:134](../run.py)），网页版行为不变。
- 仅采集支持逐场覆盖，不传就跟全局（[app/server.py:2447](../app/server.py)）；老库自动补 `sessions.capture_only` 列。
- 本机全量 `pytest`：**884 passed**（2026-11-26）；`test_capture_only.py`、`test_feishu_capture_only.py`、`test_offline_asr.py` 覆盖「仅采集不碰模型/工作池」「飞书文案」「增量补写」，`test_feishu_publish.py`、`test_cloud_chain.py` 覆盖发布幂等与云端整链。
- CI 在 Python 3.11/3.13 跑同一套 pytest，并检查网页分层与「不装实时依赖也能 import」。

### 5.2 回归网没盖住的地方

- `run.py` 的 helper 编排（`_capture_mode` / `_capture_agent_cmd` / `_watch_capture_mode`）没有测试引用；只有 `settings` 的枚举测试。
- 桌面壳 Rust（房间 watcher、采集模式读取、进程回收）不在 CI；`tests/test_desktop_shell.py` 是对 `shell.js/html` 的静态断言。
- `tools/ui_smoke.py` 不在 CI（需要 Chrome），前端白屏类回归只能手动跑。
- 「仅采集 + 离线补转写 + 飞书 /总结」的端到端用例已补上（`tests/test_cloud_chain.py`，2026-11-26）；磁盘满、机器人租约冲突、断流死链仍没有用例。
- `test_capture_watch.py` 在 CI 会 `importorskip("websockets")` 而整体跳过（`requirements-dev.txt` 不含 websockets），下播判定逻辑在 CI 实际没有跑。

### 5.3 已发现的具体回归风险

**P0 · 采集方式切换竞态（本机，新增的「改完立即生效」引入）。**
`run.py` 切换采集方式时，有房间在听就先不切（[run.py:222](../run.py)）；但桌面壳每 2 秒读一次新 prefs，切到 `browser` 后立刻开始自己接新房间（[desktop/src-tauri/src/rooms.rs:735](../desktop/src-tauri/src/rooms.rs)），而旧采集代理还活着，会接管任何 pending/starting/live 房间（[tools/capture_agent.py:1381](../tools/capture_agent.py)）。服务端按 `room_id` 复用已有会话（[app/server.py:2455](../app/server.py)），于是两个采集栈可能同时往同一会话推音频：多一个 WebView/Chrome、重复 PCM、时间轴错乱。反过来 `browser → external` 时，新房间会停在 pending：壳不接、代理又还没启动，直到旧房间全部结束。

**P1 · 云端断流预警死链。** `push_capture_lost` 用 `lan.base_url()` 拼 `/live?session=`（[app/live.py:1914](../app/live.py)）；云端默认回环，手机打不开。机器人自己的 `_live_hint` 有 `CAPTURE_ONLY` 分支，但这条引擎侧推送绕过了它。

**P1 · 离线补转写后的下游断链（2026-11-26 已修）。** 此前仅采集收尾不跑 `tasks.submit_finalize`（[app/live.py:749](../app/live.py)），离线补写完成后也只 `recluster + set_offline_asr`（[app/offline_asr.py:443](../app/offline_asr.py)）。`insights.after_finalize`、`note_ready`、`notes.index_session`（进而 `claims.rebuild_session`）都不会跑（[app/tasks.py:92](../app/tasks.py)）。结果：飞书 `/总结` 能出（它直接读库），但观点档案、主动提醒、笔记索引不会随云端场次积累。
现在补写完成后，离线进程通过 `POST /api/sessions/finalize`（`recluster=False`）让引擎排队收尾；状态存 `offline_asr.finalize_state`，失败按窗口重试。引擎侧还新增 `GET /api/jobs?job_id=` 供离线进程跟任务，以及 `/api/publish` 手动发布。整链由 `tests/test_cloud_chain.py` 覆盖。

**P2 · 仅采集的文案依赖机器人自己的环境变量。** `tools/feishu_bot.py` 在 import 时读 `CAPTURE_ONLY`（[tools/feishu_bot.py:38](../tools/feishu_bot.py)）。如果引擎是仅采集而机器人进程没带这个变量（或反之），它会给手机发 `127.0.0.1` 链接，或隐藏本来可用的入口。引擎已经在 `/api/live/info` 暴露 `capture_only`（[app/live.py:2621](../app/live.py)），机器人应该读它，而不是信自己的 env。

### 6.4 云端运维

| 缺陷 | 影响 | 建议 |
|---|---|---|
| 同一条飞书长连接没有租约 | 桌面 + 云端同时开，命令随机被一边吃掉 | R3 |

## 7. 制度建议

### R1 · 统一名词与产品模型（立即）

- 文档、设置页、机器人、代码注释统一为：**引擎 / 网页界面 / 飞书界面 / 桌面壳 / 采集节点**。
- 禁止再把「云端」称为「端」；「仅采集」统一叫「只录音」对用户说，「采集节点」对运维说。
- 验收：README、docs/43/44/45、设置页、`/help` 用词一致；新增一个 `docs/glossary.md` 或在本文件附录维护。

### R2 · 能力清单单一真相源（立即）

- 引擎新增 `GET /api/capabilities`（或扩 `/api/live/info`）：`capture_only`、`capture_modes`、`asr_realtime`、`offline_asr`、`public_base`、`llm_configured`、`disk_free`、`feishu_lease`、`host_profile`。
- 桌面设置、网页设置、机器人文案全部按它渲染/隐藏；**禁止**再用进程 env 推断产品状态。
- 验收：机器人不再 import `CAPTURE_ONLY`；把机器人 env 去掉后，云端文案仍正确。

### R3 · 飞书长连接租约（立即）

- 引擎维护 `feishu_lease`：谁持有、心跳、接管时间；桌面启动机器人前先查，云端持有则**拒绝启动并显式提示**（不是静默）。
- 提供「接管 / 释放」入口（桌面设置或 `/接管` 命令），把现在「改名 feishu.json / 设 LIVENOTES_NO_FEISHU」的手工制度变成系统状态。
- 验收：两端同时启动时，只有一端连上；另一端在 UI/日志里明确说「已被云端接管」。

### R4 · 数据主权与回流（下一迭代，需产品决策）

- 先定义云端场次的归宿：在节点保留 N 天 → 自动打包到飞书云空间 / 桌面可导入。
- 最小实现：`/api/export/bundle?session=`（录音+字幕+总结+meta）+ 桌面「导入场次」；或复用 `share.build_package` 自动推送。
- 验收：云端录一场，桌面能导入并在笔记库/周报里看到；不需要 SSH。

### R5 · 房间归属与采集互斥（立即）

- 房间增加 `capture_owner`（desktop / agent:per_room / agent:shared / direct / cloud），由创建房间的一方写入，别人不得接管。
- 切换采集方式时：新房间进入显式 `waiting_switch` 状态，UI 说明原因；旧采集栈只处理自己 owner 的房间。
- 验收：在「有房间在听」时双向切换 10 次，不出现双采集、不出现永久 pending（补一个 run.py + rooms.rs 的轻量集成测试）。

### R6 · 手机端最小完整体验（下一迭代）

定义为 8 项必须可用：开录、状态、停止、重试、回听片段、总结、**补名**、**关注/自动记录**。
- 先做补名与关注：它们决定「知识产品」是否成立。
- 验收：只用飞书完成「贴链接 → 补名 → 总结 → 加入关注 → 下场自动录」全流程。

### R7 · 回归制度（立即）

- 任何碰 `capture_only` / 采集方式 / 机器人文案的改动，必须同时补三类测试：引擎模式、机器人文案、编排层。
- 把 `run.py` helper 编排纳入单测（用假 Popen）；把 `ui_smoke` 与 `test_capture_watch` 的依赖纳入 CI（或显式标注为「手工验收项」）。
- 验收：CI 能挡住「切模式双采集」「云端死链」这两类问题。

### R8 · 云端可观测（下一迭代）

- 节点心跳、磁盘水位、补转写积压、最后一块音频时间，推送到飞书（或 `/状态` 卡片）。
- 验收：拔掉节点电源 5 分钟后，手机能收到「节点失联」而不是沉默。

### R9 · 文案与帮助治理（立即）

- `/help` 从命令表自动生成；所有用户可见状态用同一套词（只录音/补转写/采集节点）。
- 「关注」拆成「关键词」与「关注直播间」两个词。
- 验收：新增命令时必须改命令表，否则帮助不更新就会被测试抓到。

### R10 · 收敛采集实现（中期）

- 现在有桌面 WebView2 采集、外部 Chrome 采集代理、ffmpeg 直取三套。长期应收敛到同一「房间采集协议 + 状态机」，否则每加一种采集方式都会乘一遍测试矩阵。
- 验收：三种采集实现共用 `pending → starting → live → stopped` 的同一套 owner/lease 契约。
