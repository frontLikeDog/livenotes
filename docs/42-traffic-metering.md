# 42 · 采集流量计量

> 面向：产品、实现
> 依据：[02 · 三种采集底座](02-live-tab-capture.md#三种采集底座)、[13 · 直取抖音流](13-direct-capture-spike.md)
> 代码：`app/traffic.py`、`tools/capture_agent.py`、`tools/direct_capture.py`
> 结论时间：2026-11-18

## 1. 量的是什么

| 口径 | 含义 | 页面位置 |
|---|---|---|
| 平台下行 | 采集端为了拿到声音，从抖音 CDN 实际收到的字节 | 房间详情「平台下行 / 折合每小时」，列表 `↓ MB/h` |
| 音频上行 | 采集端推给本机服务的 PCM（16 kHz 单声道 s16le） | 房间详情「音频上行」 |
| 音频占比 | 音频上行 ÷ 平台下行 | 房间详情「音频占比」 |

三个数字都按**本次采集从开始到现在的累计值**算速率，不是瞬时采样。

音频契约三种采集方式完全一样：8192 字节 / 256 ms = 32 KB/s = 256 kbps ≈ **115 MB/h**。
所以「上行」只取决于录了多久，「下行」才取决于采集方式。

> 同机运行时音频走 `127.0.0.1`，**不占宽带出口**；只有把采集端部署到另一台机器
> 或云端时，这 115 MB/h 才会变成真正的网络上联。飞书推送、云空间归档的流量
> 不计入这里——那不是采集流量，量级也小几个数量级。

## 2. 三种采集方式的来源与精度

| 模式 | 平台下行怎么来 | `source` |
|---|---|---|
| `per_room`（独立浏览器） | 挂在该房间页面的 CDP `Network` 事件上：`dataReceived.dataLength` 累计，`loadingFinished.encodedDataLength` 补差额 | `cdp`（实测） |
| `shared`（一个 Edge 多标签） | 同上，按房间各自的页面 WebSocket 分别计数 | `cdp`（实测） |
| `direct` + 设置页「精确流量计量」（或 `LIVENOTES_TRAFFIC_PROXY=1`） | ffmpeg 改从本机回环计数代理拉流，代理按实际转发的字节累计 | `proxy`（实测） |
| `direct`（默认） | 解析 ffmpeg 打开的流的码率；拿不到码率就按分辨率查表（1080p≈6 Mbps、720p≈3 Mbps） | `estimate`（估算） |

UI 上的「流量计量」会直接标出来源：

- `实测 · 浏览器 Network` / `实测 · 计数代理`
- `估算 · 码率/分辨率`
- `不可用`（计量失败，不影响录音）

优先级：**实测 > 估算**。CDP/代理一旦开始计数，后来 ffmpeg 打印的码率不会把来源
盖回 `estimate`；实测通道断掉时（CDP WebSocket 退出、代理停止）才降级回估算，
估算也没有就标 `unavailable`。计量任何一步失败都只影响这几个数字，不影响采集、
识别和现有的看门狗。

## 3. 直取：画质与精确计量

直取只取声音，下载的视频会被 ffmpeg 丢掉。所以**默认从最低可用画质拉流**
（`LD2 → LD1 → SD2 → SD1 → HD1 → FULL_HD1 → ORIGION`），语音厅通常只有一路
音频流，画质设置不影响声音。在「设置 → 采集 → 直取画质」可切到最高画质，
改完对**下一路解析**生效；正在听的路要等重连才换档。

流量计量默认按码率估算，因为让所有流量都绕一层 Python 代理会多一次内存拷贝
和线程开销。需要对外报账、或要验证估算准不准时，在「设置 → 采集 → 精确流量
计量」打开（或临时设 `LIVENOTES_TRAFFIC_PROXY=1`，`=0` 可强制关闭）：

```powershell
$env:LIVENOTES_TRAFFIC_PROXY = "1"
```

代理只监听 `127.0.0.1`、路径带随机 token，不会把端口暴露到局域网；上游
403/404 会原样透传给 ffmpeg，断流判定不受影响。精确计量对**下一次启动
ffmpeg** 生效，已经连着的流不会中途换路径。

## 4. 怎么读

- **桌面壳 · 收听页右栏「这一路」**：平台下行（Mbps + 折合每小时）、音频上行、
  计量来源；指标跟「最后一块」放在一起，因为它描述的是这一路当前的健康度。
- **桌面壳底部状态栏**：所有在听房间的合计 `↓ GB/h · ↑ MB/h`，一眼看总量。
- **网页版房间详情**：平台下行（字节 + Mbps）、折合每小时、音频上行、音频占比、来源。
- **网页版房间列表**：有数据时显示 `↓ xxx MB/h`，方便一眼看出哪一路在烧流量。
- **`GET /api/traffic`**：

```json
{
  "generated_at": "2026-11-18T20:00:00+08:00",
  "rooms": [{"id": "rm1", "alive": true, "age_s": 2.1,
             "name": "…", "engine": "direct", "state": "live",
             "platform_bytes": 123456789, "platform_mb_per_hour": 1800.0,
             "audio_bytes": 8192000, "audio_kbps": 256.0, "source": "proxy"}],
  "totals": {"rooms": 1, "platform_bytes": 123456789, "audio_bytes": 8192000,
             "platform_mb_per_hour": 1800.0, "audio_mb_per_hour": 115.2}
}
```

数据跟着 `/api/capture/status` 心跳一起上报（约 1 秒一拍），没有新增轮询请求；
`traffic` 只保留白名单字段，采集端上报脏数据时整块丢弃，不会打挂心跳。

## 5. 已知边界

1. **CDP 计的是整个页面**，包括直播间页面的接口、聊天和静态资源，不只是视频流。
   对「这一路采集带来了多少流量」来说这是正确的口径，但会比纯视频码率略高。
2. **直取默认取最低可用清晰度**（省流），浏览器播放器会自适应降档。手动切到
   「最高画质」后，同一直播间可能比浏览器更费下行；这是画质设置的结果，不是
   计量算错。
3. **估算按「码率 × 持续时长」分段累计**：直播中途换清晰度时，旧码率先结算，
   新码率从换档时刻往后算，不会拿最新码率重算整场。但 VBR、广告插播仍会让
   估算偏离实测；要精确数字就打开「精确流量计量」。
4. **估算不是实测**：码率来自 ffmpeg 打开流时打印的 Input 行，平台实际下发
   多少只有 CDP/计数代理知道。UI 上「估算 · 码率/分辨率」就是在提醒这一点。
5. **只在采集运行期间累计**：代理重启、房间重新拉起会从 0 开始；跨场汇总看
   `/api/traffic` 的当前值，历史账应落到后续的录制节点/账单表，不在本模块里。
