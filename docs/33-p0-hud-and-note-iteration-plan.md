## 0. 一页纸

### 0.1 这次要交付什么

**A. 极简记录 HUD + 托盘 + 通知**

用户点「开始记录」后，界面从「监控台」切成一张安静的记录卡：大计时、几位说话人、最近几句字幕、暂停 / 标记 / 结束。关掉窗口后录音继续，托盘能看到「正在记录 00:42:10」；断流、恢复、生成完成、生成失败都会收到一条人话通知，点通知回到对应界面。

**B. 笔记页 v1**

一场直播的完成态不再是「工作台 + 右侧总结侧栏」，而是一篇独立的笔记：标题、一句话总结、3–5 个带原话和时间码的要点、3 段值得回听的高光、谁说了什么、导出。每个要点和时间码都能点开原声；没有原话出处的要点不上页面。

### 0.2 不做什么（本迭代）

- 新首页、首次向导、样本笔记、预检卡、5 分钟预览（P0 其余项，单独排）
- 笔记库卡片流、全库搜索、关注 / 自动记录、周报、分享卡片（P1）
- 多路 / 监控墙 / 人物档案 / 文件中心的信息架构大改（只做最小衔接）
- 移动端、云同步、账号体系
- 新的 AI 能力（不新增模型任务，只把已有总结 / 高光 / 说话人组装成笔记）

### 0.3 工作量与排期

按 1 名熟悉本仓库的高级工程师估算：

| 工作流 | 人日 |
|---|---|
| A. HUD + 托盘 + 通知 | 13–17 |
| B. 笔记页 v1（含生成链路） | 15–19 |
| 联调、验收、文案、狗粮 | 4–6 |
| **合计** | **32–42 人日** |

- **2 人并行**（1 人引擎 / 1 人桌面壳 + 前端）：**4 周左右**，每周一个有价值的可演示切片。
- **1 人顺序做**：**7–8 周**。
- 如果必须先出结果，可砍成 2 周切片：HUD + 托盘 + 「笔记已生成」通知 + 笔记页只读版（不含通知中心、通知设置、重新生成、过期提示）。见 §7.3。

**对 32 的进度预期做个校准**：32 里 P0 九项写着 4–6 周，但仅这两项（记录卡 + 托盘改造 + 通知链路 + 笔记页）在 2 人并行下就要 3–4 周。建议把这两项当作 P0 的第一个 release 主体，其余七项（首页、向导、预检、5 分钟预览、安装更新、种子测试等）另排；不要在同一周期里既做信息架构大改又做桌面壳和笔记页。

### 0.4 验收口径

- 干净 Windows 11：开始记录 → 关窗 → 托盘可见计时 → 断流 45 秒内收到通知 → 结束 → 笔记生成通知 → 点开笔记，全流程不需要命令行。
- 20 分钟以上的真实直播：笔记页同时出现总结、≥3 个带原话和时间码的要点、3 段可播放高光、说话人、导出；截图发给没看过这场直播的人，对方能说出「这场讲了什么」。
- 没有配置 LLM 也能生成规则版笔记；LLM 失败不丢数据，页面给人话和重试按钮。
- HUD / 托盘 / 通知里不出现「采集、断流、ASR、聚类、token、场次」等工程词。

## 1. 为什么是这两件事

用户真正会做的动作只有四个：**开始记录 → 离开 → 收到结果 → 回来读**。

现在的产品在这四步里各断了一次：

| 用户动作 | 现在发生什么 | 断点 |
|---|---|---|
| 开始记录 | 进入「收听」工作台：左侧房间列表、中间信号 / 页面 / 标注舞台、右侧实时字幕，还有未转写分钟、重叠秒数、采集阶段码 | 用户以为自己在看监控，不知道该盯哪里 |
| 离开 | 关窗会收进托盘，但托盘菜单是诊断向的；没有「正在记录多久」的持续感知 | 不敢关，或者关了之后不知道还在不在录 |
| 收到结果 | 只有飞书推送；本地没有通知 | 录完不回来看，笔记等于没生成 |
| 回来读 | 打开工作台：筛选器 + 时间轴 + 逐字稿表格 + 右侧 AI 总结，要点混在侧栏里，高光是另一个页面，导出只有逐字稿 | 没有一个「一篇笔记」的完成态 |

这两项一起做，才能把「敢离开 → 有通知 → 有东西读」串起来。只做笔记页，用户录完不知道；只做 HUD，录完没东西看。

## 2. 目标、指标与设计原则

### 2.1 目标

1. **录的时候不用盯**：关掉窗口也知道在录、录了多久、有没有出事。
2. **出事有人管**：断流、静音、引擎异常、磁盘不足，用户先于「发现少录两小时」知道。
3. **录完马上有产物**：结束记录后自动生成笔记，不需要再点「AI 分析」。
4. **笔记是证据**：每个要点、每段高光都有原话、说话人和时间码，点一下能听到原声。
5. **不配外部账号也能用**：规则版总结 / 高光兜底，飞书和 LLM 都是可选增强。

### 2.2 指标（先埋点，不追求统计显著性）

| 指标 | 定义 | 目标 |
|---|---|---|
| 端到端完成率 | 开始记录 → 生成出笔记 | ≥ 90%（狗粮） |
| 结束到笔记可读 | 点「结束」到笔记页数据 ready，P95 | ≤ 90 秒（20 分钟场，LLM 正常） |
| 关闭窗口后继续录 | 关窗后 5 分钟仍有音频块、有定稿 | 100% |
| 断流发现时延 | 音频中断到用户收到通知 | ≤ 45 秒 |
| 笔记打开率 | 生成完成的通知 / 页面被打开 | ≥ 60%（种子用户） |
| 高光试听率 | 打开笔记的人里点过至少一段高光 | ≥ 30% |
| 导出率 | 打开笔记的人里导出 / 复制过 | ≥ 10% |
| 通知重复率 | 同一事件重复通知 | 0 |

### 2.3 设计原则

1. **记录中只回答三个问题**：在录吗？录了多久？出事了吗？其他都收起来。
2. **完成态只有一个主角**：笔记。逐字稿是证据，不是首页。
3. **通知必须可行动**：每条通知要么能打开对应页面，要么能重试；纯告知型通知默认少发。
4. **工程词不上界面**：采集 → 录音；断流 → 听不到声音；聚类标签 → 说话人；token → 隐藏；场次 → 这场直播。
5. **失败要给人话和下一步**：不弹堆栈、不显示阶段码；错误文案统一由一张映射表生成。

## 3. 方案 A：极简记录 HUD + 托盘 + 通知

### 3.0 现状 → 目标

| 能力 | 现状 | 目标 |
|---|---|---|
| 记录中界面 | 「收听」工作台：房间列表 + 信号 / 页面 / 标注舞台 + 实时字幕 + 工程指标 | 一张记录卡：计时、说话人、最近字幕、暂停 / 标记 / 结束 |
| 关窗之后 | 已能收进托盘继续录，但托盘不显示录了多久，用户不敢确信 | 托盘 tooltip / 菜单持续显示计时与状态 |
| 托盘 | 诊断向菜单：诊断包、日志、停止全部、工作区、浏览器 | 录音向菜单：暂停 / 标记 / 结束 / 最近笔记；诊断折叠进「检查问题」 |
| 通知 | 只有飞书推送；本地无通知 | Windows toast + 应用内通知中心 + 分类开关 |
| 断流感知 | 引擎更新房间提示，壳变警告图标；用户不主动看就不知道 | 45 秒内 toast + 记录卡人话提示 + 恢复通知 |
| 错误文案 | 阶段码 / ASR 超时 / 引擎退出等工程词 | 统一映射成人话 + 下一步按钮 |

### 3.1 用户流程

```
粘贴链接 / 选择房间
        │
        ▼
   ┌─────────────┐   关窗 / 最小化    ┌──────────────┐
   │  记录卡 HUD  │ ────────────────▶ │    托盘       │
   │ 计时 / 字幕  │ ◀──────────────── │ 计时 / 菜单   │
   └──────┬──────┘    点托盘打开       └──────┬───────┘
          │ 结束并生成笔记                     │ 暂停 / 标记 / 结束
          ▼                                   │
   ┌─────────────┐   完成 / 失败 / 断流       │
   │  收尾进度卡  │ ────────────────▶ 通知 ───┘
   └──────┬──────┘
          ▼
       笔记页（方案 B）
```

### 3.2 HUD 的形态：壳内「记录卡」，不是独立悬浮窗

**决策建议：v1 不做独立的置顶小窗。** 记录卡作为桌面壳的一个视图存在，与托盘配合：

- 关窗 / 最小化 = 收进托盘，录音继续（现有能力，保留）。
- 记录卡本身保持极简；用户想看直播画面再切「多路视图」。
- 独立置顶小窗（always-on-top pill）放 v1.1；它需要额外的窗口生命周期、DPI、焦点和任务栏行为，收益不如先把记录卡做对。
- 网页版不要求同款记录卡：网页版继续用现有实时监听面板；记录卡是桌面客户端的能力，先把桌面第一次使用做成立。

这样也符合 [32](32-desktop-product-polish.md) §3.3 的描述：记录中是一张安静的记录卡，主按钮是「结束并生成笔记」。

### 3.3 记录卡界面

```
┌──────────────────────────────────────────────────────────────┐
│  ● 正在记录                                    [—] [×]       │  ← 壳顶栏保留窗口控制
│                                                              │
│                       00:42:10                               │  ← 大计时，用音频时长，不用墙钟
│              2 位说话人 · 已转写 1,284 句                      │
│                                                              │
│      [⏸ 暂停]      [📍 标记此刻]        [结束并生成笔记]        │
│                                                              │
│  最近在说                                                     │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 主播 00:42:03                                           │  │
│  │ 所以这个品类的核心其实是复购，不是拉新……                 │  │
│  ├────────────────────────────────────────────────────────┤  │
│  │ 嘉宾 00:41:58                                           │  │
│  │ 对，我们上个月的数据也是这样……                           │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  关掉窗口也会继续记录，音频只存本机                             │
└──────────────────────────────────────────────────────────────┘
```

模块与规则：

| 模块 | 规则 |
|---|---|
| 状态行 | 圆点 + 人话状态：正在记录 / 已暂停 / 听不到声音 / 正在收尾；右侧只有「最小化到托盘」和关闭 |
| 计时 | 取 `/api/live/status` 的 `elapsed`（音频累计，暂停时自然不走），每秒刷新；不要用 `Date.now()` 算，否则暂停时会继续涨 |
| 统计行 | `N 位说话人 · 已转写 M 句`；只在记录中显示，不显示未转写分钟、重叠秒数、token、队列深度 |
| 字幕 | 最近 6–8 句定稿，说话人颜色 + 名字 + 时间码；新句从底部进入；不做表格、筛选、分类 |
| 主操作 | 「结束并生成笔记」是唯一主按钮；点击后二次确认「结束这场记录？」（[结束并生成笔记] [继续记录]） |
| 次操作 | 暂停 / 继续、标记此刻（写 `marks`，toast「已标记 00:42:31」）、看画面（切到现有收听视图的「页面」舞台，不新开窗口；没有可显示直播页时隐藏） |
| 打点 | 折叠显示最近 3 个标记；不在记录卡里编辑 |
| 安心条 | 固定一行：关掉窗口也会继续记录；音频只存本机 |
| 多路 | v1 只把「恰好 1 路在录」做成记录卡；≥2 路时恢复现有「收听」多路视图，记录卡顶部显示「2 路录制中 · 切换到多路」 |

**明确从记录卡拿掉**：波形画布、采集阶段、房间列表、筛选、分类标签、重叠提示、token、说话人聚类编号、监控墙入口。

### 3.4 HUD 状态机

| 状态 | 触发 | 界面 | 托盘 / 通知 |
|---|---|---|---|
| 启动中 | 点开始记录后 | 「正在打开直播间…」「正在连接声音…」+ 取消 | 托盘「正在启动」 |
| 记录中 | 首块音频到达 / 有定稿 | 计时、字幕、暂停 / 标记 / 结束 | 托盘显示计时 |
| 已暂停 | 点暂停 | 计时变灰 + 「暂停中，这段不会被记录」+ 继续 | 托盘「已暂停」；不通知 |
| 安静 | `idle_s` > 30s（没人说话） | 顶部提示「已经 N 秒没检测到人声，确认直播还在说话」+ 看画面 | 不通知（可能只是冷场） |
| 断流 | `last_chunk_ago_s` > 30s | 红色提示「听不到声音了（连接断开 N 秒）」+ [重新连接] [结束并保存] | 托盘警告图标 + 一次通知 |
| 直播结束 | 引擎看门狗判定下播 | 「直播可能已经结束了」+ [生成笔记] | 通知一次 |
| 收尾中 | 点结束后 | 三步进度：保存录音 / 分人 / 生成笔记；「可以关掉窗口，完成后通知你」+ [后台进行] | 不通知，直到完成 |
| 生成失败 | 笔记任务失败 | 「笔记没生成成功：<人话>」+ [重试] [先看原文] | 失败通知 |
| 完成 | 笔记 ready | 「笔记已生成」+ [打开笔记] [再记一场] | 完成通知 |

### 3.5 收尾进度卡

复用现有 `workflow.js` 的收尾状态机，但收敛成三步、全部说人话：

1. **保存录音** —— 音频和逐字稿落盘（不可跳过的真实步骤）
2. **整理说话人** —— 全场重新分人
3. **生成笔记** —— 总结 + 高光

规则：

- 进度卡出现后，用户可以点「后台进行」收起，继续用别的页面；**不要锁死整个应用**（现有 `setLiveLocked` 的行为在新记录卡里只锁记录卡，不锁全壳）。
- 完成时如果用户还停在进度卡，直接切到笔记页；否则发通知。
- 失败时保留「先看原文」兜底，绝不出现「录音没了」的错觉。

### 3.6 托盘

**当前现状**：托盘已有状态项、诊断导出、打开日志、显示主窗口、停止全部录音、应用内浏览器、收听工作区、在浏览器中打开、退出（[lib.rs](../desktop/src-tauri/src/lib.rs) `setup_tray`）；关窗收进托盘已实现（`on_window_event`）；断流会让托盘变警告图标（[diag.rs](../desktop/src-tauri/src/diag.rs)）。**它是一套运维菜单，不是一套录音菜单。**

**改成**：

```
● 正在记录 00:42:10 · 2 位说话人     ← 状态项，只显示，不响应点击
打开记录卡
────────────────────────
暂停记录
标记此刻
结束并生成笔记…
────────────────────────
打开最近笔记
检查问题…            ← 诊断页 / 导出诊断包 / 日志都收进这里
────────────────────────
退出 LiveNotes
```

空闲时：

```
○ 未在记录
打开收听页
打开最近笔记
检查问题…
────────────────────────
退出 LiveNotes
```

规则：

| 项 | 行为 |
|---|---|
| 图标 | 三态：空闲、记录中（带红点 / 录音标记）、异常（现有警告图标）；记录中的 tooltip 带计时 |
| Tooltip | 空闲「LiveNotes · 未在记录」；记录中「正在记录 00:42:10 · 2 位说话人」；多路「正在记录 2 路 · 最近 00:42:10」；异常「1 路断流 · 点此查看」 |
| 左键单击 | 显示主窗口；记录中直接落在记录卡 |
| 双击 | 同左键（保留现有） |
| 暂停 / 标记 / 结束 | 通过 `shell_tray_action` 事件交给壳页调 `/api/live/*`；窗口隐藏时壳页仍然存活，事件可用。壳页不在时直接 HTTP 调引擎兜底 |
| 结束并生成笔记 | 需要确认，避免误点结束一场两小时的直播 |
| 打开最近笔记 | 直接进最近一场有笔记的场次；没有则进收听页空态 |
| 退出 | 有录音时弹确认：「还在记录，退出会停止录音」[结束并保存后退出] [仍然退出] [取消] |
| 关闭窗口 | 有录音时一定收进托盘（不询问）；空闲时按现有设置 `prefCloseAction`（托盘 / 退出），默认托盘 |
| 菜单刷新 | 跟随现有诊断轮询（默认 3 秒，tooltip 秒数允许 3 秒一跳）；空闲时可降到 5 秒；不要为此新增轮询源 |

**多路**：v1 菜单只针对「最近开始的一路」；显示「还有 1 路」并给「切换到多路视图」。真正多路批量操作留给 P1。

### 3.7 通知

#### 3.7.1 事件矩阵

| 事件 | 触发点 | 默认 | 标题 / 正文 | 点击 | 去重 |
|---|---|---|---|---|---|
| 断流 | 引擎看门狗检测到 `last_chunk_ago_s > 30` | 开 | **听不到声音了** · 《标题》已 30 秒没有收到音频，可能断流了。 | 打开记录卡 | 每个断流 episode 一次 |
| 恢复 | 断流后音频块恢复 | 开 | **声音恢复了** · 《标题》继续在录。 | 打开记录卡 | 每次恢复一次 |
| 连续静音 | 全零音频超过预警阈值（默认 2 分钟） | 开 | **直播可能静音了** · 《标题》已经连续 N 分钟没有声音。 | 打开记录卡 | 每次静音 episode 一次 |
| 直播结束 | 看门狗判定下播 / 流结束 | 开 | **直播可能结束了** · 已停止记录，正在生成笔记。 | 打开收尾 / 笔记 | 每场一次 |
| 笔记完成 | 笔记任务成功 | 开 | **《标题》的笔记已生成** · N 个要点 · N 段高光 | 打开笔记 | 每场一次 |
| 笔记失败 | 笔记任务失败 | 开 | **笔记没生成成功** · <人话原因>，录音和逐字稿都在。 | 打开笔记 / 重试 | 每场每任务一次 |
| 引擎异常 | 壳检测到引擎退出 / 重启 | 开 | **记录程序断开了** · 正在尝试恢复；恢复不了可以导出诊断包。 | 检查问题 | 每次异常一次 |
| 磁盘不足 | 启动 / 收尾时剩余 < 2GB | 开 | **磁盘空间不足** · 还剩 X GB，长直播可能存不下。 | 存储设置 | 每天一次 |
| 首次收起提示 | 第一次关窗进托盘 | 开 | **已收进托盘，录音继续** · 右键托盘图标可以暂停或结束。 | 打开记录卡 | 终身一次 |
| 预览就绪 | 5 分钟预览（后续迭代） | 预留 | —— | 打开预览笔记 | 每场一次 |

**不做**：开始记录也发一条「开始录音了」——用户刚点完，没必要。

#### 3.7.2 展示规则

- 主窗口在前台且聚焦：用应用内 toast + 通知中心红点，不弹 Windows 系统通知，避免打扰。
- 主窗口隐藏 / 最小化 / 不在前台：系统通知（Windows toast）。
- 系统通知被用户关闭 / 失败：应用内通知中心仍然保留，不丢事件。
- 通知点击：先 `show_main`，再把壳切到目标视图（记录卡 / 笔记 / 检查问题）。
- 冷却：同类型同场次 10 分钟内不重复；断流按 episode 去重，恢复后重新计。

#### 3.7.3 通知中心（最小版）

壳顶栏加一个铃铛：未读数、按时间倒序列出最近 50 条、全部已读、单条点击跳转。不做分组、筛选、分类 tab。

#### 3.7.4 通知设置

在设置抽屉里加一组「通知」：

- 录音异常（断流 / 静音 / 引擎异常）：默认开
- 笔记生成：默认开
- 系统提示（托盘提示 / 磁盘）：默认开
- 桌面通知总开关：默认开；关掉后仍保留应用内通知中心

存储放在引擎 `settings` 的 prefs 里，壳和引擎都能读；不要只存在 WebView 的 localStorage，否则重装 / 换壳就丢。

| 设置 | `app/settings.py` prefs + 设置抽屉 | 通知分类开关 |

**为什么通知走引擎而不是壳**：断流、静音、笔记完成都发生在引擎侧；壳可能被隐藏甚至重载。把事件写进引擎的通知队列，既能保证不丢，也能让网页版 / 手机回放页以后复用；壳只做「取件 + 展示」。

**例外：壳侧事件**。引擎崩溃、托盘首次提示这类事件引擎自己写不了，由壳生成一条本地通知（`id` 用 `local:` 前缀），直接进通知中心并弹 toast；不写引擎表，避免引擎重启后重复。应用内通知中心把「引擎通知」和「壳本地通知」按时间合并展示即可。

#### 3.9.1 通知表

```sql
CREATE TABLE IF NOT EXISTS notifications (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id  TEXT DEFAULT '',
  type        TEXT NOT NULL,          -- 引擎侧：stream_stalled | stream_recovered | silent | live_ended
                                      --        | note_ready | note_failed | disk_low
                                      -- 壳侧本地通知不写本表：engine_error | tray_hint
  title       TEXT NOT NULL,
  body        TEXT NOT NULL DEFAULT '',
  action_json TEXT NOT NULL DEFAULT '{}',  -- {view, session_id, t, run_id}
  dedupe_key  TEXT NOT NULL DEFAULT '',    -- type + session_id + episode
  created_at  TEXT NOT NULL,
  read_at     TEXT,
  delivered_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_notifications_created ON notifications(created_at DESC);
CREATE UNIQUE INDEX IF NOT EXISTS idx_notifications_dedupe ON notifications(dedupe_key)
  WHERE dedupe_key <> '';
```

- `dedupe_key` 用唯一索引保证不重复；断流 episode 用一个自增 / 时间窗 key。
- `delivered_at` 由壳回写；重装 / 重启后不会把旧通知再弹一遍，但通知中心仍能看到未读。
- 通知正文只放标题和简短原因，**不放逐字稿原文**，避免锁屏泄露内容。

#### 3.9.2 托盘动作协议

```json
// Rust -> shell
{ "action": "hud" | "pause" | "resume" | "mark" | "finish" | "recent_note" | "quit_confirm" }
```

壳收到后调对应 `/api/live/*`；成功后刷新托盘状态（Rust 侧下一轮轮询会自然更新）。`quit_confirm` 由壳弹确认框，用户确认后调用 Tauri 的退出命令。

### 4.4 五个模块的详细规格

#### 4.4.1 标题与元信息

| 元素 | 规则 |
|---|---|
| 标题 | 沿用现有 AI 标题 / 用户改名；点击就地编辑，Enter 保存，Esc 取消；调用 `/api/sessions/rename` |
| 元信息 | `日期 · 时长 · N 位说话人 · 录音方式（可选）`；不显示场次 ID、采集阶段 |
| 播放整场 | 有音频时显示；没有音频（按保留期清理）显示「录音已清理」并禁用 |
| 生成信息 | `AI 生成` 或 `本地规则生成`；`更新于 HH:MM`；AI 失败后显示「本地规则」小标签，不弹窗 |
| 查看原文 | 跳工作台 `/?session=<id>`，保留时间码定位 |

#### 4.4.2 一句话总结

- 直接展示 `summary.overview`，3–5 行内。
- 没有总结时：显示「还没有生成笔记」+ [生成笔记]；如果正在生成，显示步骤进度。
- 总结为空但逐字稿很多：说明模型不可用或内容不适合总结；给「用本地规则生成」按钮。

#### 4.4.3 要点

- 取 `summary.points` 按 `importance / utterance_count` 排序，最多 5 条，最少 3 条（不足 3 条就按实际数量）。
- 每条：序号、标题（≤20 字）、gist（≤100 字）、1–2 条证据。
- 证据展示：原话（≤90 字）+ 说话人 + 时间码 + 播放按钮；点击时间码用 `/api/audio?session_id&t_start&t_end` 播这一句。
- 超过 5 条时底部「查看全部要点」展开剩余；不要横向滚动。
- 证据来自 `analysis.py` 的 `evidence` 字段（已包含 `id / t_start / t_end / timecode / speaker_label / quote / audio_url`），前端不要自己猜。

#### 4.4.4 高光

- 取 `highlights` 表按 score 排序的前 3 段；现有 `_mix` 已保证信息型和情绪型都有配额。
- 卡片字段：时间码（`peak_t`）、标签 / 钩子（`tag` / `hook`）、为什么（`why`）、峰值原话（`quote` 优先，其次 `text`）、说话人、时长。
- 「播放这段」播放 `t_start..t_end` 的音频窗口；没有音频时禁用。
- 底部「查看全部高光」跳 `/highlights?session_id=<id>`。
- 没有高光时：不要显示空模块；显示「这场没有明显高光，先看要点」或自动构建中。
- 高光构建属于笔记生成的一部分（见 §4.5），用户不需要单独点「计算高光」。

#### 4.4.5 说话人

- 数据来自 `store.speaker_totals`：名字、发言时长、占比、句数；未确认的显示「未确认」小标签。
- 每位说话人给 1–2 条代表原话：优先 `substantive` 类、长度 15–80 字、置信度高、时间上分散；没有合适的就不放。
- 行内「改名」调用 `/api/speakers/rename`，刷新后笔记里的说话人名同步变化。
- 少于 2 位说话人：不显示整节，只在标题下写「1 位说话人」。
- 「去确认身份」跳标注模式 / 人物页；不改名也不阻塞笔记。

#### 4.4.6 导出

| 格式 | 内容 | 入口 |
|---|---|---|
| 笔记 Markdown（默认） | 标题、元信息、总结、要点 + 原话 + 时间码、高光、说话人；文末附可折叠全文稿 | 导出 ▾ → 笔记 Markdown |
| 逐字稿 Markdown | 现有 `export.to_markdown`，保持不变 | 导出 ▾ → 逐字稿 |
| SRT | 现有字幕导出 | 导出 ▾ → 字幕 SRT |
| 复制笔记 | 复制笔记 Markdown（不含全文稿）到剪贴板 | 主按钮旁「复制」 |

- 笔记 Markdown 必须可被飞书文档 / Obsidian / Notion 直接粘贴后保持结构。
- 文件名：`<标题>-笔记-YYYYMMDD.md`；标题为空时用日期。
- 分享卡片（竖版图 + 二维码）**不在本迭代**；导出菜单里不要放「即将上线」占位，避免噪音。

### 4.5 生成链路：把「总结」升级成「生成笔记」

**现状**：`live.stop()` 之后 `tasks.submit_finalize` 自动排队做重聚类 + 整场总结（[live.py](../app/live.py) `_auto_finalize` / [tasks.py](../app/tasks.py)）。**高光不会自动落库**：只有飞书 digest 里调用 `score_session`（不写库），或者用户手动调 `/api/highlights/build`。

**改成**：收尾任务升级为「生成笔记」，用一张独立的 `notes` 表记录状态，**不挤占 `analysis_runs` / `analysis_job` 的互斥锁**——否则用户在生成笔记期间点「AI 分析」，会被 `get_active_run` 误判成「已有任务在跑」而直接返回笔记任务。`analysis_runs` 继续只服务原来的分析面板。

```
结束记录
  → 保存录音、逐字稿落盘（stop 同步完成）
  → 整理说话人（全场重聚类）
  → 生成总结（整场，auto：内容够才用 LLM）
  → 构建高光（limit=3；有 LLM 时让模型写钩子/原声，没有则规则版）
  → 标记笔记 ready + 发通知
```

规则：

| 问题 | 决策 |
|---|---|
| 是否自动生成 | **是**。用户点「结束并生成笔记」后不需要再点「AI 分析」；手动重新生成放在笔记页 |
| 失败怎么办 | 分阶段：总结失败但高光成功 → `partial`，页面显示基础笔记 + 「重试 AI」；全部失败 → `failed`，录音和逐字稿仍在 |
| LLM 未配置 | 总结走本地抽取式，高光走规则版，笔记照常生成；页面标注「本地规则」 |
| 成本 | 复用 `/api/summarize/estimate`；重新生成前显示「这场大约花 X 元」；自动生成沿用现有 token 预算 / 调度器 |
| 高光用不用 LLM | 跟随 AI 设置：`auto` / `llm` 且已配置 Key 时让模型写钩子和挑原声；否则规则版。不要让「没配 LLM」变成「没有高光」 |
| 幂等 | 同一场已有 running 任务时返回现有 run id，不重复排队；已有笔记且输入未变时直接复用缓存 |
| 顺序 | 高光在总结之后构建：总结可能触发重聚类，高光要用重聚类后的说话人名 |
| 飞书 digest | 保持现有行为；高光落库后 digest 的幂等不受影响（`pushed_peaks` 仍按峰值去重） |
| 长直播 | 总结沿用现有分层抽样；高光 O(n) 打分；页面先展示已有部分，不要整页转圈 |
| 短场 / 无实质内容 | 不调模型：沿用 `_worth_llm` 的判断，直接规则版或 insufficient；不为 30 秒录音烧 token |
| 历史场次 | 没有笔记的旧场次按 `empty` 处理，用户点「生成笔记」才跑；**不批量回填**，避免一次升级烧掉大量 token |

**状态机**：

| 状态 | `/api/note` 返回 | 页面 |
|---|---|---|
| `empty` | 无总结、无任务 | 「生成笔记」CTA + 逐字稿链接 |
| `queued` / `running` | `run_id`、stages、progress | 骨架 + 步骤进度；顶部「可以离开，完成后通知你」 |
| `ready` | 完整笔记 | 正常页面 |
| `partial` | 总结可用、高光缺失或 AI 失败 | 正常页面 + 一条「部分内容未生成」提示 + 重试 |
| `failed` | 错误人话 | 失败卡 + [重试] + [先看原文] |
| `stale` | 总结 fingerprint 与当前逐字稿/模型不一致 | 顶部「原文或说话人有更新，建议重新生成」+ 按钮 |
| `insufficient` | 内容太少 | 「这场内容太少，暂时没有要点」+ 逐字稿 + 导出逐字稿 |

**过期检测**：沿用 `analysis._fingerprint` / `session_digest`。`/api/note` 返回 `stale: true/false` 和原因（文本变了 / 说话人变了 / 模型变了 / 没说）。不要自动烧 token 重跑，给用户按钮。

### 4.6 重新生成与编辑

| 操作 | 行为 |
|---|---|
| 改标题 | 即时保存，不触发重新生成 |
| 改说话人名 | 即时保存；笔记中的显示名刷新；提示「要更新总结里的名字吗？」[重新生成] |
| 改逐字稿（校对） | 在原文页完成；回到笔记页出现 stale 提示 |
| 重新生成 | 二次确认 + 成本预估；可选择「只重建高光」/「全部重建」（v1 可只做全部重建） |
| 生成中离开 | 任务在引擎里继续；完成发通知；页面回来显示 ready |
| 删除笔记 | 不单独删除；删除场次时一起删除（现有清理逻辑） |

## 5. 两个功能的衔接

```
点「结束并生成笔记」
   → 收尾进度卡（保存 / 分人 / 生成笔记）
   → 完成：窗口在前台 → 直接进笔记页
           窗口隐藏   → 系统通知「笔记已生成」→ 点击进笔记页
   → 失败：进度卡 / 通知都给 [重试] 和 [先看原文]
```

关键约定：

1. **只有一个完成态**：收尾结束后，壳的目标视图是 note，不是 workbench。
2. **通知携带深链**：`note_ready` 的 `action_json` 里带 `session_id` 和 `view: "note"`，壳不猜。
3. **记录卡不再展示笔记内容**：记录中不显示总结按钮、不跳笔记页；结束才生成，避免用户在录音时误以为已经总结过。

- `notification_shown`（type）、`notification_click`（type）、`notification_muted`（type）

- `note_point_play`、`note_highlight_play`、`note_export`（format）、`note_copy`
- `note_stale_shown`、`note_stale_regenerate`

不采集逐字稿正文、房间号、通知正文。

### 8.3 上线节奏

1. 内部 dogfood：自己连续录 5 场，覆盖关窗 / 断流 / 无 LLM / 长场。
2. 3–5 名种子用户：看他们第一次结束记录后是否打开笔记；记录卡点。
3. 修 Top 5 卡点后再进封闭 beta；本迭代不面向公网。

## 9. 风险与备选

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Windows toast 点击 / AppUserModelID 在开发态与安装态行为不一致 | 中 | 通知点击无效 | 第一周就做技术验证；点击失败时至少保证 `show_main` + 通知中心可点；必要时用 `windows` crate 直接发 toast |
| `tauri-plugin-notification` 增加依赖 / 权限问题 | 中 | 通知发不出 | 保留应用内通知中心作为兜底；通知失败写日志并在「检查问题」可见 |
| 笔记生成被 LLM 拖慢 | 高 | 用户以为卡死 | 分阶段进度 + 后台生成 + 完成通知；页面先展示逐字稿和已有总结；成本预估 |
| 没有 LLM 时笔记太「干」 | 高 | 首次体验差 | 规则版也要有结构（原话 + 时间码）；文案说明「本地规则」；把配置 AI 放在进阶，不弹窗骚扰 |
| 高光为空 / 不适合 | 中 | 页面缺一块 | 规则版兜底；空模块不显示；内容太短走 insufficient |
| 说话人标签不准 | 高 | 要点归错人 | 沿用现有标注 / 改名；笔记页提供行内改名；不阻塞生成；文档明确这是已知边界 |
| 记录卡与多路视图切换复杂 | 中 | 状态错乱 | v1 严格限定「1 路走记录卡，≥2 路走现有收听视图」；多路批量操作后置 |
| 收尾任务改动影响飞书 digest / 自动总结 | 中 | 回归 | 保留 `submit_summary` 入口；新增 note 任务只串联不改语义；加回归测试 |
| 导航改名「工作台 → 笔记」引起老用户困惑 | 低 | 低 | 同一位置、同一入口；原文入口明显；发布说明写一句 |
| 2 周切片被当成完整交付 | 中 | 期望错位 | 切片明确标注「不含通知中心 / 重新生成 / stale」；不对外承诺 |

## 10. 需要拍板的 4 个点（附建议）

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| 1 | HUD 做独立置顶小窗吗？ | **v1 不做**，只做壳内记录卡 + 托盘 | 独立窗口的生命周期 / DPI / 焦点成本高；记录卡 + 托盘已能覆盖「关窗继续录」 |
| 2 | 结束记录后自动生成笔记吗？ | **自动生成**，不需要再点「AI 分析」 | 「结束并生成笔记」是同一个承诺；多一步点击就多一批没笔记的场次 |
| 3 | 笔记页占「工作台」导航位并改名吗？ | **占位并改名「笔记」**，原工作台留作「查看原文」 | 不新增导航项；完成态只有一个主角；完整 IA 调整留给 P0-7 |
| 4 | 导出先做到哪？ | **笔记 Markdown + 逐字稿 Markdown + SRT + 复制**；分享卡片下一迭代 | 导出是留存动作，卡片是增长动作；先保证内容可带走 |

## 11. 一句话总结

**HUD 解决「敢不敢离开」，通知解决「走了还回不回来」，笔记页解决「回来有没有东西看」。** 这三件事必须一起成立，第一次使用才算成立。
