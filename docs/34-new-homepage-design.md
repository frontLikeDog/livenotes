# 34 · 新首页设计：粘贴链接、最近笔记、关注

> 面向：产品、设计、实现
> 依据：[32 · 桌面客户端产品打磨清单](32-desktop-product-polish.md) §2 / §3.2 / §5，[33 · P0 迭代方案](33-p0-hud-and-note-iteration-plan.md) §0.2
> 结论时间：2026-11-15
> 一句话：**首页不是仪表盘，而是「现在开始记录 + 上次拿到了什么 + 下次为什么回来」三件事。**

---

## 0. 一页纸

### 0.1 这次交付什么

1. **默认启动页变成首页**：打开应用不再进入「收听」监控台，而是一屏能完成主要动作的首页。
2. **一个主输入**：粘贴抖音直播链接，或整段分享文案；自动识别链接、预检、开始记录。
3. **最近笔记**：最近 3–5 篇笔记的卡片流，点一下直接进笔记页；没有笔记时给样本笔记。
4. **关注**：关注直播间 / 主播；首页显示「直播中 / 未开播 / 检测失败」，可一键开始记录；开播提醒和按关注自动记录作为后续能力接上。
5. **主按钮只有一个**：任一时刻，页面上只有一个实心强调按钮。其他操作全部是文字链、幽灵按钮或图标。

### 0.2 不做什么（本迭代）

- 不做完整的笔记库（卡片流 / 搜索 / 筛选 / 批量管理）——那是 P1，最近笔记只取最近 5 条。
- 不做社交关系、账号体系、云端同步；关注只存在本机。
- 不做多关注同时自动记录、批量关注、关注分组。
- 不做首页自定义、组件拖拽、主题市场。
- 不在首页暴露：多路监听、监控墙、文件中心、人物档案、指标、采集方式、LLM Key、飞书、token。
- 不做「关注主播的全部直播日历」——关注列表不是内容 Feed，只是「他开播时提醒我」。
- 不做「AI 问答 / 搜索首页」——先把记录和笔记闭环跑通。

### 0.3 验收口径

- 干净 Windows 11 虚拟机，双击打开应用：**3 秒内**知道下一步是「粘贴链接」；不需要打开命令行、不需要注册、不需要配置 LLM。
- 从首页完成一次记录：粘贴整段抖音分享文案 → 预检卡 → 开始记录；全程 **不超过 3 次点击**（粘贴不算点击）。
- 任一静止画面里只有一个实心强调按钮；设计评审用截图检查。
- 最近一篇笔记从首页打开 **1 次点击**。
- 关注一个主播后，首页能看到他的直播状态；开播提醒走通知链路（依赖 [35](35-hud-tray-notification-design.md)）。
- 900×640 窗口、125% / 150% DPI、键盘操作、深色 / 浅色主题均可用。
- 首页文案不出现「采集 / 断流 / 聚类 / 场次 / token / ASR / 引擎」等工程词。

### 0.4 前置依赖

| 依赖 | 说明 | 没有它时的降级 |
|---|---|---|
| 笔记页（33 方案 B） | 「打开最近笔记」的落点 | 先落到现有「工作台」场次，入口文案改为「打开记录」 |
| 通知链路（35） | 开播提醒、自动记录结果 | 首页只显示状态，不发通知；先做「手动刷新」 |
| 预检 | 链接识别、房间名、开播状态 | 退化为「粘贴后直接开始」，但仍要显示人话错误 |
| 样本笔记 | 首次启动的价值证明 | 用 `seed_demo` 生成 demo 场次，标「示例」 |
| 引擎 `/api/home` | 首屏聚合数据 | 前端并行请求 `/api/rooms` + `/api/sessions`，但会慢一拍 |

## 1. 为什么首页必须重做

### 1.1 现状

现在应用启动后是「收听」工作台（[shell.html](../desktop/dist/shell.html)）：

- 左侧：房间列表 + 隐藏的「添加直播间」输入框；
- 中间：信号波形 / 页面 / 标注舞台；
- 右侧：「这一路 / 状态 / 采集 / 会话 / 时长」检查器；
- 左侧导航：收听 / 工作台 / 文件 / 人物 / 设置。

它回答的是「这一路采集得怎么样」，不是用户打开应用时脑子里的问题：

> 「我听说这个能记直播，我现在该干什么？」
> 「我上次记的那场，笔记在哪？」
> 「我关注的人今天开播了吗？」

### 1.2 三个错位（首页视角）

| 错位 | 现状 | 首页应该变成 |
|---|---|---|
| 能力 vs 任务 | 导航按「收听 / 工作台 / 文件 / 人物」组织 | 按「记录 / 笔记 / 关注」组织 |
| 监控 vs 结果 | 首屏是波形和采集状态 | 首屏是「粘贴链接」和「上次的笔记」 |
| 功能堆 vs 首次价值 | 第一次打开是空库 + 多路 + 设置 | 第一次打开先看到一篇真实笔记长什么样 |

### 1.3 首页必须回答的四个问题

1. **这里能干什么？** —— 一句价值主张，不是产品名。
2. **我现在该做什么？** —— 一个输入框、一个主按钮。
3. **我上次拿到了什么？** —— 最近笔记卡片，直接可读。
4. **我下次为什么回来？** —— 关注列表里有人开播 / 有未读笔记。

四个问题对应四个模块：价值主张、主输入、最近笔记、关注；顺序不能乱（**记录 > 上次结果 > 关注**）。正在记录时，「当前状态」插到最前面。

## 2. 设计原则

1. **一个主按钮。**
   首屏只有一个实心强调按钮：空闲时是「开始记录」，记录中是「回到记录」。关注卡片的「记录」、笔记卡片的「打开」都是次级样式。任何新增功能不得再加第二个实心按钮。

2. **粘贴即开始。**
   用户不需要理解「房间 / 采集方式 / 浏览器 / 直取 / 共享」。粘贴链接或整段分享文案，剩下的交给预检。平台、房间号、清晰度、采集方式都不问。

3. **先给结果，再要配置。**
   首次启动就能看到一篇样本笔记；不配置 LLM 也能用规则版生成笔记；飞书、AI Key、模型选择全部不在首页出现。

4. **关注是回来的理由，不是内容 Feed。**
   关注列表只回答「他开播了吗？要不要现在记录？」。不做头像流、动态、推荐、粉丝数。

5. **工程词不上首页。**
   「采集」→「记录」；「场次」→「这场直播」；「聚类标签 02」→「说话人 2」；「断流」→「听不到声音」；token / 队列 / 阶段码全部隐藏。

6. **一屏完成主任务。**
   1280×800 下，价值主张 + 输入框 + 最近笔记 + 关注首行应在一屏内；900×640 下至少露出输入框和「最近笔记」标题。不要用大图、轮播、空白留白把主任务推到折叠线以下。

## 3. 信息架构与导航

### 3.1 默认导航

```
首页        ← 默认启动页
笔记        ← 现有「工作台」升级 / 改名；笔记页就绪后指向笔记
关注        ← 新增；首页的关注模块是它的摘要
────────
设置
更多 ▾      ← 文件、人物、多路视图、监控墙、诊断，默认折叠
```

本迭代的最小改动：

- 「收听」从导航里拿掉，改为「首页」；正在记录时首页顶部出现记录条，点「回到记录」进入记录卡（记录卡是 [35](35-hud-tray-notification-design.md) 的 HUD）。
- 「工作台」保留原页面，但导航文案改为「笔记」；笔记页上线后同一位置切到新页面。
- 「文件 / 人物」收进「更多」，不再占一级导航。
- 「设置」保留在底部。

> 决策：**不在本迭代做完整的导航重排**。首页先成立，导航只做「默认页 + 隐藏高级」两件事；完整的「文件 / 人物收进设置」留到 P0-7，避免一次改太多。

### 3.2 首页模块

| 顺序 | 模块 | 出现条件 | 目的 |
|---|---|---|---|
| 1 | 顶部状态条 | 正在记录 / 正在生成 / 有错误 | 让用户知道「现在发生了什么」 |
| 2 | 价值主张 + 主输入 | 始终 | 完成主任务 |
| 3 | 最近笔记 | 始终 | 证明价值、回到上次结果 |
| 4 | 关注的主播 | 始终（空态也给入口） | 给下次回来的理由 |
| 5 | 页脚安全提示 | 始终 | 音频只存本机、关窗继续录 |

宽屏（≥1100px）两栏：

```
┌─────────────────────────────────────────────┬──────────────────┐
│ 价值主张 + 主输入                            │ 正在记录（如有）   │
│                                             │ 关注的主播         │
│ 最近笔记                                     │                  │
│                                             │                  │
└─────────────────────────────────────────────┴──────────────────┘
```

窄屏（<1100px）单栏，顺序：状态条 → 输入 → 最近笔记 → 关注。

### 3.3 首页不出现什么

- 波形画布、房间列表、频道编号、采集阶段、未转写分钟、重叠秒数、token、队列深度。
- 多路监听 / 监控墙入口。
- 文件中心、人物档案、存储清理、回收站。
- LLM 提供商、API Key、模型下载进度（模型没准备好时只用一句「正在准备记录功能…」）。
- 飞书、局域网、分享包、诊断包。
- 「高级设置」大按钮——放进设置或「更多」。

### 3.4 页面骨架

- 内容最大宽度 1120px；宽屏主栏 720–760px，侧栏 320px，间距 32px。
- 页面左右留白 48px（≥1280px）或 32px（<1280px）。
- 卡片圆角 12px，阴影只用在可点击卡片；输入框和主按钮在同一视觉组。
- 所有字号用 rem；计时等数字用等宽数字（tabular-nums）。
- 背景沿用桌面壳的 studio / paper 主题 token，不在页面里写死颜色。

### 4.2 主输入区

**目标**：让「粘贴」成为唯一入口，同时接住用户从抖音复制出来的整段分享文案。

| 元素 | 规格 |
|---|---|
| 输入框 | 单行，高度 56px；左侧链接图标；placeholder「粘贴抖音直播链接，或整段分享文案…」 |
| 输入内容 | 可以是纯链接，也可以是「【阿哲】正在直播… https://v.douyin.com/xxx/」这样的整段文案 |
| 链接提取 | 复用 [watchlink.extract_all](../app/watchlink.py)：取第一个链接，去掉尾部的中文标点 |
| 规范化 | 复用 `rooms.normalize_url`：补协议、去追踪参数、小写 host |
| 主按钮 | 「开始记录」；空输入禁用；点击后按钮进入 loading，不重复提交 |
| Enter | 输入框内按 Enter = 点击主按钮 |
| 粘贴事件 | 粘贴后立即做本地识别：能识别出链接就直接显示识别条，不自动开始 |
| 识别条 | 输入框下方一行：`已识别：抖音 · live.douyin.com/123456` + 「清除」；识别不出时给例子，不弹窗 |
| 辅助文案 | 「支持抖音 / 快手 / B 站 · 音频只存本机 · 关掉窗口也会继续记录」 |
| 错误 | 输入框下方内联显示，红色文字 + 一个下一步提示；不弹模态框 |

**关键行为**

1. **粘贴整段分享文案也能用。** 这是首页最重要的容错：用户从抖音复制出来的往往不是干净链接。
2. **不在输入框里做平台选择。** 平台由链接判断；判断不出才问。
3. **不自动开始。** 粘贴后先预检，让用户确认「记的是这一场」；自动开始会让误粘贴变成误记录。
4. **不读剪贴板。** 只在用户粘贴时处理，不主动读剪贴板，避免隐私惊吓。
5. **重复链接不建第二路。** 已经在记录 / 已关注 / 已在房间列表里，分别给不同的人话提示（见 §4.3）。

### 4.3 预检卡

用户点「开始记录」后，不立刻创建房间，先在输入框下方展开一张预检卡。它是首页唯一的「确认」层。

```
┌─ 确认一下 ──────────────────────────────────────────────┐
│  [抖音]  阿哲 · 今晚聊中小主播的选品与复购                │
│  直播间：live.douyin.com/123456                          │
│  状态：正在直播 · 1 分钟前检测                            │
│  结束后自动生成笔记 · 音频只存本机                         │
│                                                         │
│  [ 开始记录 ]                              [ 取消 ]      │
└─────────────────────────────────────────────────────────┘
```

**字段规则**

| 字段 | 来源 | 缺失时 |
|---|---|---|
| 平台 | 链接域名 | 显示域名，不猜 |
| 主播 / 房间名 | 分享文案里的【主播名】→ 采集端页面标题 | 显示「这个直播间」 |
| 直播间地址 | 规范化后的 URL | 必填 |
| 直播状态 | 轻量检测（复用 watchlink / 平台页面） | 显示「开始后确认」，不阻塞 |
| 预计时长 | **不显示**（不可靠，不要编） | —— |
| 关注勾选 | 可选：「关注主播，开播时提醒我」 | 默认不勾选 |

**分支状态**

| 情况 | 预检卡 | 主按钮 |
|---|---|---|
| 正常 | 显示名称、平台、状态 | 「开始记录」 |
| 已经在记录 | 「这个直播间正在记录」+ 计时 | 「回到记录」（唯一主按钮） |
| 已在关注列表但未开播 | 「已在关注列表」+ 上次直播时间 | 「仍然记录」 |
| 达到 5 路上限 | 「最多同时记录 5 个直播间。先结束一个再开始。」+「查看正在记录」 | 禁用「开始记录」 |
| 链接无效 | 内联人话原因 + 一个正确示例 | 无，回到输入 |
| 陌生网站 | 「第一次记录这个网站：example.com」+「允许并开始」/「取消」 | 「允许并开始」 |
| 检测失败 | 名称 + 「开始后确认直播状态」 | 仍然「开始记录」 |

**开始后的进度**

确认后，预检卡原地变成一条进度条，不跳页：

1. 「正在打开直播间…」→ 2. 「正在连接声音…」→ 3. 「开始记录了」

- 进度文案不用阶段码；每一步超过 5 秒才显示「比平时慢一点，再等等」。
- 失败时：「这个直播间没能开始记录：<人话原因>」+「重试」/「换个链接」；同时保留「查看问题」入口。
- 进度期间可以取消；取消后清理半开的房间，不留垃圾。

### 4.4 正在记录条

首页顶部的状态条是 HUD 的「摘要」，不是第二个播放器。

| 状态 | 文案 | 操作 |
|---|---|---|
| 1 路记录中 | `● 正在记录 00:42:10 · 2 位说话人 · 阿哲` | 「回到记录」 |
| 多路记录中 | `● 2 个直播间正在记录 · 最近 00:42:10` | 「查看」→ 多路视图 |
| 暂停 | `◐ 已暂停 · 阿哲` | 「回到记录」 |
| 听不到声音 | `● 听不到声音了 · 阿哲`（红色） | 「查看」→ HUD |
| 收尾中 | `正在生成笔记… · 阿哲` | 「查看进度」 |
| 笔记已生成 | `笔记已生成 · 阿哲` | 「打开笔记」 |
| 生成失败 | `笔记没生成成功 · 阿哲` | 「去处理」→ 笔记页 |

规则：

- 记录条只显示「最近开始 / 最需要处理」的一路；多路时给「查看」。
- 记录条不显示波形、音量、队列、token。
- 记录条出现时，主输入区仍然可用（容量未满时），但主按钮降级为幽灵按钮。
- 应用从托盘恢复时，如果用户是通过托盘「打开记录卡」进来的，直接进 HUD，不经过首页；正常启动才进首页。

### 4.5 最近笔记

**数据来源**：`sessions` + 笔记状态（`notes` 表 / 现有 `summaries`）。本迭代不新建笔记库，只做首页摘要。

**卡片结构**

```
┌──────────────────────────────────┐
│ 中小主播的选品与复购               │  ← 标题，2 行截断
│ 阿哲 · 11-14 21:03 · 1 小时 42 分 │  ← 主播 · 日期 · 时长
│ 低价不是核心，复购取决于选品和信任… │  ← 一句话总结，2 行截断
│ 3 个要点 · 3 段高光 · 2 位说话人    │  ← 能力标签
└──────────────────────────────────┘
```

| 元素 | 规则 |
|---|---|
| 标题 | 优先笔记标题；没有则用 AI 标题 / 日期 |
| 主播 | 场次的房间名 / 主播名；没有则「未知主播」 |
| 时间 | `MM-DD HH:MM`；今天的显示「今天 21:03」 |
| 时长 | `1 小时 42 分`；不足 1 小时显示「42 分钟」 |
| 一句话总结 | `summary.overview` 前 60–80 字；没有则显示「还没有一句话总结」 |
| 能力标签 | 要点数、高光数、说话人数；没有的项不显示，不写 0 |
| 音频 | 已清理时显示「录音已清理」小标；不影响打开笔记 |
| 状态 | 生成中 / 部分生成 / 生成失败 |

**排序与数量**

- 只展示「有笔记或正在生成笔记」的场次，按笔记更新时间倒序；最多 5 条。
- 宽屏 3 列（第一行 3 张，第二行 2 张）；中屏 2 列；窄屏 1 列。
- 「查看全部」→ 笔记库（暂为工作台场次列表）。

**交互**

- 整张卡片可点击；hover 抬升 1px + 边框变亮；键盘 Tab 可聚焦，Enter 打开。
- 不在卡片上放「导出 / 删除 / 重命名」按钮；这些留在笔记页或右键菜单，避免首页变成操作面板。
- 生成中的卡片点击进入笔记页的进度状态，不阻塞其他卡片。
- 生成失败的卡片文案：「笔记没生成成功 · 去处理」，点击进入笔记页重试。

**空状态**

- 有历史场次但没有笔记：显示一张「还没有笔记」的说明卡 + 「记录第一场直播」文字链（把焦点移到输入框）。
- 完全没有数据：显示样本笔记卡（见 §4.7）。
- 全部删除：同上，但不说「错误」，只说「还没有笔记」。

**加载与错误**

- 骨架卡保持与真实卡片相同高度，避免布局跳动。
- `/api/home` 失败：显示「最近笔记暂时读不出来」+「重试」；不影响输入区。
- 首页不展示「数据加载中」的全屏 spinner。

### 4.6 关注的主播

**定位**：关注列表是「开播提醒 + 一键记录」的名单，不是社交 Feed。

**行结构**

```
● 阿哲        直播中 · 开播 12 分钟 · 2 分钟前检测      [ 记录 ]
○ 小林        上次直播 11-12 21:03 · 记过 3 场
◐ 老王        检测失败 · 3 分钟前 · 点此重试
```

| 元素 | 规则 |
|---|---|
| 状态点 | 红色实心 = 直播中；灰色空心 = 未开播；琥珀半环 = 检测失败 / 未知；红色脉冲 = 正在记录 |
| 名称 | 最近一次检测到的房间名 / 主播名；截断 1 行 |
| 状态行 | 直播中：开播时长 + 最近检测时间；未开播：上次直播时间 + 记过几场；未知：检测失败 + 重试 |
| 操作 | 直播中：「记录」（幽灵按钮）；正在记录：「回到记录」；未开播：无操作或「打开直播间」；未知：「重试」 |
| 排序 | 正在记录 > 直播中 > 未知 > 未开播（同组按最近直播时间倒序） |
| 数量 | 首页最多 5 行；「管理」打开完整列表 |

**添加入口**

1. 预检卡上的「关注主播，开播时提醒我」勾选（默认不勾选）。
2. 笔记页标题下的「关注主播」按钮（P1 依赖笔记页）。
3. 首页关注模块的「+ 关注」→ 粘贴链接 → 同一个预检卡，主按钮改为「关注」。

**管理抽屉**

- 完整关注列表（最多 50 个）；每行：名称、平台、直播状态、最近检测、开关（开播提醒 / 自动记录）、移除。
- 顶部「+ 关注」；底部「关注只保存在本机，不会上传」。
- 不显示粉丝数、头像墙、推荐关注。

**空状态**

```
关注一个主播，开播时提醒你。
[ + 关注主播 ]        ← 幽灵按钮，不是主按钮
```

### 4.7 首次启动与样本笔记

**原则**：第一次打开必须看到「一篇笔记长什么样」，但不伪造用户数据。

- 使用 `seed_demo` 生成一场 20–40 分钟的示例场次，标题、说话人、要点、高光、时间码齐全。
- 卡片和笔记页都带「示例」标签；示例场次不计入用户统计，不参与「最近笔记」排序（固定显示在空态位置）。
- 主输入区仍然是唯一主按钮；「先看看示例笔记 →」是文字链，不是第二个按钮。
- 不要求配置 LLM、飞书、模型、账号；如果模型未就绪，示例笔记用预置数据渲染。
- 设置里提供「移除示例数据」，文档里说明示例不占多少空间。

**首次启动的一句话**

> 把一场直播，变成一篇能读的笔记。
> 粘贴链接，记录这一场；结束后自动整理成要点、原话和高光。

不写「欢迎使用」「开始你的旅程」这类空话。

### 4.8 空态、加载、错误

| 状态 | 首页表现 | 下一步 |
|---|---|---|
| 引擎启动中 | 顶部状态「正在准备记录功能…」；输入框禁用；最近笔记显示骨架 | 等待，超过 15 秒给「检查问题」 |
| 引擎未启动 / 断开 | 顶部横幅「记录程序没有启动」；输入框禁用 | 「重试」/「检查问题」 |
| 网络断开 | 输入框可用，预检失败时提示「网络断开，连上后再试」；本地笔记仍可打开 | 「重试」 |
| 磁盘空间不足 | 主输入下方一条黄色提示「磁盘只剩 2.1GB，长直播可能存不下」 | 「清理空间」→ 存储设置 |
| 模型未就绪 | 不阻断记录；只显示「笔记会先用本地规则生成」 | 「了解」 |
| 没有任何笔记 / 关注 | 样本笔记 + 关注空态 | 粘贴链接 |
| 最近笔记读取失败 | 模块内错误卡，不影响输入 | 「重试」 |

### 4.9 窗口尺寸与响应式

| 宽度 | 布局 |
|---|---|
| ≥1200 | 两栏：主栏 760 + 侧栏 320；最近笔记 3 列 |
| 1100–1199 | 两栏：主栏自适应 + 侧栏 300；最近笔记 2 列 |
| 900–1099 | 单栏；侧栏模块移到最近笔记下方；最近笔记 2 列 |
| 700–899 | 单栏；最近笔记 1 列；关注行允许换行 |
| <700（网页版 / 手机） | 单栏；输入框与按钮上下堆叠；卡片 1 列；底部导航 |

- 桌面壳最小窗口 900×640；再小就提示「窗口太小」，不强行挤压。
- 125% / 150% DPI 下不出现横向滚动；按钮文字不换行。
- 深色 / 浅色主题都检查对比度；状态点不能只靠颜色区分（旁边有文字）。

### 4.10 键盘与可访问性

| 操作 | 快捷键 |
|---|---|
| 聚焦主输入 | 启动后自动聚焦；`Ctrl+L` 随时聚焦 |
| 粘贴并识别 | `Ctrl+V`（任意位置，焦点不在其他输入框时） |
| 开始 / 预检 | `Enter` |
| 取消预检 / 清空 | `Esc` |
| 打开命令面板 | `Ctrl+K`（保留现有） |
| 打开最近一篇笔记 | `Ctrl+Shift+N`（可选） |

- Tab 顺序：导航 → 主输入 → 主按钮 → 最近笔记卡片 → 关注行。
- 预检、错误、状态条用 `aria-live="polite"`；不要每秒播报计时。
- 关注开关用 `role="switch"` + 文本标签；状态点有 `aria-label`。
- 焦点环始终可见；不要为了好看去掉 outline。
- 尊重 `prefers-reduced-motion`：卡片 hover、预检展开不做大幅动画。

## 5. 关注：产品规格

### 5.1 关注对象

**决策：关注「直播房间」，不关注「人」。**

- 平台没有稳定、跨房间的人物 ID；抖音的 `web_rid` 就是主播的直播间号，最稳定。
- 关注对象标识：`platform + room_key`（抖音 `web_rid` / 快手 `u/xxx` / B 站房间号）。
- 名称只是展示字段，允许采集端检测后更新；用户改名优先。
- 同一个房间短链 / 长链指向同一个 key，不会重复关注。

### 5.2 添加入口

| 入口 | 行为 |
|---|---|
| 预检卡勾选 | 「关注主播，开播时提醒我」默认不勾选；开始记录成功后写入关注 |
| 首页「+ 关注」 | 粘贴链接 → 预检卡（主按钮「关注」）→ 写入关注，不开始记录 |
| 笔记页「关注主播」 | 从场次房间信息写入关注；已关注则显示「已关注」 |
| 关注管理抽屉 | 「+ 关注」同上 |

写入后立即出现在首页关注列表；直播状态在下一轮检测（≤2 分钟）更新。

### 5.3 直播状态检测

这是关注功能里唯一有技术风险的部分，必须按「宁可说未知，不可误报」设计。

**检测方式**

- 引擎内的轻量 worker，按固定间隔请求直播间页面，解析「直播中 / 未开播」。
- 优先复用平台页面 / 公开接口；不为了检测去启动采集浏览器。
- 支持平台：抖音、快手、B 站。其他平台：显示「无法自动检测」，只保留手动「打开直播间」。
- 不登录、不携带用户 Cookie；使用普通 UA 和只读请求。
- 检测是只读的，不会创建房间、不会开始记录。

**节奏**

| 参数 | 值 |
|---|---|
| 检测间隔 | 默认 120 秒；可在设置里改 60–300 秒 |
| 抖动 | ±15%，避免所有关注同时请求 |
| 并发 | 2 |
| 超时 | 8 秒 |
| 失败退避 | 2 → 4 → 8 → 15 分钟，成功后恢复 |
| 暂停 | 系统睡眠 / 应用退出 / 用户关闭「开播提醒」时停止 |
| 上限 | 50 个关注；超过提示「关注太多，检测会变慢」 |

**状态机**

```
unknown ──成功且直播中──▶ live
unknown ──成功且未开播──▶ offline
unknown ──连续失败 3 次──▶ unknown（显示检测失败）
live ──成功且未开播──▶ offline
offline ──成功且直播中──▶ live（触发开播提醒）
live/offline ──单次失败──▶ 保持原状态，只更新 checked_at
```

- **单次失败不改变状态**：网络抖动不能把「直播中」说成「未开播」。
- **连续 3 次失败**才显示「检测失败」；卡片给「重试」，不自动无限请求。
- 每次检测写入 `last_checked_at`；卡片显示「2 分钟前检测」。
- 直播中状态最多保留 3 个检测周期；超过没有成功检测，降级为未知，避免「一直显示直播中」。

### 5.4 开播提醒与自动记录

**开播提醒**

- 关注后默认开启（每行开关可关）。
- `offline/unknown → live` 时发一条通知：**「你关注的主播开播了」**，正文「《阿哲》正在直播 · 已开播 3 分钟」。
- 同一场直播只提醒一次；直播结束后重置。
- 应用在前台时用应用内提示；隐藏 / 最小化时用 Windows 通知。具体规则见 [35](35-hud-tray-notification-design.md) §6。
- 如果用户已经在记录同一个房间，不再提醒。

**自动记录**

- 每个关注独立开关，默认关闭；首次开启弹确认：

> 开播时自动开始记录？
> LiveNotes 需要保持运行；最多同时记录 5 个直播间。结束记录后会自动生成笔记。

- 触发条件：`→ live` + 自动记录开启 + 未在记录该房间 + 当前记录数 < 5 + 应用在运行。
- 成功后进入 HUD，并发一条低优先级提示「已自动开始记录《阿哲》」；应用隐藏时用系统通知。
- 失败（容量满 / 链接失效 / 平台风控）发一条人话通知 + 「重试」；不静默失败。
- 同一时间只自动开始一路；如果多个关注同时开播，按检测顺序取第一个，其余只提醒。
- 应用启动时检测到关注正在直播：开启自动记录则直接开始，并在通知里说明「已开播 N 分钟」；未开启则只提醒。
- 自动记录不自动停止；下播由看门狗收尾。

### 5.5 关注管理

- 管理抽屉 / 关注页：列表、添加、移除、开播提醒开关、自动记录开关、最近检测时间、打开直播间。
- 移除关注不删除历史笔记 / 录音。
- 支持「暂停全部提醒」总开关（设置 → 通知）。
- 导出 / 导入关注列表：P1；本迭代不做。

### 5.6 数据模型

```sql
CREATE TABLE IF NOT EXISTS follows (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  platform       TEXT NOT NULL,          -- douyin | kuaishou | bilibili | other
  room_key       TEXT NOT NULL,          -- web_rid / u/xxx / room id
  url            TEXT NOT NULL,
  name           TEXT NOT NULL DEFAULT '',
  live_title     TEXT NOT NULL DEFAULT '',
  live_state     TEXT NOT NULL DEFAULT 'unknown',  -- live | offline | unknown
  live_started_at TEXT,                  -- 能拿到就写
  last_live_at   TEXT,
  last_checked_at TEXT,
  last_error     TEXT NOT NULL DEFAULT '',
  notify         INTEGER NOT NULL DEFAULT 1,
  auto_record    INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL,
  UNIQUE(platform, room_key)
);
```

- 不存头像、粉丝数、主播简介——这些会过期，且不是首页需要的信息。
- `live_state` 只是检测结果，不是事实；界面上永远带「检测时间」。
- 删除关注只删这一行；场次表不受影响。

### 5.7 失败与边界

| 情况 | 表现 | 不做什么 |
|---|---|---|
| 平台反爬 / 需要登录 | 状态「检测失败」，保留手动打开 | 不伪造「未开播」 |
| 短链过期 | 关注行显示「链接失效」+ 重新添加 | 不反复重试死链 |
| 直播标题变化 | 每次检测更新 `live_title`；名称不来回跳 | 不用标题覆盖用户改过的名字 |
| 关注 50+ | 提示上限；已有列表保留 | 不静默丢弃 |
| 应用长时间关闭 | 启动后检测一次；正在直播则按自动记录设置处理 | 不补发关闭期间的每条开播通知 |
| 同一主播多房间 | 按 room_key 视为不同关注；产品上提示「可能重复」 | 不自动合并 |

## 6. 接口与数据

### 6.1 `GET /api/home`

首屏聚合，一次返回，避免前端瀑布请求。

```json
{
  "engine": {"ready": true, "starting": false},
  "recording": {
    "count": 1,
    "items": [{
      "room_id": "rm...", "session_id": "...", "name": "阿哲",
      "elapsed_s": 2530, "speakers": 2, "state": "live"
    }]
  },
  "recent_notes": [{
    "session_id": "...", "title": "中小主播的选品与复购",
    "streamer": "阿哲", "started_at": "2026-11-14 21:03",
    "duration_s": 6120, "note_state": "ready",
    "summary": "低价不是核心，复购取决于选品和信任……",
    "n_points": 3, "n_highlights": 3, "speaker_count": 2,
    "audio_available": true
  }],
  "follows": [{
    "id": 1, "name": "阿哲", "platform": "douyin",
    "live_state": "live", "live_title": "今晚聊选品",
    "checked_at": "2026-11-15 20:31", "auto_record": false,
    "notify": true, "last_live_at": "2026-11-15 20:30",

```

- `recent_notes` 最多 5 条；`follows` 最多 5 条，排序在服务端完成。
- `note_state`：`ready | partial | running | failed | empty`（与 33 §4.5 一致）。
- `summary` 只给一句话，不返回完整 payload；首页不加载逐字稿。
- P95 < 150ms（本地 SQLite）；首页首屏不等待模型。

### 6.2 `GET /api/home/status`

轻量轮询（3 秒），只返回会变的部分：

```json
{
  "engine": {"ready": true},
  "recording": {"count": 1, "items": [...]},
  "follows": [{"id": 1, "live_state": "live", "checked_at": "..."}],
  "notices": []
}
```

- 最近笔记只在页面加载和收到 `note_ready` 通知时刷新。
- 不在首页新增 WebSocket；3 秒轮询与现有诊断轮询同源同频，避免多套心跳。

### 6.3 预检

`POST /api/watch/precheck` `{ "text": "整段分享文案" }`

```json
{
  "ok": true,
  "kind": "watch",
  "platform": "douyin",
  "url": "https://live.douyin.com/123456",
  "room_key": "123456",
  "name": "阿哲",
  "live_state": "live",
  "already_recording": false,
  "already_followed": false,
  "capacity_full": false,
  "need_allow": false,
  "reason": ""
}
```

- 复用 `watchlink.decide` / `resolve` / `extract_all` / `share_label`，不重写链接判定。
- `need_allow=true` 时，前端显示「第一次记录这个网站」，确认后调已有的允许逻辑再预检一次。
- 预检不创建房间；确认才开始。短链解析结果缓存 5 分钟。

### 6.4 关注 API

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/follows` | 完整列表 + 状态 |
| POST | `/api/follows` | 添加（url / room_key） |
| POST | `/api/follows/update` | 改名、开关、通知、自动记录 |
| POST | `/api/follows/remove` | 移除 |
| POST | `/api/follows/check` | 手动立即检测一个 / 全部 |

- 写操作成功后返回最新列表，前端不本地拼状态。
- 检测失败也返回 200 + `last_error`，不要用 5xx 让前端只能弹「失败」。

### 6.5 前端落点

- 首页是**基座页面**：`app/web/home.html` + `app/web/js/home/*` + `app/web/css/home.css`，网页版 `/home` 可直接打开，遵循 [29 · 页面宿主契约](29-page-host-contract.md)。
- 桌面壳新增 `home` 视图，iframe `/home?embed=1`；壳只负责导航、托盘、通知、窗口。
- 桌面专属观感（更紧凑的间距、托盘提示文案）放 overlay，不在页面里写 `if (desktop)`。
- 首页通过 `/api/home` 与 `/api/home/status` 取数；不直接读 localStorage 里的房间 / 关注。
- 现有 `listen` 视图保留为「记录中 / 多路」视图；首页「回到记录」切到 HUD（35），多路时切到 `listen`。
- 导航改动最小化：保留现有 `switchView`，新增 `home` 分支；`listen` 不再作为默认 view。

### 6.6 首屏性能

- 首页 HTML + CSS + JS 总量目标 < 120KB（gzip 前）；不引入前端框架。
- 首屏先渲染骨架（价值主张 + 输入框），数据到达后填充卡片；输入框不等 `/api/home`。
- `/api/home` 慢于 500ms 时，输入框仍可用；最近笔记和关注显示骨架。
- 不预加载笔记正文、不预下载音频。

## 8. 指标与埋点

### 8.1 北极星与漏斗

**北极星（本迭代）**：从首页开始一次记录并拿到笔记的成功率。

```
首页打开
  → 主输入聚焦 / 粘贴
  → 预检成功
  → 点击开始记录
  → 进入记录卡
  → 生成笔记
  → 从首页打开笔记
```

目标：

| 指标 | 定义 | 目标 |
|---|---|---|
| 首屏下一步时间 | 打开首页到第一次点击主输入 / 主按钮 | P50 ≤ 5s，P90 ≤ 20s |
| 粘贴识别成功率 | 能识别出合法直播链接的粘贴 / 全部粘贴 | ≥ 90% |
| 预检 → 开始 | 点击开始记录 / 预检成功 | ≥ 80% |
| 开始 → 记录成功 | 进入记录中 / 点击开始 | ≥ 95% |
| 首页 → 笔记打开 | 打开最近笔记 / 首页访问 | ≥ 25% |
| 关注添加率 | 添加关注 / 有笔记的用户 | ≥ 20% |
| 关注 → 开播提醒点击 | 点击开播通知 / 开播通知展示 | ≥ 15% |
| 7 日内二次记录 | 首次记录后 7 天内再次记录 | ≥ 30%（与 32 一致） |
| 首页错误率 | 预检失败 / 预检总数 | ≤ 10%（不含用户误粘贴） |

### 8.3 定性验收

- 检查截图：是否只有一个实心按钮。

## 11. 与其他迭代的衔接

```
首页
 ├─ 粘贴 → 预检 → 开始记录 → HUD（35）
 ├─ 最近笔记 → 笔记页（33 方案 B）
 └─ 关注 → 开播提醒 → 通知（35）→ 一键记录 → HUD
```

- **与 33 笔记页**：首页只给卡片摘要，不重复笔记内容；「查看全部」进笔记库。
- **与 35 HUD / 托盘 / 通知**：首页的记录条是 HUD 的摘要；开播提醒复用 35 的通知中心和系统通知；结束收尾的「后台进行」回到首页时显示记录条状态。
- **与 32 P0**：首页承担 P0-1；样本笔记承担 P0-2 的一部分；预检承担 P0-3；5 分钟预览（P0-5）不在此文档，后续在 HUD / 笔记页接入。
- **与 P1**：笔记库卡片流、全库搜索、分享卡片、周报在首页只留入口，不展开。

## 12. 需要拍板的决策（附建议）

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| 1 | 首页是壳内原生视图还是基座页面？ | **基座页面 + 壳 iframe** | 网页版也要有首页；壳只做窗口 / 托盘 / 通知，符合 29 的宿主契约 |
| 2 | 默认启动页？ | **首页** | 用户打开应用的第一件事是「记录 / 看笔记」，不是「看采集状态」 |
| 3 | 最近笔记是否包含「没有笔记的场次」？ | **不包含**，只显示有笔记 / 生成中的场次 | 「最近笔记」要诚实；没有笔记的场次进笔记库处理 |
| 4 | 关注对象？ | **直播间（platform + room_key）** | 平台没有稳定人物 ID；房间号最可靠 |
| 5 | 直播检测方式？ | **引擎 HTTP 轮询 + 未知态**，不启动浏览器 | 成本低、可解释；失败不误报 |
| 6 | 自动记录默认？ | **关闭**，每个关注单独开启 | 自动录音是敏感行为，必须明确同意 |
| 7 | 导航本迭代改多少？ | **只做默认页 + 隐藏「文件 / 人物」到「更多」** | 首页先成立，完整 IA 留给 P0-7 |
| 8 | 预检是否显示预计时长？ | **不显示** | 拿不到可靠数据，编一个数字会伤害信任 |

## 13. 一句话总结

**首页只做三件事：让用户粘贴一个链接、看到上次的笔记、知道关注的人有没有开播。** 其余能力全部退到它后面；只要首页出现第二个实心按钮，这一版就算失败。
